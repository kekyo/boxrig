# Integrating into an X11 application

[日本語](../../ja/platforms/x11.md)

The boxrig UI X11 component adds a terminal display to an existing parent window, with keyboard, mouse, and IME input.
Core interprets text and manages terminal state; UI handles rendering and input.
Your application connects the parent window, event loop, and communication with a shell or other peer.

The [README example](../../../README.md#add-a-terminal-display-to-an-application) shows a short excerpt for displaying fixed text.
Use the [UI step-by-step guide](../step-by-step/step-by-step-ui.md) to start from window creation, or follow the creation, event, and allocation steps on this page to integrate into an existing application.

## Required libraries

Use the core, UI, and X11 libraries.
Text rendering requires Pango/Cairo, and window integration uses X11, Xrender, Xfixes, Xcomposite, and related libraries.
Add session and POSIX when using a PTY.
See the [build guide](../building.md) and the shared [step-by-step Makefile](../../ja/step-by-step/Makefile) for dependencies and link order.

## Place a component in a parent window

The following function creates a child window displaying a terminal.
Pass an open `Display`, an existing parent `Window`, and a UI model referencing the terminal.
To enable blinking, also provide an [animation runtime](../blinking.md) used by the same event loop.
This excerpt creates a component for your application to call; it does not create the whole window hierarchy.

```c
#include <boxrig/x11.h>

boxrig_ui_status create_terminal_child(Display *display, Window parent,
    boxrig_ui_model *model, boxrig_ui_animation_runtime *animations,
    boxrig_x11_terminal_component **component_out)
{
    boxrig_x11_terminal_component_config config =
        boxrig_x11_terminal_component_config_default();
    config.animation_runtime = animations;
    return boxrig_x11_terminal_component_create_child(
        display, parent, model, &config, component_out);
}
```

On success, the component owns the child window and view.
The application owns the parent, Display, model, and terminal.
Provide allocation dimensions and make the component visible before advancing rendering.

`create_on_target()` can use an existing drawing target.
In that case, the application selects events for the drawing and input targets and manages their visibility, movement, and destruction.
A compatible Visual, depth, and Colormap are required.
For an initial implementation, the child-window approach has fewer responsibilities to manage.

## Advance events and rendering

Pass X events to `boxrig_x11_terminal_component_dispatch_event()`.
Handle unrelated events in the parent or other components.
`BLOCKED` does not mean that input may be discarded.
Make room on the output side, then retry the same event.

After advancing communication, synchronize the model and call `boxrig_x11_terminal_component_frame()`.
If `additional_dispatch` is true, process again before waiting.
If only `frame_pending` is true, you may need to wait for another event.
Do not render continuously in a busy loop.

See the [X11 event loop](../../../examples/boxrig_term/x11/event_loop.c) for waiting that includes IME, the clipboard, and blinking.
The first step-by-step example displays fixed text and disables blinking to keep its waiting logic small.

## Change allocation and size

Once the parent's available area is known, set the position, width, height, and window state in `boxrig_ui_component_allocation` and pass it to `allocate()`.
The returned layout provides usable grid dimensions.

Only one view determines a model's layout.
Retrieve grid resize requests, apply them to the [session](../sessions.md) or core, and report success or failure with `complete_grid_resize()`.
Apply and complete parent size requests caused by font changes or zooming in the host as well.
Distinguish requested dimensions from dimensions confirmed by the OS.

## Choose OpenGL

The standard configuration uses software rendering.
For an OpenGL child window, use the [dedicated creation API](../../../include/boxrig/x11/opengl_component.h) and the `boxrig-x11-ogl` SDK.
See [Rendering options](../renderers.md) for GLX/EGL selection and backend requirements.

If a creation API fails, the application decides whether to switch to another backend.
You can keep the existing terminal and model when creating a new component.

## Cleanup and complete examples

Stop accepting input and registering waits, then release the component, model, and terminal in that order.
Keep the Display and parent window valid until component destruction finishes.

See [Step-by-step](../step-by-step/step-by-step-ui.md) for a complete example and [boxrig_term](../boxrig_term.md) for PTY communication and configuration.
The [public component header](../../../include/boxrig/x11/component.h) specifies the conditions for every operation.
