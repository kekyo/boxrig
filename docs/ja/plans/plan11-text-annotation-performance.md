# plan11：リンク装飾の全履歴探索による入力遅延の修正

作成日：2026年10月28日

状態：段階1〜3を実施済み。段階4の描画比較を終え、処理完了状態の補足確認と全体試験を進めています。

## 目的と対象

elder-termsで、使い続けると1文字の入力反映に2〜3秒かかる問題が報告されました。利用するプログラムはCodex CLIで、Local terminalとSSHの両方で発生しています。別のPCでも症状がありますが、今回の検証は利用者の指定により、このPCだけで行いました。

elder-terms側の調査では、履歴を保持したboxrig UIのリンク装飾処理から、報告された規模の遅延を再現できました。本計画では、表示中の行と装飾を直接照合する方法を第一候補とし、boxrig本体の修正・回帰試験・性能比較を進めます。リンクの表示と操作を保ったまま、継続的な本文更新に伴う全履歴探索を除くことが目的です。

作業先は`~/Projects/boxrig/`です。elder-terms内の`deps/boxrig`や、boxrigが参照する外部依存コードは編集しません。elder-termsへの依存更新、配布、mainへのマージは今回の計画に含めず、修正済みコミットと再現手順を引き渡します。

### 未確認の条件

実際のCodexセッションで、遅い入力と同じ関数の負荷を直接対応付ける確認は残っています。SSHで出力を追加し続ける試行では、2キー目の反映を10秒以内に観測できませんでした。出力の滞留や通信側の待ちを分解していないため、この失敗を装飾の問題だけで説明したとは扱いません。

今回の再現は本文中のHTTP・HTTPS URLを使っています。端末の制御列OSC 8だけで指定されるリンクや、URLを含まない長時間利用まで同じ原因だとは断定しません。boxrig側の修正完了と、報告された実利用上の問題すべての解消は区別します。

## 用語と現在の処理

論理行は、画面幅による折り返しをつないだ本文の1行です。物理行は、折り返し後の画面上の1行を指します。boxrigでは物理行の断片をfragmentとして参照でき、画面の種類、論理行ID、論理行内の開始列、内容の版である`line_revision`を取得できます。

annotationは、本文の範囲に色や下線を対応付けた装飾情報です。再描画範囲を表すdirtyは、変更後に描き直す必要がある画面領域を指します。可視範囲は、現在のスクロール位置で表示している物理行の集合です。

| 処理 | 現在の実装と問題 |
| --- | --- |
| 行IDからの位置探索 | [view.c](../../../src/ui/view.c)の`find_line_bounds()`が、履歴の先頭からfragmentを走査する |
| 再描画範囲の計算 | 本文全体の版が変わると`mark_all_text_annotation_dirty()`が全装飾を処理し、装飾ごとに全可視行を調べる |
| 行と範囲の重なり判定 | `range_logical_interval()`が範囲の始点・終点・対象行のそれぞれを履歴から探す |
| 装飾の描画問い合わせ | `text_annotation_visual_ranges()`が、装飾の有効性確認と範囲計算で同じ探索を行う |
| マウス位置の装飾判定 | `boxrig_ui_view_query_text_annotation_hits()`にも、装飾の有効性を調べる全履歴探索がある |

履歴を含むfragment数をH、保持する装飾数をA、可視物理行数をRとすると、現在の経路にはA×R×Hに応じて増える走査があります。これは処理全体の厳密な計算量の式ではなく、今回確認した反復探索の増え方です。描画では文字の配置計算など、ほかの費用も発生します。

[公開APIコメント](../../../include/boxrig/ui/view.h)は、装飾1件の範囲が同じ論理行に収まることを要求しています。`validate_text_annotation()`も始点・終点の画面、行ID、行の版を検証します。一方、可視行のfragmentは、既存の`view_fragment_index()`から直接参照できます。この2つを組み合わせれば、装飾の表示判定に論理行同士の前後関係を求める必要がありません。

## 解決案の比較と採用方針

### 案1：可視行と装飾を直接照合する

可視fragmentの画面、行ID、行の版を装飾と比較し、列範囲の重なりを求めます。画面外の別の論理行であれば、その場で対象外と判断できます。同じ論理行でも折り返し位置が異なる場合は、fragmentの開始列と可視列数で装飾範囲を切り取ります。

モデル同期、描画問い合わせ、マウス位置の判定に適用し、継続更新時の装飾処理からHの要因を除きます。既存の公開APIで必要な情報を取得できるため、新しい公開APIや全履歴キャッシュを前提にしません。A×Rの照合は残ります。今回の第一候補です。

複数の論理行にまたがる選択や検索結果は、単一論理行という制約を持ちません。装飾専用の範囲計算を設け、共有の`range_logical_interval()`を一律に単一行用へ変更することは避けます。装飾を登録する際の検証に残る探索も別に計測し、すべての履歴関連処理が一定時間になったとは扱いません。

### 案2：装飾を行IDごとにまとめる

保持する装飾を画面と行IDで引けるようにし、表示行に属する装飾だけを取得します。案1の後も残るA×Rの比較を減らし、画面外に装飾が増えた場合の費用を抑える方法です。案1の後に同じ条件で測り、非表示の装飾数による負荷が主要因として残る場合だけ実施します。

索引は装飾の追加・置換・消去に合わせて更新し、本文変更のたびに全装飾から作り直さない構成を検討します。照合結果を可視行ごとに保存する場合は、スクロール位置、画面切り替え、行の版、レイアウト、装飾集合の変更に応じた失効が必要です。装飾の重なり順や容量上限も維持します。

変更行だけを再計算する方法は、さらに細かな最適化です。最初から差分管理を広げると、古い下線の消し忘れや再計算漏れが起こりやすくなります。索引による絞り込みを先に評価し、残る負荷を確認してから判断します。

### 案3：履歴全体に行IDの索引を設ける

行IDから保存位置を直接引ける共通の索引をcore側に設ける案です。装飾に加え、複数行の選択など、行の位置を必要とする処理にも利用できます。保持履歴に応じたメモリーと、履歴の追い出し、行移動、幅変更による折り返し直し、画面切り替えへの対応が必要です。

[fragment APIのコメント](../../../include/boxrig/terminal.h)が示すとおり、fragmentの添字は端末更新で変わり得ます。古い添字をそのまま使うことはできません。また、本文の版が変わるたび全索引を作り直すと、1文字の更新ごとにO(H)の仕事が残ります。今回の単一行装飾には案1を優先し、共通索引は追加の必要性が確認された場合の別設計とします。

### 案4：elder-termsが登録する装飾を可視範囲に限る

アプリ側で認識結果を保持し、boxrig UIへ渡す装飾だけを表示範囲に絞る方法です。boxrigの更新を待てない場合の候補ですが、スクロール時の再登録、表示の遅れ、クリック対象の復元が必要になります。boxrig内部の全履歴探索も残るため、本計画の製品修正には採用しません。

### 案5：リンク機能の無効化や履歴上限の削減

リンク機能の無効化は、今回の測定で効果を確認した暫定回避です。履歴上限を減らす方法も探索量を抑えられますが、リンク操作や過去の本文を参照する機能を制限します。リンク機能を有効にした状態での修正確認を、本計画の完了条件とします。

処理順の変更や別スレッド化だけでは、反復する探索の総量は減りません。古い装飾を使用しないための同期も増えるため、第一段階の解決策にはしません。認識器の`LINE_REPLACED`や`LINE_EVICTED`は利用候補になりますが、認識器以外の装飾やイベント欠落まで表す通知ではありません。これらの通知だけを正しさの根拠にする案も採用しません。

## 修正時に維持する動作

表示に使う装飾は、現在の画面、行ID、行の版と一致するものに限ります。行IDの`epoch`と`serial`は識別に使い、数値の大小を本文の並び順の代わりにしません。同じ論理行の先頭が履歴から失われ、折り返しの途中から保持されている場合も確認します。

表示の有効性確認と、古い表示を消すためのdirty計算は分けます。内容が変わって無効になった装飾でも、以前の下線や色が残っていれば消去が必要です。行の版が違うという理由だけで、旧表示の再描画まで省略しないようにします。履歴から消えた行IDは現在位置へ直接対応付けられないため、モデル本体のdirtyや表示位置変更時の全面再描画も含め、古い装飾が消えることを確認します。

論理列から表示列への変換は、現在の文字レイアウトを使います。双方向文字では1件の装飾が複数の表示範囲に分かれる場合があります。全角文字、結合文字、装飾の重なり順、必要件数の問い合わせ、容量不足時に部分結果を返さない契約を保ちます。置換時の検証・メモリー確保が失敗した場合も、保持している装飾集合を途中の状態にしません。

同じモデルに複数のビューがある場合は、各ビューの表示位置とレイアウトに従います。primary画面とalternate画面、本文の変更、装飾の置換、スクロール、リサイズで、古い描画結果やマウス位置の判定を再利用しないことを確認します。

## 段階1：boxrig単独で実行できる再現試験を整える

既存の[UI試験](../../../tests/test_ui.c)と[リンク連携試験](../../../tests/test_example_text_policy.c)を利用し、描画を伴わない最小ドライバーを`tests/performance/`へ追加します。elder-terms側の最小ドライバーを参照しつつ、boxrigのMakefileからビルド・実行できる成果物にします。本文更新後も、保持履歴、装飾の有効性、表示される装飾件数が想定どおりであることを検証します。

H、A、Rを独立に変えます。基準は193列・45行、履歴0・1千・5千・1万行、装飾0・1・10・100件です。行ごとに装飾を分散させる条件では、存在する行数に合わせて組み合わせを選びます。装飾が画面外に多数あり、可視範囲には1件だけある条件を必ず含めます。

登録・初期化と、1文字更新後のモデル同期・装飾範囲問い合わせ・マウス位置の判定を分けて測ります。各条件を複数回実行し、順序を逆にした結果も保存します。CPU時間、実時間、実際の保持履歴と装飾数、ソースのコミット、バイナリ、ビルド条件、アロケーターを記録し、ビルドや全体試験と同時に性能値を測りません。

処理量の回帰試験では、固定のミリ秒制限だけに依存しません。静的リンクした試験でfragment取得回数などを観測し、AとRを固定したときに、継続更新の参照量がHに比例しないことを検証します。同期・可視行の範囲問い合わせ・マウス位置の判定を別々に数え、少量履歴と1万行の両方に、RとAから定めた同じ有限上限を適用します。[既存のMakefile](../../../Makefile)にはUI試験で関数をラップする構成があります。具体的な呼び出し回数は代理指標です。測定器の動作を確認し、Hを増やしても緩めない上限を修正前に定めます。現在の実装の厳密な回数に合わせた期待値や、ソース文字列の検査にはしません。

成果物は実行可能なドライバーと修正前の基準値です。少量・大量履歴で表示結果が同じことを確認し、現行版が性能要件を満たさないREDを次の修正前に記録します。ドライバー自体の検証はGREENにし、計測基盤を`chore:`でコミットします。

## 段階2：直接照合に置き換え、履歴依存を除く

段階1で失敗した処理量の試験に対し、案1を実装します。最初から全履歴索引や新しい公開設定は加えません。モデル同期、描画問い合わせ、マウス位置の判定を同じ方針で修正し、使われなくなった専用処理があれば整理します。選択や検索など、残る利用先がある共有処理は維持します。

再描画前の装飾の消去、古い行の版の除外、マウス位置の判定について、変更前に問題を再現する試験を確認してから修正します。性能だけの変更で既存の機能試験が成功する場合は、機能の期待値を変更して無理にREDを作りません。

成果物は、履歴探索を除いたboxrig UIと、修正前後を比較できるドライバーです。AとRが同じ条件でHを増やしても、対象3経路の走査量にHの要因が残らず、表示範囲・dirty・判定結果が一致すれば完了とします。対象試験のGREENと再測定を確認し、`fix:`でコミットします。

## 段階3：残る装飾数依存を評価し、必要なら索引を加える

段階2の成果物で、HとRを固定してAを増やします。画面外の装飾を増やした条件と、表示中の装飾を増やした条件を分け、同期・描画問い合わせ・マウス位置の判定・装飾登録のどこに時間を使うか調べます。

案2に着手する条件は、画面外の装飾を増やすと入力遅延が繰り返し増え、A×Rの照合が主要因として残ることです。該当しなければ索引は追加せず、案1で十分と判断した測定条件と根拠を記録します。機械性能だけに依存する合否を避け、処理量とCPUプロファイルを合わせて判断します。

案2を実施する場合は、装飾の置換・消去や行の失効を含む試験を先に追加し、非表示の装飾数に比例する参照量についてREDを確認します。索引の更新と範囲問い合わせを一つの実行可能な成果物として仕上げます。本文の変更ごとに全装飾を組み直す費用が移っただけになっていないことも測定対象です。

成果物は採否の記録、採用時は索引を使うboxrigと回帰試験です。採用時には、可視行の問い合わせとdirty計算が非表示の装飾数に比例せず、結果・優先順位・失効処理が保たれることを完了条件とします。修正は`fix:`または`refactor:`、採否と比較結果は`doc:`でコミットします。

全履歴索引、認識器の変更、さらに細かな変更行管理が必要と分かった場合は、その根拠を記録して計画を見直します。案3以降へ自動的に作業範囲を広げません。

## 段階4：実際の描画と全体の回帰を確認する

GTKサンプルと既存の認識連携試験で、修正済みライブラリを使います。まずCairoとOpenGLを同じ履歴量、リンク有効、実表示サイズで比較します。履歴準備と認識が終わった状態での入力、大量出力中、出力停止後に仕事が残る状態、処理完了後の入力を分けて記録します。

Codex型の負荷では部分スクロール領域、固定した入力欄、日本語、同期更新を組み合わせます。キー送出、相手プログラムへの到達、応答の受信、モデル同期、描画、画素への反映を可能な範囲で対応付けます。修正前後で中央値・p95・最大値、CPU時間を比較し、計測を軽くした試行でも傾向を確認します。装飾を減らす設定変更で速くした結果を、案1の効果として扱いません。

本文変更やスクロールをまたぐ装飾の動作は動画を記録し、古い下線の消去、新しい下線の到達、応答の順序をアサートします。画素観測の時刻と物理モニターの走査完了は区別します。画像判定のマスターを追加・変更する場合は、採用前に目視で確認します。

既存の`test-gtk-sample-recognition`、`test-decoration-backends`、`test-selection-history`、`test-selection-layout-provider`などを利用します。共通UIの変更が影響する他の描画系も、対応する既存試験で確認します。実装完了時は`make test`を最後まで実行し、ビルド警告、失敗、スキップ、未実施条件を分析して記録します。必要な環境がない場合は、その制約を明記し、未確認の描画系まで成功と報告しません。

成果物は、修正後の入力遅延・描画・全体試験の記録と、elder-termsへ取り込めるコミットです。既存機能を保ち、再現条件で支配的だった全履歴探索が解消され、実描画でも改善を確認できたら完了とします。追加試験は`chore:`、結果と必要な文書更新は`doc:`でコミットします。
