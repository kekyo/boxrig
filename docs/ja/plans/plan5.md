# plan5: 認識・部分描画・操作応答の残課題

## 目的と開始点

[plan4-2](plan4-2.md)の完了後に検討した5つの課題を引き継ぐ。boxrigとgnome-terminalの実装・挙動を比較し、余分な処理と遅延の原因を明らかにして改善する。

計画保存時のHEADは `a81294cce271d1d7112b872a850cfc17612ebdf4`。plan4の変更をdevelopへ取り込んだコミットで、作業ブランチは `feature/plan5` である。以下の測定値はplan4-2の実施結果を参照し、plan5の新しい測定結果とは区別する。

優先するのは、認識処理に残る全履歴走査の削減と、ときどき発生する遅延の原因特定である。最初の実装候補は変更のない行を、認識用の文字列へ作り直す前に除外する処理とする。余分な処理がコードと計数の両方で確認できており、変更範囲を絞って効果を検証しやすいためである。

DSRは端末の状態を問い合わせる制御列で、この計測では応答を入力処理の終点に使う。DSR応答、認識完了、描画処理の完了、実ディスプレイへの提示は、それぞれ異なる時点として扱う。

## 課題1: 認識結果を再利用する前にも、行全体を読み直している

plan4-2で省けたのは、主に「一致しなかった行の文字準備と正規表現照合」である。その判定前に、セルから認識用の文字列と位置情報を作り直している。この処理を以下では投影と呼ぶ。履歴10,024行で初回認識を完了した後、最終行を上書きする計測では、調べるセル数が1,611,600件のまま残っていた。

まず、変更のない行を文字列の作成前に判定できれば、追加の削減が期待できる。一致がある行の結果再利用と、最大8,192件のキャッシュで発生する取りこぼしも、その次の候補である。キャッシュの上限や保存位置の衝突によって通常の照合へ戻るため、ヒット率と保持量を合わせて確認する。

対象は [recognizer.c](../../../src/core/recognizer.c) の行スナップショット取得と `cached_empty_line()` の判定、および [text.c](../../../src/core/text.c) の `boxrig_terminal_reuse_text_line_snapshot()` である。現在は行の投影後にキャッシュを調べ、投影では必要量の計測と書き込みのため同じ行を2回走査している。

初回認識と、その完了後の更新を別の負荷として測る。最初は前回一致がなかった変更のない行を対象にし、一致がある行やキャッシュ方式の変更は独立した試行として採否を判断する。結果ID、認識範囲、通知、0件になった行の問い合わせ、履歴破棄、再折り返し、画面切り替え、途中の再編集、確保失敗時の動作を維持する。

## 課題2: 初回認識の時間と、まれに遅くなる試行の内訳が未確定

履歴ありの測定では、入力応答後も認識完了まで約65〜73ミリ秒残る。これは認識完了までの経過時間であり、画面がその間ずっと停止するという意味ではない。履歴準備後にDSRだけを待って入力を始めており、履歴の初回認識を完了させた状態での更新とは区別する。文字列の作成、正規表現、結果反映、イベント処理の待ち時間を分ける必要がある。

また、通常製品の履歴なし日本語入力では、中央値が約11ミリ秒の条件で、DSR応答まで約60ミリ秒かかった試行があった。本測定5回のうち1回が59.687ミリ秒で、送信39.995ミリ秒と送信後19.692ミリ秒の両方が伸びている。試行数を増やし、遅い回にどの処理が重なったかを追うことが、引っ掛かりの改善につながる。

計測には [既存の性能比較ドライバー](../../../tests/performance/) と [GTK3のイベント処理](../../../examples/boxrig_term/gtk3/event_source.c) を使い、初回認識中と認識完了後を分ける。入力の書き込み、端末の読み取りと処理、認識の実行区間、再開までの待ちを記録し、速い回と遅い回を比較する。計測を加えたことによる負荷も通常製品との比較で確認する。

約65〜73ミリ秒の全体を正規表現のCPU時間とは扱わず、遅い試行も除外しない。実行環境や録画方法へ原因を帰属させる場合も根拠を確認する。原因が未特定なら、その状態と再現条件を記録する。修正候補が得られた場合は、原因・対象・検証方法を本計画へ追記してから独立して試す。

## 課題3: 小さな再描画でも、文字色・文字・装飾は行全体を処理している

背景色の走査は変更列に限定したが、色の準備や文字・下線などの処理には、行全体の走査が残っている。カーソル、選択、URLの強調など、小さな更新が多い場面の候補である。

文字の整形結果を維持しながら、必要な表示範囲だけを処理できるか試す。全角文字、双方向文字、隣のセルにはみ出す字形を壊さないことが条件になる。現在も描画範囲はクリップしているため、行全体を調べていることと、全ピクセルを更新していることは区別する。

対象は [Pango/Cairo描画処理](../../../src/pangocairo/renderer.c) の `prepare_row_colors()`、`draw_terminal_row()`、`draw_shaped_item()`、`draw_decorations()` である。まず色の準備、次に文字と装飾の処理を、それぞれ変更前後で比較できる単位に分ける。背景色、選択、注釈、画像との重なりを維持し、文字の整形や双方向文字の並べ替えまで不要になるとは仮定しない。

1セル、複数セル、行全体の更新で、処理するセル・文字区間の数と実時間を測る。部分更新後の画像を全面描画の結果と照合し、画面幅を広げた場合の費用も確認する。

## 課題4: 日本語や、一括処理の対象外になる入力経路

現在の一括処理はASCIIに限定している。また、画像配置の追跡やテキスト変更の監視など、条件によって通常の文字単位処理へ戻る。

次は日本語入力の解析・文字幅判定・結合文字処理・セル更新を分けて測り、繰り返しが多い部分を探す。ASCIIの改善率をそのまま期待できるわけではなく、現状のプロファイルを取り直して判断する対象である。

対象は [parser.c](../../../src/core/parser.c) の印字処理と [screen.c](../../../src/core/screen.c) の `boxrig_screen_put_ascii_run()` および通常の文字配置処理である。一括処理できた割合と通常経路へ戻った条件を記録し、日本語自体の費用と、ASCIIでも一括処理できない場合の費用を分ける。

プロファイルで費用を確認した候補から、具体的な変更範囲と適用条件を本計画へ追記し、1件ずつ試す。文字幅、結合文字、絵文字、制御列との境界、分割された入力、確保失敗時の消費済みバイト数、セルと通知の結果を維持する。機能を無効にした比較は原因の切り分けに使い、製品の改善結果とは分ける。

## 課題5: GNOMEとの「操作中の応答」の比較がまだ不足している

DSR応答では改善を確認できたが、連続出力中のキー入力、スクロール、選択操作、フレーム間隔まで同じ条件で比較できてはいない。接続済みのFHDモニターを独立した環境として使い、これらを確認する。残る差が入力処理・認識・描画・処理の実行順序のどこにあるかを絞るための比較とする。

boxrigとgnome-terminalで、端末の行列数、フォント、履歴量、出力負荷、操作列、表示環境を合わせる。バージョンと設定を記録し、最初に1種類の操作を再現できる比較を作ってから、他の操作へ広げる。比較対象を同時に動かさず、操作から応答までの時間と更新間隔の分布を残す。

何をもって操作や表示の完了とするかを先に定義する。boxrigの内部処理の完了とGNOMEの外から観測した表示を、同じ終点として比較しない。DSRだけから滑らかさを判断せず、共通に測れた範囲と測れない範囲を示す。差の原因候補は計測した版の実装と対応づけて確認する。

動画は必要な時間軸の挙動を確認する手段とし、外部キャプチャー機器は要件にしない。取得周期、欠落・重複、タイムスタンプ、撮影負荷を確かめ、内部計測と食い違う場合は取得方法も調べる。時間軸の挙動を変更した場合は、動画による回帰テストで確認する。

## 試行の進め方と段階ごとの完了条件

課題1から順に、現行コードの確認、再現するテストまたは計測ドライバー、最小限の変更、検証、採否の記録を進める。課題1と2を優先し、その結果を踏まえて課題3以降へ進む。課題内でも独立した候補を一度に混ぜず、各段階でドライバーまたはサンプルを実行できる状態とコミットを残す。

コードを変更する場合は、問題や余分な処理を再現するテストの失敗を確認してから修正し、成功を確認する。公開API、認識結果と通知、入力途中の状態、描画結果を維持し、時間とメモリの悪化も含めて採否を判断する。時間差が測定のばらつきと重なる場合は、処理量の削減と速度の改善を分けて記録する。

## 計画全体の完了条件

- 5つの課題について、原因の根拠、対象、測定条件、結果、採否と理由を本書へ記録している。
- 採用した変更を個別にコミットし、各段階でビルド・テストとドライバーまたはサンプルの実行を確認している。
- 入力処理の短縮、入力後に残る認識、描画と表示、待ち時間を区別し、遅い試行や未特定の原因を残している。
- 性能計測とビルド・テストを重ねず、比較順序、通常製品と計測用製品の違い、生データと再実行手順を記録している。
- 実装を伴う作業の最後に全体テストを完走し、既知の失敗・スキップと新たな回帰を区別している。plan4-2の基準は20実行コマンドの失敗と15件のスキップであり、環境が変わった場合は差を確認する。
- コンパイル警告、メモリエラー、Cairo終了時の再発を確認し、保留した候補と残課題を明示している。

本書の保存時点では計画の実装は開始していない。文書のみの変更でビルドには影響しないため、保存時の確認は記述内容、日本語、参照先、差分の確認とする。
