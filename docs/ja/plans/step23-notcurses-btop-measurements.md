# notcurses-demoとbtopで測ったboxrigの描画性能

2026年11月20日、LinuxのX11実機でboxrigの`ca31e0371d637ba7d06875b2a124599af92ba9ed`を計測しました。notcurses-demoの対象は、多色の罫線を描くgridと動画を表示するxrayです。btopではCPU、メモリー、ネットワーク、プロセスの4パネルを表示しました。

## 実アプリの送信速度と端末CPU時間

表の「X11」はネイティブX11端末サンプル、「GTK3」は同じX11サーバーで動かしたGTK3端末サンプルを指します。値は各条件3試行の中央値で、括弧内は最小値と最大値です。端末CPU時間はboxrigプロセスの全スレッドが使ったユーザー時間とシステム時間の和です。子プロセスで動くアプリのCPU時間は別に測りました。

| boxrigの描画構成 | gridの送信完了（秒） | gridの端末CPU（秒） | xrayの送信完了（秒） | xrayの端末CPU（秒） |
| --- | ---: | ---: | ---: | ---: |
| X11 OpenGL ES | 10.21（10.16〜10.28） | 4.87 | 11.87（11.87〜11.89） | 5.85 |
| GTK3 OpenGL | 1.02（1.02〜1.03） | 0.91 | 10.36（10.30〜10.40） | 5.03 |
| GTK3 Cairo | 2.03（1.94〜2.14） | 1.90 | 10.03（9.85〜10.05） | 5.20 |

notcurses-demo 3.0.7を`-c -d 0.03 g`と`-c -d 0.03 x`で起動しました。デモが報告した送信フレーム数は、gridが全試行で768、xrayが全試行で887でした。1試行の記録量はgridが約119 MiB、xrayが約1.69 GiBです。xrayは再生が遅れると送るフレームを間引くため、送信時間と枚数を併記しています。画面に反映されるまでの時間は、後述の固定入力で測りました。[notcurses 3.0.7のxray実装](https://github.com/dankamongmen/notcurses/blob/v3.0.7/src/demo/xray.c#L93-L118)

X11 OpenGL ESのgridでは、疑似端末（PTY）への書き込みがデモの実行時間の96%を占めました。3構成それぞれの記録をboxrigの端末コアだけで再生すると、入力の解釈に使ったCPU時間は0.56〜0.58秒でした。[端末コアの再生ドライバー](../../../tests/performance/notcurses_replay.c)

### X11で画面更新を待つ時間

記録用の`script`を外し、boxrigのPTYでgridを直接起動しても差が出ました。デモ起動から終了までの中央値はX11 OpenGL ESが10.24秒、GTK3 OpenGLが1.31秒、GTK3 Cairoが2.85秒でした。各3試行です。

X11の端末は、端末入力を取り込むイベントループの中で描画し、`eglSwapBuffers`で描画結果をウィンドウに渡します。既定の交換間隔1は、画面の更新に合わせてバッファを交換する指定です。間隔0はその同期待ちを外す指定です。[X11のイベントループ](../../../examples/boxrig_term/x11/event_loop.c)・[バッファ交換](../../../src/x11_opengl/component.c#L1077)・[交換間隔の既定値](../../../src/x11_opengl/component.c#L1596)・[EGLの交換間隔の仕様](https://registry.khronos.org/EGL/sdk/docs/man/html/eglSwapInterval.xhtml)

75 Hzのモニター上で同じX11の計測用バイナリを動かし、要求する間隔だけを1と0に切り替えました。実行順を入れ替えて各3回測り、すべての試行でgridは768フレームを送りました。

| X11のgridで測った項目 | 交換間隔1（既定） | 交換間隔0（比較用） |
| --- | ---: | ---: |
| デモの送信完了（秒） | 9.89（8.87〜9.97） | 3.52（3.49〜3.53） |
| 端末CPU時間（秒） | 3.70 | 3.53 |
| バッファ交換の呼び出し回数 | 744 | 754 |
| 交換呼び出し内の経過時間の合計（秒） | 6.33 | 0.029 |
| 交換呼び出し内のスレッドCPU時間の合計（秒） | 0.139 | 0.029 |
| 連続する交換完了時刻の間隔（中央値、ms） | 13.32 | 4.75 |

既定の13.32ミリ秒は75 Hzの1周期に相当します。交換呼び出し内で経過した約6.33秒のうち、呼び出しスレッドがCPUを使ったのは約0.14秒でした。交換間隔を変えると、この待ち時間とデモの送信時間がともに縮まりました。実アプリ36試行のホスト全体のCPU使用率は約7〜16%、交換間隔の比較時は約69〜72%でした。比較試行の値は同じ時間帯の組で解釈します。

GTK3では入力をまとめて描きます。既定設定のgridを別に3回ずつ計測すると、OpenGLの描画呼び出しは中央値35回、Cairoの描画は86回、Cairo画像を表示するGTKの描画通知は64回でした。gridを送り終える速さには、768回の送信を何回の描画にまとめるかという違いも含まれます。GTK3 Cairoで端末のユーザーCPUをサンプリングすると、整形済みの字形を描く処理に31.32%、行の字形を決める処理に1.44%を使っていました。[GTK3の描画予約](../../../src/gtk3/terminal_widget.c#L3549)・[Cairoの字形描画](../../../src/pangocairo/renderer.c#L4441)

## btopの更新頻度とCPU使用率

btop 1.3.0の更新間隔を2,000ミリ秒と100ミリ秒に設定しました。時計は非表示です。最初の画面出力から4.2秒待ち、続く12秒間に受信した同期更新の終了を数えました。これはbtopが一連の書き換えの終わりを端末に伝える制御シーケンスです。CPU使用率は論理CPUを1個使い切ると100%です。

| boxrigの描画構成 | 2秒更新の端末CPU | 100ミリ秒更新の端末CPU | 100ミリ秒更新のbtop自身のCPU | 受信1更新あたりの端末CPU時間（100ミリ秒設定） |
| --- | ---: | ---: | ---: | ---: |
| X11 OpenGL ES | 0.42% | 7.91%（7.49〜8.66%） | 14.98% | 7.98 ms |
| GTK3 OpenGL | 0.50% | 9.57%（9.24〜9.74%） | 16.23% | 9.66 ms |
| GTK3 Cairo | 0.58% | 9.74%（9.41〜11.07%） | 14.65% | 9.92 ms |

2秒設定では12秒間に6更新、100ミリ秒設定では118〜119更新を受信しました。CPUカウンターの分解能は10ミリ秒です。12秒の計測では、CPU使用率の刻みは約0.08ポイントになります。btop終了後、カーソルを隠した空の画面で3秒待つと、18試行すべてで端末CPUカウンターの増加は0でした。

100ミリ秒設定での端末プロセスのピーク常駐メモリーは、X11 OpenGL ESが146 MiB、GTK3 OpenGLが154 MiB、GTK3 Cairoが68 MiBでした。いずれも起動から観測終了までの最大値を試行ごとに取り、その中央値を示しています。

### 変更していないセルの字形整形

100ミリ秒設定のbtopで端末プロセスを20秒間サンプリングしました。文字列から字形と位置を決める行整形関数に、端末のユーザーCPUサンプルの44.97%（X11 OpenGL ES）、39.86%（GTK3 OpenGL）が集まりました。GTK3 Cairoでは行整形が24.19%、整形済みの字形を描く処理が24.42%でした。各割合には呼び出し先で使ったCPUを含みます。[OpenGLの行整形](../../../src/opengl/text_provider.c#L1266)・[Cairoの行整形](../../../src/pangocairo/renderer.c#L3582)・[Cairoの字形描画](../../../src/pangocairo/renderer.c#L4441)

1回分のbtop出力から連続する24更新を取り出し、同じ入力を両方のOpenGL構成で再生しました。文字または表示属性が変わったのは延べ6,628セルです。Pangoで字形を整形した延べ81,774セルのうち、75,146セル（91.9%）は内容も属性も前の画面と同じでした。両構成で件数は一致しました。boxrigは字形に関わる変更を行単位で判定し、該当行を整形し直します。[行キャッシュの更新判定](../../../src/opengl/renderer.c#L550)・[実際に整形した列を数える計測器](../../../tests/performance/opengl_update_probe.c)

## 同じ入力が画面に反映されるまで

GTK3 OpenGLで記録したgrid、btop、xrayから、それぞれ24更新を選びました。各更新に観測用の目印を入れ、同じバイト列を3構成に再送しました。更新の間隔は100ミリ秒です。PTYに書き始めてから、X11ウィンドウで期待した目印を読み取るまでを計測しました。連続した2回の読み取りで画面全体の画素が一致すれば、その2回目を観測時刻としました。時間には画素の読み取りも含みます。実ディスプレイの発光時刻は未計測です。[入力の切り出し](../../../tests/performance/extract_capture_updates.mjs)・[X11ウィンドウの画素計測](../../../tests/performance/frame_latency.c)

各試行で24更新すべてを確認し、最初の1更新を除く23件から95パーセンタイル（p95）を求めました。表は各構成3試行のp95の中央値と範囲です。例えばGTK3 Cairoのgridでは、遅い側の更新が画面に現れるまで約46ミリ秒かかりました。

| boxrigの描画構成 | gridの画素反映p95（ms） | btopの画素反映p95（ms） | xrayの画素反映p95（ms） |
| --- | ---: | ---: | ---: |
| X11 OpenGL ES | 21.47（20.89〜33.62） | 38.94（23.66〜39.24） | 42.98（38.20〜43.69） |
| GTK3 OpenGL | 24.48（16.40〜42.48） | 26.98（15.48〜30.13） | 44.92（37.78〜49.22） |
| GTK3 Cairo | 45.55（37.82〜49.62） | 31.10（20.68〜33.01） | 46.61（40.93〜49.62） |

最初に1回の読み取りで計測したところ、X11のbtopで目印と背景が別の更新を指す画像が1枚ありました。端末領域の520,380画素を直前と直後の画像と比較すると、上から順に境界が1か所あり、どちらにも属さない画素は0個でした。上表の27試行はすべて2回読み取りで取り直し、録画のフレーム時刻と24更新の順序も照合しました。[画素と録画時刻の検証](../../../tests/performance/check_frame_latency.mjs)

この27試行と下の画像処理計測3試行で、2回の読み取りに差があった126組252枚も調べました。端末領域で更新前後の画素が混在したのは40枚で、境界は各1か所でした。前後のどちらの画像にも属さない画素はありませんでした。

### xrayの画像復号と描画

xrayの最後の23画像と消去を再生し、3構成とも途中の画像と最終的な消去を確認しました。別に処理時間を記録した試行で、最初の1枚と消去を除く22枚を比較しました。表は1画像あたりに処理スレッドが使ったCPU時間です。入力処理には、画像を表すBase64データの復号を含みます。Cairoの描画には画像の変換と合成を、OpenGLの描画にはテクスチャの転送指示を含みます。[処理区間の計測](../../../tests/performance/image_phase_probe.c)・[画像と配置の照合](../../../tests/performance/check_xray_replay.mjs)

| boxrigの描画構成 | 入力処理（ms） | うち画像の復号（ms） | 描画（ms） | 描画の内訳（ms） |
| --- | ---: | ---: | ---: | --- |
| X11 OpenGL ES | 5.89 | 2.30 | 2.17 | テクスチャ転送指示 0.11 |
| GTK3 OpenGL | 6.38 | 2.52 | 2.49 | テクスチャ転送指示 0.14 |
| GTK3 Cairo | 7.92 | 3.12 | 2.60 | 画像の変換 0.67、合成 0.22 |

この画像列では3構成とも、端末の入力処理が描画よりも長くCPUを使いました。GTK3 Cairoでは画像の復号だけで、合成の約14倍かかりました。

## 実行環境と計測記録

計測環境はUbuntu 24.04.5、Core i9-12900KS（24論理CPU）、GeForce RTX 3090、NVIDIAドライバー615.71.09です。boxrigはGCC 13.3.0と標準の`-O2 -g`でビルドしました。GTK3は3.24.41、Pangoは1.52.1、Cairoは1.18.0です。ネイティブX11サンプルはOpenGL ES 3.2を、GTK3サンプルはデスクトップOpenGLまたはCairoを使っています。

端末は118列45行、フォントはDejaVu Sans Mono、1セルは7×14画素です。端末領域826×630画素と`TERM=xterm-256color`を実行時に確認しました。自動URL認識はnotcursesで無効、btopで有効です。実アプリの出力は`script`で記録しました。計測用のウィンドウは1つずつ開き、3回の繰り返しで描画構成の順番を変えています。実アプリ36試行の送信時間とCPU使用率は、CPUプロファイラーと録画を外して測りました。

ホスト全体の負荷は`/proc/stat`から求めました。notcursesでは起動前から記録の再生終了まで、btopでは起動後の観測12秒間を対象にしています。

集計と各試行の元データは、この作業環境の`artifacts/perf-live-20261120-jpbBTX/`に保存しました。`summary.json`に試行別の数値と中央値、`environment.txt`に環境とバイナリのSHA-256があります。固定入力とそのハッシュは`inputs/`、CPUプロファイルと処理別の計測は`detail/`、画素の照合結果は`readback-verification.json`にあります。

容量の大きいPTY記録は`output.bin.zst`に圧縮し、展開したデータのSHA-256を元の記録と照合しました。57記録の一覧は`recordings.tsv`にあります。画素の反映を計測した各試行の録画は`video.mkv`、元の画素画像は同じ場所の`frames.tar.zst`です。画像はアーカイブを元ファイルと照合してから圧縮版を残しました。

X11のbtopでは、セル寸法を取得できずにアプリの起動前に終了した試行が1回あります。同じ条件で再実行し、完走した3回を集計しました。gridの直接起動で追加の統計出力を試した際には、デモがJSONに不正なフレーム数を出した例とシグナル11で終了した例が各1回あります。直接起動の9試行は、追加出力を外して最初から測り直したものです。予備計測のログは`direct-json-trial/`に保存しました。

同じX11環境で、リポジトリ直下からGTK3 OpenGLのgridとbtopを計測する例です。btopのドライバーは、各試行で専用の設定ディレクトリを作ります。[notcursesの計測スクリプト](../../../tests/performance/run_notcurses_evaluation.sh)

```sh
make -j8 notcurses-evaluation-tools build/boxrig_term/x11/boxrig_term
mkdir -p artifacts
out=$(mktemp -d artifacts/perf-recheck-XXXXXX)
bash tests/performance/run_notcurses_evaluation.sh \
  build/boxrig_term/gtk3/boxrig_term opengl 856 690 0 g 0.03 "$out/grid" 0 0 45 118
node artifacts/perf-live-20261120-jpbBTX/run-btop.mjs "$out" gtk-gl 100 1
```
