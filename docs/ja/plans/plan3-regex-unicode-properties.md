はい。現在のboxrigの構成で対応可能です。既に組み込まれているutf8procにUnicode文字種を返す`utf8proc_category()`があり、追加の外部依存なしで`\p{L}`を実装できます。[utf8proc公式API](https://juliastrings.github.io/utf8proc/doc/utf8proc_8h.html)

現在の未対応箇所は、正規表現の[エスケープ解析](/home/kouji/Projects/boxrig/src/core/regex.c:290)と[文字クラスの照合](/home/kouji/Projects/boxrig/src/core/regex.c:1786)です。文字クラスにUnicodeカテゴリの判定を加えれば、既存の照合エンジンを拡張する形で対応できます。公開APIの関数追加は不要と考えます。

対応範囲としては、次が妥当です。

- `\p{L}`と、その否定である`\P{L}`を、単独でも`[]`内でも使用可能にする。
- Unicodeの一般カテゴリを対象にする。`L`（文字）に加え、`M`（結合符号）、`N`（数）などと、`Lu`（大文字）、`Nd`（十進数字）などの細分類を扱う。
- 既存の`\d`・`\s`・`\w`は、現在のASCIIとしての意味を維持する。

`L`は`Lu・Ll・Lt・Lm・Lo`の集合なので、カテゴリの集合をビットマスクで保持すれば、大量の文字範囲を列挙する必要もありません。現在の処理量を制限できる設計にも組み込めます。[Unicodeの一般カテゴリ定義](https://www.unicode.org/reports/tr44/#General_Category_Values)

この対応により、elder-termsでは元の文字種の条件を維持したまま、次の式を使えるようになります。

```regex
(?<scheme>https?)://(?<host>[\p{L}0-9.-]+)
```

ただし、結合文字には注意が必要です。boxrigは一致全体の始点・終点を「見た目の1文字」に相当する書記素の境界に制限しています。そのため、`e`と結合アクセントからなる文字列では、`\p{L}+`だけで`e`部分を一致結果として返すことはできません。結合符号も取り込む用途では`\p{M}`を含める必要があります。[現在の一致規則](/home/kouji/Projects/boxrig/docs/ja/regex.md:50)

実装の完了条件は、元の式で日本語ホスト名・名前付きキャプチャ・バイト位置を取得でき、否定・結合文字・不正なカテゴリ指定・処理量上限の試験と既存の全体試験を通過することです。なお、文字体系を指定する`\p{Greek}`などは、一般カテゴリとは別の属性なので、追加の対応範囲として扱うのが適切です。
