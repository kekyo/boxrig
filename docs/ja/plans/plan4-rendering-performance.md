# 描画遅延と本文認識の負荷を減らす計画

elder-termsで残っている描画遅延について、boxrig側で改善できる範囲を整理します。優先するのはGTK3でのOpenGL画像の合成待ちと、CPU側の描画準備です。本文認識はCPU負荷の削減対象として扱います。実装例の認識が途中で止まる問題を先に直し、同じ仕事を完了した状態で性能を比較します。

調査日は2026年10月17日です。対象はboxrigの`develop`、`6402257d9e848b13a3ae1f67779b59560b8ed629`です。測定値はelder-termsの`66ebf3ffe4e173401f9b8c4f02b315f534ef3e2c`に保存した[plan3](../../../../elder-terms/docs/ja/plans/plan3-rendering-performance.md)から引き継ぎました。このリンクは、両リポジトリを同じ親ディレクトリに置いた構成を前提とします。測定時のboxrig固定参照は`1d379548fd0de1ff7b15725cad90f4e1136d732b`です。

調査対象と測定時の固定参照について、`src`、`include`、`examples`、`tests`に差分がないことを確認しました。

本書は追加調査と実装計画です。以下の最適化は未実装で、今回の保存によって性能が改善したという意味ではありません。

## 1. 前提と改善の範囲

elder-termsでは、ステータスバー用の描画ウィンドウを共有する修正と、同じ活動表示画像を重ねて設定しない修正が完了しています。150 msの正当な点滅は維持しました。本計画では、この状態をアプリ側の比較基準にします。

スクリーンリーダー向けの本文公開は、boxrigとelder-termsの両方で既定OFFです。以下の主要な測定もOFFで行いました。本文公開をさらに省略することを、残る遅延への対策にはしません。ON時の読み上げと切り替えは、回帰試験で確認する機能に含めます。

変更候補は、GTK3の表示接続、共通のOpenGL／Pango-Cairo描画、coreの本文認識、GTK3／GTK4の付属ターミナルです。GTKやGPUドライバーの改変、正規表現の意味の簡略化、点滅やIMEの停止は含めません。各段階を独立してビルド・実行・比較できるように進めます。

今回の計画保存では製品コードを変更しません。将来の実装では作業ブランチを使い、意味のある単位で`fix:`、`refactor:`、`feat:`、`chore:`、`doc:`のコミットを作ります。マージ、リリース、elder-termsの固定参照更新は、その時点の指示に従います。

以下では、現在のAPIやソース名に合わせて次の用語を使います。

| 用語 | 本書での意味 |
| --- | --- |
| 経過時間／CPU時間 | 待ちを含む区間の長さ／そのスレッドがCPU上で処理した時間 |
| frame／draw | アプリがboxrigへ画像更新を要求する処理／GTKがwidgetを描く処理。実行時点が異なる |
| GL surface | boxrigが完成画像を保持するOpenGLの画像資源と、その描画処理 |
| dirty | 前回の受理済み画像から更新が必要な領域。成功した表示処理に応じて受理する |
| snapshot／投影 | ある時点の本文を所有する写し／端末セルからUTF-8本文と位置情報を作る処理 |
| identity／revision | 行などを区別する識別子／同じ対象の内容や状態の更新番号 |
| work／budget | 認識APIが数える処理量／1回の呼び出しに与える上限。時間そのものではない |
| GSource／dispatch | GLibへ登録する実行条件と処理／その条件に応じた処理の呼び出し |
| NFA | 正規表現を照合するための状態機械。途中の進行をcursorに保持する |

RGBは色の3成分、RGBAは不透明度を示すalphaを加えた形式です。RGB8／RGBA8は各成分8 bitの保存形式を表します。sRGBは色の保存時の符号化方式で、線形の色値とは区別します。FBOはOpenGLの描画先を表すオブジェクトです。

## 2. 測定から分かっていること

### 2.1. 描画待ちとCPU処理は両方残っている

主な測定条件はGTK 3.24.41、X11、RTX 3090、NVIDIAドライバー615.71.09、Core i9-12900KSです。端末は190列×66行、セルは10×22 px、フォントは16 DIPの`Noto Sans Mono;Monospace`です。子プロセスをCPU 2へ割り当て、governorは`powersave`、EPPは`power`でした。

周波数は測定中に変動しました。以下の5.2 GHzと0.8 GHzは観測した中央値であり、固定周波数に設定した試験ではありません。異なる周波数の値から、変更の効果を直接計算しないようにします。

| 指標 | 周波数中央値5.2 GHzの系列 | 周波数中央値0.8 GHzの系列 |
| --- | ---: | ---: |
| 修正前elder-termsの出力→GTK合成完了 | 96.25 ms | 118.15 ms |
| 修正後elder-termsの出力→GTK合成完了 | 48.66 ms | 78.30 ms |
| 修正後のGL surface描画の経過時間 | 4.42 ms | 27.34 ms |
| 修正後のGL surface描画のCPU時間 | この表では未集計 | 27.32 ms |
| 修正後の文字整形の経過時間 | 1.58 ms | 9.86 ms |
| 修正後のGDKへのGL画像取り込み | 27.85 ms | 20.92 ms |

5.2 GHzの系列は各条件4試行・計160更新、0.8 GHzの系列は各条件3試行・計120更新の中央値です。各区間は包含関係を持ちます。区間ごとの中央値を足して全体時間とみなすことはできません。

前者のGL画像取り込みでは、対応する160更新のスレッドCPU時間の中央値は約0.59 msでした。約27.85 msの経過時間との差から、CPU計算以外の待ちが大きいと分かります。ただし、この差だけではGPU処理、Xサーバーとの同期、ドライバー内部の待ちを分離できません。

低周波数の系列ではGL surfaceの経過時間とCPU時間がほぼ一致しました。この条件では文字整形を含むCPU処理も大きな負荷です。約27.3 msのうち、文字整形以外の内訳はまだ十分に測れていません。

ここでいうGTK合成完了は`gdk_window_end_draw_frame()`の終了です。物理モニターへの表示完了ではありません。録画からの表示検出には、60 fpsの取得間隔や転送の遅延も加わります。

### 2.2. Cairoへの固定切り替えには根拠が足りない

初期の探索ではCairoの方が短い遅延でしたが、後の比較では逆転しました。0.8 GHzの系列で、修正版OpenGLの出力→GTK合成完了は78.30 ms、Cairoは91.41 msでした。

Cairoのwidget draw自体は約9.23 msでした。しかし、その前の公開`frame()`内で画像を準備するCPU時間が約69.29 msありました。OpenGLは`frame()`からGTKの描画を予約し、その後で描画します。両方式を比べる際は、この実行位置の違いを含めます。

### 2.3. 認識の負荷はあるが、表示遅延の主因とは確認できていない

elder-termsでリンク認識を無効にした診断比較では、出力→GTK合成完了は48.73 msから48.39 msでした。各3試行のばらつきを含めると、一定した遅延削減はありませんでした。一方、プロセスCPU時間の中央値は870.36 msから781.87 msへ減っています。

公開APIの独立ドライバーでも、初期画面を含む41更新を調べました。更新ごとに認識を完了させ、次の更新へ進めています。elder-termsの式、Unicode空白の追加条件だけを除いた式、boxrig_termの式を各6回比較しました。

| 指標 | 結果 |
| --- | --- |
| 認識CPU時間の中央値 | 各式63.75〜64.21 ms |
| 再開呼び出し | 各式1,967回 |
| バイト位置から本文位置への照会 | 各式519,552回、平均12,672回／更新 |
| URL一致 | 0件 |

この入力では式の簡略化による利益は確認できませんでした。位置照会、本文の準備、変更していない行の再走査を調べる方が具体的です。URLが多い入力では別途測定します。

### 2.4. 実装例との比較には未完了の仕事が含まれていた

同じ1,794,017バイトを与えた逐次比較で、elder-termsは認識を2,632回、10,640,571 work進めました。GTK3版boxrig_termは141回、574,233 workでした。最後の表示後に約3.1秒待っても、sampleは`more_work=true`のまま再開しませんでした。

現在のGTK3実装例では、認識の続行要求を`frame_requested`へ入れます。その直後のframe処理が同じフラグを消すため、続行要求を失う場合があります。GTK4にも同じ構造があることを今回確認しました。実際の停止を測定したのはGTK3であり、GTK4は再現試験から始めます。[GTK3のevent_source.c](../../../examples/boxrig_term/gtk3/event_source.c)、[GTK4のevent_source.c](../../../examples/boxrig_term/gtk4/event_source.c)

sampleの認識時間が短いことを、同じ仕事をした結果の性能差とは扱えません。続行の修正によりsampleのCPU時間が増える可能性があります。これは正しさの修正による仕事量の増加として記録します。

## 3. 現在のコードを踏まえた設計

### 3.1. 認識の未完了状態を描画要求から分離する

付属ターミナルが持つ状態を、少なくとも「認識・イベント処理が未完了」と「表示内容が変わりframeが必要」に分けます。`boxrig_term_text_policy_resume()`の続行結果は、coreの認識とイベントキューの残りを両方含んでいます。認識だけ完了しても、64件単位で取り出すイベントが残る場合を落とさないようにします。[text_policy.c](../../../examples/boxrig_term/common/text_policy.c)

第一候補は既存GSourceに独立した未完了フラグを持たせる案です。認識だけが残る場合はidle優先度で再開し、表示要求は作りません。URL装飾やhoverの実際の変更がある場合は、既存のview通知からframeを要求します。認識を続けるためだけに、セッション同期やフォント設定などの処理を毎回やり直す必要があるかも区別します。

| 状態 | 次の処理 | 描画要求 |
| --- | --- | --- |
| PTY出力や認識の再走査要求を受信 | budget付きで認識を開始・再開 | 本文・装飾が変わった場合に要求 |
| 認識またはイベントが未完了 | idle優先度で次のdispatchを用意 | 未完了という理由だけでは要求しない |
| 認識とイベント処理が完了 | 認識によるready状態を解除 | 既存の表示要求だけを処理 |
| widgetが未map・サイズ未確定 | 認識は進め、表示は可能になるまで待つ | frameの失敗による再起動を繰り返さない |
| 終了・失敗 | sourceと所有データを既存の終了手順で解放 | 解放後のcallbackを残さない |

GLibは高い優先度のsourceを先に処理します。idleでの続行だけでは、常に高優先度の仕事がある状況での完了を保証できません。まず有限の出力が止まった後の完了を保証し、連続出力では入力・描画との公平性と最新状態への追従を別に測ります。同期出力中の既存の優先度制御も維持します。[GLibのmain loop](https://docs.gtk.org/glib/main-loop.html)

### 3.2. 不透明な表示先と内部のRGBA画像を分ける

現在の[gl_area.c](../../../src/gtk/gl_area.c)は、GTK3で常に`gtk_gl_area_set_has_alpha(TRUE)`を設定します。GTK3 widgetはGLAreaを描く前にCairoのclipをCLEARし、透明度の意味を保っています。GTKの公開APIでは、alphaなしのGLAreaは下の内容を置き換えて表示します。[GTKのAPI説明](https://docs.gtk.org/gtk3/method.GLArea.set_has_alpha.html)、[GTK 3.24.41のAPIコメントと実装](https://gitlab.gnome.org/GNOME/gtk/-/blob/3.24.41/gtk/gtkglarea.c#L1184)

GTK 3.24.41には、alphaなしのrenderbufferなどの条件を満たす場合に直接転送する処理があります。ただし、変換、clip、windowの描画状態にも条件があります。不透明化だけで必ずこの処理へ入るとは限りません。X11での画像取り込みにはGLXとの同期処理もあるため、実際に通った処理と待ち時間を測定します。[gdkgl.c](https://gitlab.gnome.org/GNOME/gtk/-/blob/3.24.41/gdk/gdkgl.c#L421)、[X11の画像取り込み](https://gitlab.gnome.org/GNOME/gtk/-/blob/3.24.41/gdk/x11/gdkglcontext-x11.c#L426)

現行コードはGTKの出力先をRGBA各8 bitに限定しています。GL runtimeにも同じ制約があります。`BOXRIG_GL_ALPHA_OPAQUE`は既にありますが、これはalphaの意味を表す値です。RGB8という保存形式への対応とは別です。[runtime.h](../../../include/boxrig/render/runtime.h)、[runtime.c](../../../src/opengl/runtime.c)

以前の診断では、GTKのalpha設定だけをFALSEへ差し替えるとCairoへフォールバックしました。40状態は表示できましたが、boxrigのGL surface描画は0回でした。この結果は不透明OpenGLの高速化を示しません。

今回の調査では、[gl_surface.c](../../../src/gtk/gl_surface.c)がGTKとは別にRGBAの保持画像を作り、その完成画像をGTKへ転送していることを改めて確認しました。現在は両者に同じ`boxrig_gl_target`形式を使い、形式とalphaの意味の一致を要求しています。この結合を解く方法は二つあります。

| 案 | 変更内容 | 評価 |
| --- | --- | --- |
| A. GTKへの表示先だけRGB対応 | 非公開の表示先記述を分ける。内部の保持画像とGL runtimeはRGBAを使い続ける | 第一候補。GTKの合成負荷を検証するための変更範囲を限定できる |
| B. 公開GL targetにRGB8／sRGB8を追加 | runtimeの形式検証、色変換、renderer、利用側の検証を広げる | RGB出力先へ直接描く汎用APIも必要になった場合の派生案 |

採用する設計はAです。GTK表示先はFBO、寸法、色のencoding、実際のalpha bit数、sample数、世代で記述します。rendererへ渡す設定の元になるのは、実際に確保したRGBA保持画像です。表示先のRGB8をRGBA8と偽ってruntimeへ渡す実装にはしません。

内部RGBAを残す理由は、現在のrendererが背景画像などの合成に宛先alphaを使うためです。`BOXRIG_GL_BLEND_BEHIND`は`GL_ONE_MINUS_DST_ALPHA`を使用します。内部までRGBへ変えると、この合成の前提も変わります。最終画像が不透明な場合だけRGB表示先へ転送する案なら、内部の合成を維持できます。[renderer.c](../../../src/opengl/renderer.c)、[runtimeのblend設定](../../../src/opengl/runtime.c#L1554)

RGBA→RGB転送は、同じ寸法、単一sample、対応する色のencodingから検証します。OpenGLとGLESそれぞれで実行し、sRGBの二重変換やalphaを捨てたことによる色の暗化を画素で確認します。利用するのは既存の`glBlitFramebuffer()`で、仕様と実機の両方を確認します。[KhronosのOpenGLリファレンス](https://github.com/KhronosGroup/OpenGL-Refpages/blob/main/gl4/glBlitFramebuffer.xml)、[GLES 3.0リファレンス](https://github.com/KhronosGroup/OpenGL-Refpages/blob/main/es3.0/glBlitFramebuffer.xml)

GTKの出力先は前回の内容を保持しているとは限りません。既存の[保持画像の試験](../../../tests/gtk/test_gl_surface.c)も、表示先を別の色で塗ってから全画像を復元できるか確認しています。内部描画は変更領域を使い、GTKへの転送は完成画像全体を維持する設計です。GTK内部の実装は原因調査の参照にとどめ、製品から呼ぶのは公開APIに限ります。

### 3.3. 不透明と判断する範囲と切り替え

判定の対象は端末セルだけでなく、GLAreaが占める画像全体です。余白、端数ピクセル、スクロールバー、背景画像、選択、IME未確定文字と候補を含めます。背景色のalphaが255という条件だけで判定しません。

第一段階では、解決済みの透明度設定がOPAQUEで、rendererが領域全体を不透明に埋め、その後の描画もalphaを下げないことを確認できる構成だけを候補にします。未知の背景効果や、合成中に透明画素を残し得る構成はRGBAを使います。既存の`boxrig_ui_transparency_state`と各描画処理から判定し、性能目的だけの公開設定は最初から増やしません。[透明度の公開契約](../../../include/boxrig/ui/view.h)、[背景描画](../../../src/opengl/renderer.c#L3069)

判定のために毎frameの画素読戻しを行う案は採用しません。試験では実際のalphaを確認しますが、製品では設定と描画規則から判定します。OPAQUEという設定だけでは余白などを保証できない箇所が見つかった場合は、判定を狭めるか、この段階の計画を見直します。

切り替えの時点はframeの境界です。透明度設定などが変わったら次の境界で新しい表示先を用意し、対象の世代を更新します。GTK 3.24.41の`set_has_alpha()`は既存bufferを削除するため、以前のFBO名を使い続けてはいけません。完全な新画像の転送が成功してから、表示済み状態とdirtyの受理を更新します。失敗したframeは受理しません。[GTKのbuffer再生成](https://gitlab.gnome.org/GNOME/gtk/-/blob/3.24.41/gtk/gtkglarea.c#L1205)

RGB表示時は、その表示方式に不要なCairo CLEARを省けるか確認します。RGBA表示とCairoの透明度は従来の意味を保ちます。RGBが使用できない場合は、まず既存のRGBA OpenGLで描けるか判断し、Cairoへのフォールバックとは診断を分けます。画面の色だけでbackendを推定せず、既存のrender stateとGL描画数で確認します。

GTK4にはこのGTK3用のalpha設定を流用しません。ただし、共通の`src/gtk/`を変更するため、GTK4のRGBA描画と表示先の再生成も試験対象です。

### 3.4. CPU描画は既存キャッシュの再計算を調べる

OpenGL rendererは変更行、行整形結果、グリフ、画像を既に保持しています。グリフ検索もhash bucketを使います。単にキャッシュを追加する案や、線形検索を前提とした置換には根拠がありません。[renderer.c](../../../src/opengl/renderer.c)、[公開描画統計](../../../include/boxrig/render/opengl.h)

グリフは描画する字形、atlasは複数の字形をまとめて保存する画像です。signatureは、整形や表示の入力が同じかを比較するhash値を指します。Pangoは文字の字形と配置を決める処理を担い、BiDiは左右の書字方向が混在する文字配置です。

現在の`update_row_shape()`は、対象行の各セルから整形用と表示用のsignatureを作ります。signatureが同じなら整形を再利用しますが、確認のためのセル走査は必要です。`ensure_frame_shapes()`は、全体の表示状態が変わっていてMODEL dirtyがない場合、全行のsignatureを確認します。この確認にどの操作が入るかを記録します。

| 測定する区間 | 既存の手掛かり | 効果があれば行う変更候補 |
| --- | --- | --- |
| dirtyの収集・行signature | `row_signature_cell_count`、`row_color_hash_byte_count` | 未変更の行と整形に影響しない更新の検証を省く。文字・書体・幅・色・リンク境界の依存を分ける |
| Pango整形・行データ作成 | `row_shape_count`、text provider内の処理 | 変更行の作業領域再利用、不要なitem分割や再整形の削減 |
| グリフ・atlas・描画命令 | cache hit、比較回数、upload bytes、batch数 | 実測で多い再生成・upload・batch分割を対象にする |
| Cairoの描画・完成画像準備 | renderer描画と`create_presentation_surface()`を別計測 | 同寸法の完成画像用領域を再利用し、必要な領域だけ更新する案を検証 |

色だけの変更でも、現在のPango itemの区切り方に影響する場合があります。signatureから項目を外す前に、その項目がlayout、描画分割、hit testへ影響しないことを確かめます。整形をセル単位に分割して、結合文字、合字、BiDiを壊す最適化は行いません。

Cairoでは`create_presentation_surface()`が新しいARGB32画像を作り、現在の完成画像を全面コピーしています。これは削減候補ですが、約69.3 msのすべてがこのコピーだとは分かっていません。Pango-Cairoの描画、確保、コピーを分けて測ります。[GTK3の完成画像作成](../../../src/gtk3/terminal_widget.c#L1216)、[Pango-Cairo renderer](../../../src/pangocairo/renderer.c)

再利用する場合も、公開済みの完成画像を未完了の描画で上書きしません。変更領域を描く作業画像と表示中の画像を分け、失敗時の旧画像維持、resizeのpreview、dirty受理の順序を守ります。bufferを交互に使う場合は、各bufferがどの世代まで更新済みかを持ち、前回更新していない領域の欠落を防ぎます。

### 3.5. 認識の境界照会を順次走査する

`prepare_line_step()`はUTF-8をUnicodeスカラー値へ展開し、各境界で`boxrig_text_snapshot_position_at_byte_offset()`を呼びます。現在の位置照会は、snapshot全体の位置表を毎回二分探索します。[recognizer.c](../../../src/core/recognizer.c#L618)、[text.c](../../../src/core/text.c#L1716)

認識の行準備では、照会するバイト位置が単調増加します。snapshotを所有する側に非公開の走査cursorを置き、位置表を前から一度ずつ進める案が第一候補です。任意の位置を照会する公開APIは維持し、キャプチャなどの非単調な照会はそちらで扱います。行ごとの全位置表を別途複製する必要はありません。

位置表にないバイト位置を成功として返してはいけません。UTF-8の途中、結合文字の途中、全角セルの継続位置は、現在の公開APIと同じ結果にします。同じoffsetを持つ項目がある場合の選択、空行、末尾、改行の扱いも、現在の二分探索を参照実装として照合します。cursorはsnapshotと同じ寿命を持ち、snapshotを作り直したら破棄します。

位置表を進める仕事もbudgetへ計上します。一つの要求offsetまで内部で大量に進む場合は、途中で中断・再開できるようにします。呼び出し回数が減っても、内部で同じ二分探索を繰り返していないかを比較回数で確認します。

### 3.6. 未変更行を認識し直さない

認識器は既に結果と`match_id`を保持し、NFA cursorと作業配列も再利用しています。しかし本文またはlayoutの全体revisionが変わると、`prepare_scan()`はsnapshotを作り直します。行のidentityを確定するのはUTF-8展開と境界照会の後で、同じ行でも照合まで進みます。結果の比較による通知抑制だけでは、この仕事は減りません。[recognizer.c](../../../src/core/recognizer.c)

再利用の単位は、折り返しをつないだ論理行です。screenの種別、行ID、行revision、認識器の登録世代をキーにします。文字やlayoutの変化により行が分割・結合された場合は、行IDと投影範囲を検証します。全体revisionが変わったという理由だけで、無関係な行の照合結果を捨てない設計を目指します。[text.cの行identity管理](../../../src/core/text.c#L565)

一致した行だけの再利用では、今回のURLが0件の入力を改善できません。「このrevisionの論理行には一致がない」という結果も必要です。一方、現在の`dirty_line_capacity`は現在結果の管理行数の上限です。不一致の全履歴をそこへ保存すると、容量1で長い不一致履歴を扱う既存試験の意味を変えてしまいます。

第一候補は、結果とは別に上限付きの行メタデータキャッシュを持つ案です。容量と既定値は、段階1の保持量測定で決めます。キャッシュからの追い出しは性能だけに影響し、認識結果を`INCOMPLETE`に変えません。登録認識器数との積を含めた最大保持量を示し、capacityを小さくした場合も正しく再走査できるようにします。

最初の実装ではsnapshot全体の作成を維持し、そこに行の範囲とidentityを持たせます。行のUTF-8展開より前に再利用を判定します。これにより、照合の省略とsnapshot構築の変更を別々に検証できます。後者は次節の独立した段階です。

既存の結果を使い直す場合も、現在の本文revision、結果集合revision、キャプチャ、一致バイト列、公開時点の所有権を整えます。`match_id`の維持、行の削除通知、`STALE`、`RESCAN_REQUIRED`、容量超過の契約を保ちます。途中まで走査した結果を、完了した結果としてキャッシュしません。

### 3.7. snapshot作成と再開予算の範囲を見直す

現在の認識APIは、行の準備とNFAの処理量をworkとして返します。`prepare_line_step()`の処理は既にbudgetへ計上されています。一方、`resume_text_recognizers()`が先に呼ぶ本文同期と`prepare_scan()`内のsnapshot作成は、この明示的なworkとは別に動きます。snapshot作成は投影量の測定と実データの作成を行います。[認識APIのコメント](../../../include/boxrig/terminal.h#L1914)、[snapshot作成](../../../src/core/text.c#L1453)

したがって、既存の`recognizer_unbudgeted_prepare_steps=0`だけで、公開API全体が短時間で戻るとは判断できません。現行の指標は維持し、snapshotのセル訪問、投影バイト、本文同期、結果の確定を別に測ります。[文字処理の既存計測](../text-workload-measurements.md)、[計測ドライバー](../../../tests/measure_text_workloads.c)

行の再利用後もsnapshot構築が支配的なら、変更した論理行だけを投影する段階へ進みます。既存の行範囲snapshot APIは利用候補ですが、呼ぶだけでは同期的な作成費用は分割されません。長い1論理行も、位置情報とUTF-8投影の準備からbudget付きで進める必要があります。

複数回のdispatchでsnapshotを構築すると、その間に本文が変わります。所有済みの断片を保持し、対象行のIDとrevisionを再確認してから公開します。借りたセルポインターをdispatch間に持ち越しません。別行の更新で全作業を捨てず、変更された行だけを無効にする設計を検証します。結果集合の確定時には、現在の全体revisionとの整合も確認します。

初期走査、行の削除、再走査、結果の確定が予算外の長い処理にならないかも計測します。すべてを一度に置換せず、投影の再利用、投影の分割、確定処理の順に必要性を判断します。外部のsnapshot APIは変更しない案を優先し、新しい公開契約が必要なら、その契約とテストを計画へ追記してから実装します。

## 4. 実装の順序と各段階の完了条件

修正前に問題を再現するRED、修正後に同じ試験が成功するGREENを確認します。性能の回帰試験で確認するのは、結果、訪問量、保持量、残っている仕事です。経過時間とCPU時間は別のベンチマークで比較します。診断用の追加計数は通常ビルドへ不要な負荷を加えない形にします。

### 段階1. 比較ドライバーと計測の不足を補う

既存の`measure_text_workloads.c`と描画統計を使い、btop相当の更新を再生できるドライバーを用意します。最初の成果物は、coreのみ、GTK3 OpenGL、GTK3 Cairoを起動し、最後の状態と認識結果を確認できる構成です。補助処理には既存のC99／MakeとNode.jsを使います。

まず現在の計数で何が見えているかを確認し、snapshot準備、行signature、Pango整形、Cairoの確保・コピー、GTK画像取り込みを分けます。sampleの認識停止を再現する試験もここで追加します。計測器自体は小さい入力で既知の結果と仕事量を照合します。

完了条件は、実行した版、入力、実backend、最終状態、認識の完了状態を一緒に記録できることです。詳細計測あり・なしの対照を取り、計測の追加で傾向が変わっていないことも確認します。成果物は実行可能なドライバー、基準値、認識停止のREDです。

### 段階2. GTK3／GTK4実装例の認識を最後まで進める

第3.1節の状態を実装します。GTK3／GTK4の`event_source.c`、`application_internal.h`、`event_source_policy.c/.h`と、必要な`text_policy.c`の接続を対象にします。

回帰試験は、1回のbudgetでは届かない位置にURLを含む有限出力を与え、以後のPTY入力とマウス操作を止めます。末尾URLの認識と装飾まで到達し、イベントを取り出し終えたことを確認します。認識なしの静止画面、未map状態、連続出力、同期出力、終了中の未完了仕事も確認します。

`test_gtk3_sample.c`、`test_gtk4_sample.c`、`test_example_text_policy.c`と実際のmain contextを使う試験を組み合わせます。補助判定関数だけの真偽試験では完了にしません。完了後は認識によるsourceのready状態が消えることを確認し、idle callback数が一定時間増えないという判定だけに頼らないようにします。

完了条件は、追加入力なしで認識・イベント処理が完了すること、未完了の認識だけを理由にframeを増やさないこと、入力と描画の進行を妨げないことです。この版を以後のsample比較基準として再測定します。

### 段階3. GTKのRGB表示先へ完成画像を渡せるようにする

まず内部RGBA保持画像とGTK表示先の記述を分け、既存RGBA試験を通します。その後、RGB表示先への転送試験で現行の拒否をREDとして確認し、対応を追加します。主対象は`src/gtk/gl_area.c/.h`、`gl_surface.c/.h`、`tests/gtk/test_gl_surface.c`です。公開GL runtimeの受理形式はこの段階では広げません。

実行可能な小さいGTKドライバーで、RGBA保持画像からRGB表示先への転送、色、余白、表示先の入れ替わり、故障後の再試行を確かめます。GTKの実FBOを調べ、期待するalpha bit数とGL描画が観測できた試行だけをRGB試験の成功に数えます。

完了条件は、OpenGL／GLESの対応環境でRGB転送が正しいこと、既存RGBAとGTK4が維持されること、失敗時にdirtyを受理しないことです。RGBが得られない環境は理由を付けて区別します。ここでは表示遅延の改善までは主張しません。

### 段階4. GTK3で不透明経路を選び、合成待ちを比較する

第3.3節の保守的な判定とframe境界での切り替えを実装します。通常のGTK3版boxrig_termで、不透明な静止画面、btop出力、背景透明度の往復変更、resize、IMEを動かせる状態にします。

RGBとRGBAを診断時に選べる同条件の比較を用意します。画面全体のalphaを試験用に確認し、RGBへ進める構成とRGBAへ残す構成を再現します。透明化への切り替え失敗、contextの再生成、出力先の世代変更も故障注入で検証します。製品へ常設する設定は、必要性を確認してから決めます。

完了条件は、RGBAと同じ表示・入力機能を保ち、GL backendを維持したうえでGTK画像取り込みと出力→合成完了の変化を説明できることです。単独の端末と、GTK部品の正当な点滅を伴う構成で測定します。効果がなければ段階3・4の性能目的の製品差分を残すかを見直し、改善したという扱いにはしません。

### 段階5. CPU描画の実測で多い処理を減らす

段階1の区間計測を掘り下げ、第3.4節の候補からCPU時間が大きいものを一つずつ選びます。最初から行cache、Pango、Cairoのすべてを書き換えません。対象操作と再計算量が決まったら、減らすべき仕事量の上限を試験に追加してREDを確認します。

操作は同じ画面の再提示、カーソル点滅、hover・選択、色変更、1行更新、プロセスリストのスクロール、resizeに分けます。パレット、フォント、倍率の変更も確認対象です。行を移動して再利用する場合は、内容だけでなくフォント、BiDi、幅、描画属性、layoutの所有権を検証します。

完了条件は、選んだ処理の訪問数・確保量・CPU時間が減り、文字、色、選択範囲、IME、失敗時の完成画像維持が同じであることです。CPU周波数の異なる観測群は分けて比較します。内訳を確認して候補を不採用にした場合も、その理由を成果として記録します。

### 段階6. 認識のバイト境界照会を線形に進める

第3.5節のcursorを実装します。実際の公開認識結果と任意位置照会を照合し、結合文字、全角文字、空行、折り返し、キャプチャの位置を検証します。小さいbudgetを使って途中中断を繰り返し、同じ最終結果に到達させます。

現行の二分探索の比較量を計測用ビルドで数え、順次アクセスに対する線形の処理量上限をREDにします。修正後は、スカラー境界数と位置表の件数に応じた上限に収まることを確認します。既存の公開APIを呼んだ回数だけを合否にしません。

完了条件は、41更新の一致結果を変えず、位置表の探索仕事を削減できることです。使ったworkがbudgetを超えず、snapshot破棄後の参照がなく、ASan／UBSanでも問題がないことを確認します。

### 段階7. 一致・不一致の行結果を再利用する

第3.6節の上限付きcacheと早い行判定を追加します。まず全体snapshotを作る方式を維持し、UTF-8準備とNFAの削減を単独で測ります。無関係な1行だけが変わる入力で、同じ認識結果を返すのに全行を再準備する現状をREDにします。

一致0件の入力、一致が多い入力、cache容量を超える履歴を別々に検証します。既存の`recognizer-retained-matches`に加え、未変更行の探索量と上限付きcacheの保持量を計測します。cacheの照合自体が行数の二乗にならないよう、その比較量も含めます。

完了条件は、1行更新のUTF-8準備・照合量が変更行に応じて減ること、cache不足で認識の意味が変わらないことです。主画面・代替画面・BOTH、履歴の削除、折り返しの分割・結合、resize、途中更新、イベントoverflow、`match_id`の維持を確認します。

### 段階8. 必要ならsnapshot構築を変更行へ限定し、分割する

着手条件は、段階7後も全体snapshotの作成が主な負荷として残ることです。小さいbudgetでも長い履歴を一度に投影する現状を、訪問量の試験でREDにします。第3.7節の所有権とrevisionの規則を満たす形で、変更行の投影と分割構築を実装します。主対象は`src/core/text.c`、`recognizer.c`、内部状態の定義と既存の文字処理計測です。

長い1論理行、初期走査中の追記、同じ行の連続書き換え、別行の連続更新、主画面と代替画面の切り替えを検証します。最新の入力が有限回で止まれば、追加操作なしで最新状態の完全な結果に到達することを確認します。無限に変更され続ける本文の「完了」は要求しません。

完了条件は、1回の再開が訪問する処理量に説明可能な上限があり、未変更行の投影を省き、結果と容量制約を保つことです。結果確定や本文同期に予算外の処理が残れば、その量と理由を記録します。work値だけを減らして、実際の走査量が減っていない状態は成功にしません。

### 段階9. 全体試験と統合比較を行う

各段階の有効な差分だけを残し、通常ビルドと全体テストを実行します。確認先は[開発時の試験手順](../development/testing.md)と[Makefile](../../../Makefile)です。全体の基本コマンドは`make -j1 test`です。ビルドだけのtargetと実行まで行うtargetを区別します。

関連試験には、GTK GL surface、GTK3／GTK4 rendering、OpenGL／GLES、描画方式切り替え、連続出力動画、背景・色、IME、本文認識、公開SDKを含めます。共通rendererを変えた場合はnative X11／WaylandとWin32の既存試験も対象です。画像のmasterを追加・変更した場合は目視で確認し、点滅や切り替えは動画の状態遷移でも検証します。

実機でbtopのプロセスリストをスクロールし、bashの入力・大量出力も確認します。GNOME Terminalは同じ行列数・フォント寸法で測り直した場合にだけ定量比較します。旧elder-termsプロセスと混同しないよう、実行ファイル、PID、使用ライブラリーの版を記録します。

完了条件は、全体試験の実行と失敗理由の説明、機能と仕事量をそろえた比較結果、残る遅延の内訳がそろうことです。未実施の環境や失敗が残る場合は、計画全体を検証済みとはしません。elder-termsへ引き継ぐ際は、製品の固定参照更新と一時的な比較ビルドを区別します。

## 5. 比較方法と採否の決め方

### 5.1. 入力と比較条件

逐次更新では、40更新を前の状態の表示確認後に送ります。連続更新は60更新を25 ms間隔で送る条件です。最後の状態までの到達、表示された異なる状態数、順序を確認します。表示状態数とdraw回数は別の指標です。GUI比較では全出力の表示後も認識を進め、`more_work=false`とイベント消費まで確認します。

coreの独立測定では、初期画面を含む41更新を各回完了させる条件と、認識中に次の更新を与える条件を分けます。URLがないbtop出力だけでなく、URLが多い出力、末尾だけにURLがある出力、Unicode・結合文字を含む出力を使います。

保存済みのbtop入力は`/tmp/elder-render-profile/btop-host-baseline.output`です。SHA-256は`5a5a8bceee8f361658f3a91bb1aaf70db2c25f877bf72ce18102ce1e483daaf3`です。取得できる間はこの入力を使い、消失した場合は再現用の入力を作り直して新しい基準値を採ります。異なる入力の数値を連続した比較として扱いません。

| 軸 | 主要条件と対照 |
| --- | --- |
| アプリ | 同じ認識を完了するboxrig_term、修正済みelder-terms、GTK部品を併設する比較ドライバー |
| 描画 | RGBA OpenGL、RGB表示先OpenGL、Cairo。要求した方式と実backendを両方記録 |
| 周辺UI | 静止、正当な150 ms点滅。消灯・点灯を省いた条件は診断用として区別 |
| 内容 | btop再生、プロセスリスト操作、1行変更、無変更再提示、URL多数、長い行 |
| 環境 | X11の実GPUを性能の主条件とする。Wayland、Mesa／GLES、別GPUは個別の結果として扱う |
| 本文公開 | 主要性能比較はOFF。ONと切り替えは機能回帰を確認 |

条件は交互または順序を入れ替えて最低3組実行し、ばらつきが大きければ増やします。各試行の中央値・p95と全試行の分布を残し、一つの試行や集約中央値だけで判断しません。warm-upと初回のフォント・GL資源準備は区別します。

### 5.2. 計測する境界

書き込み、PTY取込み、parser完了、公開frame開始・終了、widget draw、GL surface描画、GTK画像取り込み、GTK合成完了、録画での状態検出を分けます。各区間に経過時間とスレッドCPU時間を付け、試行全体ではプロセスCPU時間も記録します。

GL命令の呼び出し時間はGPU完了時間と同じではありません。必要な場合だけ、対応するGPU queryを診断用に非同期で回収します。結果取得のための`glFinish()`や直後の待機を加えて、元の待ち方を変えないようにします。GPU側の時間が取れない環境では、未計測と明記します。

実GL API、vendor、renderer、driver、targetの形式、alpha bit数、fallback理由、context／target世代を記録します。CPU割当、周波数の分布、governor、EPP、温度や同時負荷が分かる場合はそれも残します。周波数が異なる群を一つの改善率へ混ぜません。

### 5.3. 採用する変更の条件

機能修正であるsampleの続行は、最後まで認識できることを採用条件にします。性能変更は、狙った仕事量または待ち時間が減り、同条件の反復で全体への影響を説明できることを条件にします。認識CPUだけが減った場合は、その成果を表示遅延の改善へ言い換えません。

狙った区間が縮んでも、p95、入力応答、描画数、メモリー保持が悪化した場合は採否を見直します。差がばらつきに埋もれる場合は効果未確認とします。固定の改善率を先に約束せず、採用・不採用・環境依存・追加調査のいずれかを根拠付きで記録します。

真の原因が分かった時点で、不要になった試作や製品差分は戻します。未使用のhelperや常設の診断設定を残しません。複数の変更を積み重ねて原因が分からなくなった場合は、段階ごとの基準値に戻って比較します。

## 6. 保留する案と残る限界

公開GL targetのRGB8／sRGB8対応は、第3.2節の案Bです。必要になった場合は、enum追加だけで済ませず、runtimeの形式・encoding検証、sRGB変換、alphaを使うblend、default FBO、GL state保存、native frontend、SDKを含む別の受入条件を追加します。今回のGTK表示先だけの改善と同時には進めません。

正規表現の固定接頭辞で候補開始位置を省く案は、まだ効果を測っていません。左から最初・同じ開始位置なら最長という規則、キャプチャ、Unicodeと書記素境界を保てるか確認が必要です。行の再利用と位置照会を改善した後もNFAが主な負荷なら再検討します。

スクロール時の行整形結果の移動再利用、Cairo完成画像の差分更新は、段階5の内訳から選ぶ候補です。btopが画面を再描画する場合と、端末のスクロール操作で行が移動する場合を混同しません。画面内容が似ているだけでlayoutを再利用することは避けます。

GTK内部やGPUドライバーに待ちが残る可能性があります。本計画はboxrigが与える画像形式と描画要求を改善できるかを検証するもので、全環境でGNOME Terminalと同じ応答性に達することを完了条件にはしません。物理入力からモニター表示までの遅延を主張するには、別の外部計測が必要です。
