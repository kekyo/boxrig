# plan32 組み込み向けの機能選択と文字コード変換フック

2026年11月25日作成。boxrigの調査基準は`77c1511`。この計画は設計段階にある。

## 移植先から選べるようにするもの

フラッシュ容量やRAMが限られる機器に向けて、boxrigを必要な機能だけでビルドできるようにする。現行のcoreは、画面や通信方法に依存せずに使える端末本体である。GUIや疑似端末（PTY）は個別にリンクでき、GTKでは`GTK_OPENGL=0`で描画方式も絞れる。一方、coreのビルドには`src/core/*.c`の全ファイルとutf8proc、libpng、zlibが入る。移植先を識別する既存の`#ifdef`に加え、同じ移植先でも製品が使う機能を選ぶための定義を用意する。[ライブラリの構成](../architecture.md)・[ビルド規則](../../../Makefile)

| 議論した案 | 内容 | 方針 |
| --- | --- | --- |
| 案1　機能ごとの切り替え | 通常のビルドは現行の機能を基準とし、不要な機能を`0`にする。ライブラリのコンパイル条件とリンクするオブジェクトを同じ設定から決める。 | 採用。文字コード変換は専用フックの有無を切り替える。 |
| 案2　用途別プロファイル | `FULL`と`COMPACT`で機能と容量の既定値を一括選択し、個別定義で上書きする。`COMPACT`の例では画像・監視・認識・状態保存を外し、UTF-8、色、カーソル、代替画面、キー入力を残す。履歴は少数行、制御文字列は数KiBを想定した。 | 比較案として保留。案1と案3は個別指定だけで利用できるようにする。 |
| 案3　小型機器向けの画面と端末制御 | セル（画面上の一文字分の枠）に保持する情報、画面数、解釈する制御列を用途に合わせて選ぶ。 | 採用。将来の組み込み向け描画にも使える境界を設ける。 |

通信路の文字コード、端末が解釈する制御列、セルが表せる文字と色は別々に選べるようにする。例えば、Shift_JISの計測器と通信し、日本語を16色で表示する製品では、画像、履歴、代替画面をそれぞれ省ける。

## 現行coreの容量と小型画面の試算

フラッシュには実行コードと定数表が載る。RAMには端末ごとに画面やバッファを確保する。下表の現在値は既存のLinux x86-64ビルドと既定の構成に基づく。移植先での実行ファイルの削減量やヒープ総量は、対象機器のビルドで測る。

| 対象 | 現在値と算出根拠 |
| --- | --- |
| Shift_JISの変換表 | `build/core/codec.o`のシンボルサイズは受信用22,560バイト、送信用29,304バイト。読み取り専用の表だけで計51,864バイト（約50.6 KiB）ある。 |
| 端末生成時のバッファ | 既定の制御文字列用バッファは1 MiB。文字列の出現監視には変更前後のデータ用に各1 MiBを確保する。監視を一件も登録しない場合も、この3領域で計3 MiBを使う。 |
| セル配列 | `sizeof(boxrig_cell)`は64バイト。初期化時に主画面と代替画面の2面を確保する。80列×24行なら計240 KiB、40列×15行なら計75 KiBになる。 |
| 小型セルの試算 | 320×240ピクセルの画面と8×16ピクセルの固定幅フォントなら40列×15行になる。固定の16色とASCIIに絞り、文字1バイト、前景・背景各4ビットとすれば、主画面600セルの配列は1,200バイト。行の管理情報、フォント、描画バッファは別に見積もる。 |

実行時に指定する容量には、生成時の割り当て量と、利用時の上限がある。例えば画像保存の既定値128 MiBは保存できる量の上限である。スクロール履歴の既定値は10,000行で、0行も指定できる。ビルドから機能を外すときは、初期化処理や使わなくなるバッファ、依存ライブラリも対象にする。[端末の既定値と生成](../../../src/core/terminal.c)・[監視バッファ](../../../src/core/text.c)・[セル定義](../../../src/core/terminal_internal.h)・[画面の初期化](../../../src/core/screen.c)・[画像の容量設定](../reference/graphics.md#形式寸法容量の制限)

## 文字コード変換をフックに置き換える

当初は`BOXRIG_FEATURE_SHIFT_JIS=0`で変換表を省き、必要な製品だけ有効にする案を検討した。`COMPACT`にShift_JISを個別に追加するのが一例だった。その後、対応する符号化をcoreに列挙する案、変換を接続側で行う案、アプリが用意した変換器をcoreから呼ぶ案を比較した。既存の変換器と表を別ライブラリにして、必要なアプリだけがリンクする案もあった。

採用するのは、アプリの変換器を呼ぶための公開フックAPIである。標準の文字コードはUTF-8とし、組み込みのShift_JIS変換表と専用処理は廃止する。フックのAPI自体をライブラリのビルド時に選べるようにする。変換器を提供する側が対応する文字コードを決める。セル、検索、選択、コピー、IMEの確定文字列には引き続きUTF-8を使う。

ビルド定義の仮称を`BOXRIG_FEATURE_ENCODING_HOOKS`とする。値を`0`と`1`で指定する場合、C側では`#if BOXRIG_FEATURE_ENCODING_HOOKS`で分岐する。`#ifdef`だけでは値が`0`でも定義済みになる。配布するヘッダーとライブラリが同じ設定を示すようにする。

| ライブラリの構成 | 端末の振る舞い |
| --- | --- |
| フックを組み込まない | UTF-8専用。フック用の公開API、呼び出し分岐、端末ごとのフック状態を省く。 |
| フックを組み込み、変換器を指定しない | 既定のUTF-8経路を使う。elder-termsのように、接続側ですでに変換しているアプリもこの経路を使える。 |
| フックを組み込み、変換器を指定する | 接続先の文字コードが適用される箇所で変換器を呼ぶ。変換表や`iconv`など、変換器が使う依存はアプリが選ぶ。 |

### 変換するデータと通過させるデータ

端末に届くバイト列には、表示する文字のほかに、カーソル操作やタイトル設定などを伝える制御列が混ざる。OSCは、タイトルやURIなどを端末に渡す制御列である。現行実装にも、同じ接続の本文とタイトルをShift_JISで受け取り、作業ディレクトリを通知する`OSC 7`のURIをUTF-8として扱うテストがある。接続先の符号化を使う場所を識別できる位置にフックを置く。[現在の入出力契約](../terminal-io.md#文字コードと生バイト)・[本文・タイトル・URIのテスト](../../../tests/test_terminal_codec.c)

| 経路 | フックに渡す内容 | boxrigが扱う内容 |
| --- | --- | --- |
| 受信 | 画面本文、`OSC 0`・`1`・`2`のタイトル文字列をUnicodeへ変換する。タイトル用の変換が本文の途中状態に干渉しないようにする。 | 制御列の構文、固有の符号化を持つURI、クリップボードや画像のプロトコルデータを解釈する。 |
| 送信 | `boxrig_terminal_send_text()`の文字列、通常の文字キー、貼り付け本文を接続先の符号化へ変換する。 | キーの制御列、問い合わせ応答、貼り付けの開始・終了マーカー、`boxrig_terminal_send_bytes()`で受け取った生バイトを送る。 |

受信のフックにはチャンクをまたぐ状態と、入力終了時に未完文字を確定する操作が要る。現行のShift_JIS変換では、不正な受信文字を`U+FFFD`に、送信時に表せない文字を`?`に置き換える。外部変換器についても置換やエラーの扱いを定める。送信では変換後のバイト数でキューの容量を判定する。空き待ちの`WOULD_BLOCK`から同じイベントを再試行しても、すでに処理した文字が重複しないようにする。貼り付けの改行変換と開始・終了マーカーの順序も従来の契約に含まれる。[受信終了と再試行](../terminal-io.md#容量不足と受信終了)・[貼り付けの実装](../../../src/core/input.c)

本文フックだけで扱えるのは、端末の制御バイトを文字から識別できる符号化である。例えばISO-2022-JPでは、文字集合の切り替えにも`ESC`を使う。これをboxrig側で扱うなら、通常の端末パーサーが`ESC`を消費する前にどちらの指定かを識別する必要がある。接続側で先に変換する方法もある。フックが引き受ける符号化の範囲は、公開契約を決める際に明記する。[boxrigのパーサー](../../../src/core/parser.c)・[ISO-2022-JPの復号規則](https://encoding.spec.whatwg.org/#iso-2022-jp-decoder)

### 廃止の範囲と公開APIの未決事項

廃止対象には`BOXRIG_ENCODING_SHIFT_JIS`、`shift_jis_table.h`、専用の送受信処理とタイトル処理が含まれる。生成元のWHATWGデータ、`generate-shift-jis`、ビルド・配布・ライセンス同梱の参照も整理する。Shift_JIS固定の例とテストは見直し、分割受信や再試行などの契約は外部変換器を使う例で引き続き検証する。[調査時の変換処理](https://github.com/kekyo/boxrig/blob/77c151178caf1f497fd20f32f43e25e1067a3ba0/src/core/codec.c)・[生成規則](../../../tools/codegen/rules.mk)・[ライセンスの同梱規則](../../../packaging/licenses/licenses.mk)

フックの公開名、ビルド時の既定値、コールバックの引数、変換状態の所有者と寿命は未決である。端末生成時に変換器を渡す案がある。端末状態の保存・復元に使うチェックポイントには、現在、符号化の種類と受信途中のバイトが入る。関数ポインターは元のプロセスでだけ有効なので、復元先で変換器を結び直す方法と、変換途中でも保存できる条件を決める。[チェックポイントの実装](../../../src/core/checkpoint.c)・[端末状態を引き継ぐ計画](./plan31-cross-process-terminal-handoff.md)

## elder-termsで確認した接続側の変換

elder-termsの作業ブランチ`8338dd64`と`origin/main`の`254bddc8`で実装を確認した。作業ブランチが参照するboxrigは`039603f`（0.16.0）。elder-termsは`boxrig_terminal_config_default()`のUTF-8設定で端末を生成し、接続側で`iconv`による変換を行う。`SHIFT-JIS`と`CP932`は別の設定候補で、`EUC-JP`や`GB18030`も候補に入る。実際に受け付けるのは、その環境でUTF-8との双方向の変換が可能な名前である。[端末生成](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/elder-terms-terminal/src/terminal-runtime.cpp#L1255)・[設定の検証](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/shared/src/settings/terminal-settings.cpp#L476)

通常の受信では接続先のデータをUTF-8へ変換してからboxrigに渡し、変換前後の両方をログに渡せる。逆方向では、キー入力や端末応答が入ったboxrigの出力キューを接続先の文字コードへ変換する。ペーストとテキストファイル送信は専用の送信処理で改行を整え、一度だけ変換する。X/Y/ZMODEMのバイナリ転送には生バイトの経路がある。[受信](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/elder-terms-terminal/src/terminal-connection.cpp#L220)・[通常の送信](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/elder-terms-terminal/src/terminal-connection.cpp#L375)・[テキスト送信](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/elder-terms-terminal/src/terminal-text-send-runner.cpp#L202)・[バイナリ送信](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/elder-terms-terminal/src/terminal-connection.cpp#L1053)

調査では、作業ブランチの既存テスト`terminal-text-stream-test`、`boxrig-connection-test`、`terminal-text-send-runner-test`がすべて通った。CP932の「日本語」を1バイトずつ扱う入出力と、ISO-2022-JPの文字集合の状態をチャンク間で保つ処理も確認できた。接続中に符号化を切り替える際は、以前のデコーダーの未完文字と送信待ちのデータを処理してから変換器を交換する。[接続テスト](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/elder-terms-terminal/tests/cpp/boxrig-connection-test.cpp#L226)・[変換状態のテスト](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/elder-terms-terminal/tests/cpp/terminal-text-stream-test.cpp#L54)・[接続中の切り替え](https://github.com/kekyo/elder-terms/blob/254bddc8816b38f2e74a8baa22c971492053fcf1/elder-terms-terminal/src/terminal-connection.cpp#L843)

したがって、boxrigの標準UTF-8入出力を維持すれば、elder-termsは専用表の廃止後も接続側で変換できる。ただし、CP932接続で`OSC 7`のURIだけがUTF-8で届く例では、そのURIも接続側の変換を通る。boxrigのフックには、同じ接続の中でもフィールドごとに変換を選べる利点がある。

## 案1で切り替える機能の候補

各定義名は仮称である。無効にする機能と、その構成で利用する基本機能を次の粒度で検討する。

| 定義の候補 | 無効にする範囲と依存関係 |
| --- | --- |
| `BOXRIG_FEATURE_KITTY_GRAPHICS` | 端末内の画像、デコード、画像資源・配置を外し、coreからlibpngを外せるようにする。 |
| `BOXRIG_FEATURE_TEXT_MONITOR`、`BOXRIG_FEATURE_TEXT_RECOGNIZER` | 文字列の出現監視と正規表現による認識を個別に外す。画面の文字取得と通常の文字列検索は使えるようにする。登録数を0にできない現行の認識設定も、初期化と合わせて見直す。 |
| `BOXRIG_FEATURE_HISTORY_DEFLATE`、`BOXRIG_FEATURE_CHECKPOINT` | スクロール履歴のDEFLATE圧縮と端末状態の保存・復元を個別に外す。圧縮を外しても履歴は保持できる。チェックポイントの検査値CRC-32もzlibを使うため、画像・DEFLATE・チェックポイントの3機能を外した構成でzlibを除く。 |
| `BOXRIG_FEATURE_ALT_SCREEN` | 主画面のほかに全画面アプリ用に確保する代替画面を省く。主画面のスクロール動作と履歴の行数は別に選べる。 |

画像を外した場合でも、受信したKitty画像の制御列は終端まで消費し、続く文字を表示する。画像や監視を実行時の設定で休止するだけでは、コードと定数表が最終実行ファイルに残り得る。ライブラリ側で設定を共有し、コンパイル対象、リンクする依存、端末生成時の割り当てまで切り替える。[画像処理](../../../src/core/graphics_protocol.c)・[履歴圧縮](../../../src/core/history.c)・[正規表現による認識](../../../src/core/recognizer.c)

## 案3で選ぶ端末制御と描画

CSIはカーソル移動、画面消去、色の指定などを伝える制御列である。色と文字属性の指定をSGRと呼ぶ。同じCSIでも用途により必要な操作は異なる。小型端末の機能は製品が実現する操作ごとに選ぶ。[現行の制御シーケンス一覧](../reference/terminal-sequences.md)

| 用途 | 必要になる操作の例 |
| --- | --- |
| 受信専用のシリアルログ | 文字の表示、復帰・改行（CR・LF）、後退・タブ（BS・HT）、右端での折り返し、下端でのスクロール。過去の行を保持しない機器でも画面はスクロールする。 |
| 色付きログや進捗表示 | SGRのリセットと基本16色、`CSI K`による行末消去。短い進捗メッセージで前の長い表示を上書きできる。 |
| 対話コンソール | カーソルの相対・絶対移動、行・画面の消去、カーソル表示の切り替え、通常のキー入力。 |
| 全画面アプリ | スクロール領域、行・文字の挿入削除、必要に応じた代替画面。 |
| ホスト連携 | タイトル、ハイパーリンク、クリップボード、通知、画像を用途に応じて追加する。 |

OSCに加え、機器への要求に使うDCS、Kitty画像に使うAPCなどにも文字列の終端がある。未対応の制御列は、本体を蓄積せずに終端または中止まで読み飛ばす。分割受信でも後続の文字を表示できることを確かめる。端末属性の問い合わせに応じる場合は、現在の固定応答を見直してビルドで使える機能を伝える。[終端処理](../../../src/core/parser.c)・[端末属性の応答](../../../src/core/interpreter.c)

日本語を表示する機器は、16色や最小限の制御列と、全角文字の幅・継続セルを扱えるセル形式を組み合わせる。英数字だけの製品には小型セルが適する。フォントや画面の大きさは同じでも必要な文字は製品ごとに異なる。

将来のboxrig UIとして、LovyanGFXで直接描く方法と、LVGLのウィジェットにする方法を検討した。単一画面なら、coreの`boxrig_terminal_take_dirty()`で変更された行と列の範囲を取り出し、`boxrig_terminal_get_cell()`で内容を読める。LovyanGFXではその範囲を直接描く。LVGLでは変更範囲をウィジェットに通知し、実際の描画イベントではLVGLが要求した範囲をセルから読み直す。これなら別のウィジェットに隠れた領域も、新しい端末入力を待たずに再描画できる。両者は移植先の候補である。[boxrigの差分描画例](../step-by-step/step-by-step-core.md#効率よくセルを描画する)・[LovyanGFXの描画API](https://github.com/lovyan03/LovyanGFX/blob/master/src/lgfx/v1/LGFXBase.hpp)・[LVGLの再描画](https://docs.lvgl.io/9.1/overview/draw.html)

## 実装段階の案と完了条件

以下は実装に着手するときの進め方である。各段階で動くcoreとドライバーを用意し、端末の入出力または描画結果で完了を判定する。

### 32.1 UTF-8単独で動くcore

専用機能の削除を確認する一時テストを先に追加し、現行実装で失敗することを確認する。専用処理と表、生成・配布物を取り除き、テストが通った時点でコミットする。その後、一時テストも削除する。完了条件は、UTF-8の日本語を表示・送信でき、通常の端末応答を返し、ビルドとSDKがShift_JIS専用のデータや生成手順を必要としないことである。

### 32.2 フックを有効・無効にして同じ端末を動かす

外部変換器を使う小さなドライバーで、分割受信、タイトルとURIの混在、貼り付け、送信の再試行を検証する。フック有効時は本文とタイトルを意図したとおりに変換し、生バイトと端末応答をそのまま送る。無効時はフック用APIを省いたSDKでUTF-8のドライバーをビルドして実行できることを完了条件とする。チェックポイントは、合意した復元条件をこの段階で検証する。

### 32.3 機能ごとにコードと割り当てを減らす

案1の候補は機能ごとに有効・無効の構成を作る。完了条件は、無効にした処理のコード・依存・初期バッファを省き、引き続き有効な操作をドライバーから使えることである。例えば画像なしで画像列の直後の文字を読み、履歴圧縮なしでスクロール後の行を取り出す。zlibを省く場合は、利用する3機能をすべて外した構成を検証する。

### 32.4 単画面の端末を描画し、フラッシュとRAMを測る

固定幅の画面を持つログ表示をドライバーで動かす。折り返し、スクロール、行末消去と差分描画を確認する。文字コードやセル形式を切り替えた構成では、日本語の列位置も確かめる。LovyanGFX版・LVGL版の製作は移植先を決めた時点で扱う。

比較用の端末は80列×24行にそろえ、同じデータを入力する。構成ごとに最終実行ファイルのコード・定数サイズと端末生成直後のヒープ確保量を記録する。小型セルは40列×15行でも実測し、試算と照合する。移植先のフラッシュ・RAMの予算値は未定である。選んだ構成ごとの測定値と表示結果を示し、全体テスト`make -j1 test`が通ることを実装の完了条件とする。
