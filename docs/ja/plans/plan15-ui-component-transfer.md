# plan15 環境別APIによるboxrig UIの移設

作成日：2026年10月28日

状態：2026年10月29日の実施依頼に基づき、案1の実装を開始しました。以下の調査記録に続く「実施時の契約と進捗」で、採用範囲と検証結果を管理します。

## 目的と対象

ウインドウ内に表示している端末を、UI操作で別のウインドウへ移せるようにします。ドックされた端末を独立ウインドウへ移すアンドックと、その逆の操作を想定しています。シェルや通信を継続したまま、表示と入力の接続先を変更する検討です。

対象はboxrig UIのX11、Win32、Wayland、GTK3、GTK4です。公開APIは各環境のウインドウ型、所有関係、イベント処理に合わせます。全環境へ同じ引数や同期的な完了方法を要求する共通APIは設けません。保持する状態や失敗時の扱いについては、各APIで対応関係を説明できる契約を検討します。

新しいトップレベルウインドウはアプリが生成し、その中へ端末を配置します。タイトルバー、ドッキング領域、ドラッグ操作、親ウインドウの寿命もアプリの担当です。OpenGLとD3D11は描画方式として扱い、環境別コンポーネントを移す際の資源管理を検討します。

今回の依頼は調査と設計案の保存です。調査中はユーザーがビルドしていたため、コードの参照だけで確認しました。この文書の保存を、各案の採用や実装開始とは扱いません。

## 用語と所有関係

`boxrig_terminal`は画面内容、履歴、端末モードを保持する端末本体です。`boxrig_ui_model`は端末を借用し、端末の変更を複数の表示へ配ります。各表示の状態を持つ`boxrig_ui_view`には、選択範囲、検索、装飾、描画更新の情報などがあります。

環境別コンポーネントの所有物は、`view`、レンダラー、入力アダプターなどです。端末とモデルは借用し、セッションや子プロセスを生成しません。通信を扱うセッションも端末を借用する別のオブジェクトです。この分離により、端末と通信を残して表示部分だけを交換できます。

コンポーネントには、自身が子ウインドウを所有する構成と、アプリ所有の描画先を借用する構成があります。借用する構成でのイベント転送、描画先の配置と寿命の管理はアプリの担当です。入力先と描画先が別のウインドウになる場合もあります。

`layout authority`は、端末の行列数やセル寸法を決める権限です。モデルにつき一つの`view`だけが持てます。複数の表示を共存させる場合は、権限の移譲とセル寸法の整合が必要です。

所有関係の根拠は[共通UIのview API](../../../include/boxrig/ui/view.h)、[セッションAPI](../../../include/boxrig/session.h)、[X11コンポーネント](../../../include/boxrig/x11/component.h)、[Win32コンポーネント](../../../include/boxrig/win32/component.h)です。

## 現在の対応範囲

| 対象 | コードと公開契約から確認した内容 |
| --- | --- |
| X11コンポーネント | 生成後に親や借用ウインドウを変更する公開APIはありません。借用する描画先と入力先はコンポーネントの寿命中固定です。 |
| Win32コンポーネント | 生成後の親・借用先の変更APIはありません。借用する両HWNDと表示コールバックのコンテキストは、コンポーネントより長く存続する契約です。 |
| X11レンダラー単体 | 生成時に渡したWindowへ結び付きます。サイズや描画領域は変更できますが、別のWindowへ交換する公開APIはありません。 |
| Win32ソフトウェアレンダラー単体 | `boxrig_win32_renderer_present()`に出力先HDCを毎回指定できます。この操作だけで入力接続が移るわけではありません。 |
| OpenGLレンダラー単体 | `boxrig_ogl_renderer_set_target()`でフレームバッファーを交換できます。同じコンテキストと所有スレッド、新しい描画先世代が必要です。処理中のフレームがある場合は交換できません。 |
| D3D11レンダラー単体 | `boxrig_d3d11_renderer_set_target()`で交換できます。同じデバイス世代とDPI、新しい描画先世代、フレーム処理中でないことが条件です。 |
| Waylandコンポーネント | 親surfaceを借用し、子surfaceとsubsurfaceを所有します。親のcommitをアプリへ依頼する要求・完了APIがあります。親変更の公開APIはありません。 |
| GTK3・GTK4ウィジェット | 取り外しと再配置に対応する処理があります。GTK4には同じウインドウへ取り外し・再接続するテストがあります。別ウインドウ間のアンドック全体を確認した結果ではありません。 |
| 共通UIのソフトウェア描画先 | `boxrig_ui_view_attach_render_target()`と`detach_render_target()`でピクセルバッファーの接続を変更できます。WindowやHWNDを変更するAPIではありません。 |

描画方式ごとの根拠は[X11レンダラーAPI](../../../include/boxrig/x11/renderer.h)、[Win32レンダラーAPI](../../../include/boxrig/win32/renderer.h)、[OpenGL API](../../../include/boxrig/render/opengl.h)、[OpenGLのコンテキスト検証](../../../src/opengl/runtime.c)、[D3D11 API](../../../include/boxrig/render/d3d11.h)です。共通のrenderer lifecycleには描画先世代の準備・確定操作がありますが、ネイティブウインドウの交換までは行いません。

環境別の根拠は[Wayland API](../../../include/boxrig/wayland.h)、[GTK3ウィジェット](../../../src/gtk3/terminal_widget.c)、[GTK4ウィジェット](../../../src/gtk4/terminal_widget.c)、[GTK4の入力ライフサイクル試験](../../../tests/gtk4/test_gtk4_widget.c)です。既存テストは参照だけで、今回の調査では実行していません。

## 現行APIだけで構成する場合

X11とWin32では、端末、モデル、PTYを含む通信セッションを維持し、旧コンポーネントを破棄して移動先に作り直す方法が使えます。旧コンポーネントへのイベント配送を止め、新しい親に同じモデルを渡して生成します。その後、フォントや表示設定、入力配送、フォーカスを設定し直します。行列数の変更は移動先の配置が確定してから端末とPTYへ反映します。

この方法では、シェルの再起動や端末内容の再送は不要です。ただし、コンポーネントとともに`view`も破棄されるため、選択、検索、装飾などは自動では移りません。IMEの未確定入力や転送中のクリップボード操作も、継続できる前提にはできません。[viewの破棄処理](../../../src/ui/view.c)と[コンポーネントの破棄処理](../../../src/x11/component.c)が根拠です。

以下の3案は、この移行処理をboxrig UIの責任として提供する方法を比較したものです。

## 案1 既存コンポーネントを別の親へ移設する

コンポーネントと`view`を維持し、親との接続を変更します。主な対象は、コンポーネントが子ウインドウを所有する構成です。選択範囲や表示設定を保持しやすく、ドックとアンドックに適しています。

| 環境 | 仮のAPI・操作 | 環境に応じた処理 |
| --- | --- | --- |
| X11 | `boxrig_x11_terminal_component_reparent(component, new_parent, allocation)` | Windowで新しい親を指定。子ウインドウの移設、配置、IME接続を更新する。 |
| Win32 | `boxrig_win32_terminal_component_reparent(component, new_parent, allocation)` | HWNDで新しい親を指定。同じUIスレッド内で移設し、DPIや入力状態を更新する。 |
| Wayland | `boxrig_wayland_terminal_component_request_reparent(component, new_parent, allocation, revision_out)` | wl_surfaceで新しい親を指定。要求の受理と、親commitを経た完了を分ける。 |
| GTK3 | ウィジェットの参照を保持し、コンテナー固有の取り外し・追加APIを使用 | 既存のrealize・unrealize処理を利用。必要な場合だけ移設前後の補助APIを設ける。 |
| GTK4 | ウィジェットの参照を保持し、コンテナー固有の取り外し・追加APIを使用 | 既存のunroot・root処理を利用。入力、描画、スケールを再接続する。 |

`allocation`は移動先での位置と寸法を表す候補です。引数型や、配置を既存APIで別に渡すかは未決定です。コンポーネントと`view`の維持に加え、ネイティブな子ウインドウやGPU資源の同一性をどこまで保証するかも、環境別に定めます。

### X11

OSの`XReparentWindow`を使う移設が候補です。同一画面などの条件と、移設による表示・イベントの変化を確認します。[X.OrgのXlib仕様](https://www.x.org/releases/X11R7.6/doc/libX11/specs/libX11/libX11.html)を根拠に、対応する範囲を定めます。

現在は生成時の親を`input_client_window`に保持し、XIMの`XNClientWindow`へ渡しています。子ウインドウだけを移しても、この接続は更新されません。IMEの再接続、座標、フォーカス、イベント配送を含めて移設します。[component.c](../../../src/x11/component.c)と[input.c](../../../src/x11/input.c)に該当処理があります。

### Win32

OSの`SetParent`を使う移設が候補です。新しいトップレベルの中へ既存の子コントロールを配置します。`SetParent`はWS_CHILDやWS_POPUPを自動変更せず、DPI awarenessが異なる場合にも制約があります。対応する親、スレッド、DPIの条件は[Microsoft公式文書](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent)に沿って決めます。

X11とWin32の標準スクロールバーは、コンポーネントの子ウインドウとして生成されています。親ごと移す構成では子孫として扱えます。移設後の配置や入力は別途検証します。[X11の生成処理](../../../src/x11/component.c)と[Win32の生成処理](../../../src/win32/component.c)が根拠です。

### Wayland

subsurfaceと親の関係を作り直す方式が候補です。既存の`wl_subsurface`を破棄して、新しい親へ関連付ける方法を検討します。同じ子surfaceを使い続けられる条件と、描画資源を再生成する条件は区別します。

[Waylandの仕様](https://wayland.freedesktop.org/docs/html/apa.html)では、subsurfaceの追加は親のcommitで反映されます。subsurfaceを破棄すると親との関係が削除され、直ちに非表示になります。別のトップレベルへ移す場合も、新しい親surfaceはアプリが用意する方針です。

boxrigには既に`take_host_action()`と`complete_parent_commit()`があります。移設要求の世代、新旧どちらの親に対する操作か、旧親を解放できる時点を識別できるよう、この仕組みとの接続を検討します。古い世代の完了通知で新しい移設を完了させません。

要求の受理と実際の表示完了は区別します。通信やプロトコルの致命的な失敗まで含めて、無条件に旧状態へ戻せるとは約束しません。回復可能な準備失敗と、接続を失った場合の状態を分けます。

### GTK3・GTK4

既存ウィジェットの参照を保持し、コンテナー固有のAPIで取り外して追加します。取り外し前に参照を保持する理由は、コンテナーが最後の参照を持っている場合に破棄されるためです。[GTK3の公式文書](https://docs.gtk.org/gtk3/method.Container.remove.html)にこの契約があります。GTK4では、例えば[GtkBox.remove](https://docs.gtk.org/gtk4/method.Box.remove.html)と[GtkBox.append](https://docs.gtk.org/gtk4/method.Box.append.html)を使う構成です。

任意のコンテナーへ配置する共通ラッパーは前提にしません。GTK4の`gtk_widget_unparent()`はウィジェット実装向けなので、アプリからの移設手順として直接使わせる設計にはしません。[公式の用途説明](https://docs.gtk.org/gtk4/method.Widget.unparent.html)が根拠です。

GTK4にはroot変更時の入力再接続と再描画、再配置後のフォーカス再開処理があります。OpenGLではunrealize時に描画資源を解放し、realize時に再準備する処理もあります。ただし、別ウインドウ、別スケール、IME処理中の移設全体は未検証です。補助APIの追加は、既存のライフサイクルだけでは不足する処理を特定してから判断します。

## 案2 借用する描画先と入力先を一括で差し替える

アプリ所有ウインドウへ描画する構成向けです。コンポーネントと`view`を維持し、接続先と関連する描画・入力資源を交換します。独自のドッキング領域や描画合成を持つアプリに適しています。

| 環境 | 仮のAPI | 一緒に更新する接続先 |
| --- | --- | --- |
| X11 | `boxrig_x11_terminal_component_rebind_targets(component, targets, allocation)` | 描画先Window、入力先Window、レンダラー、XIMと選択の接続 |
| Win32 | `boxrig_win32_terminal_component_rebind_targets(component, targets, allocation)` | 描画先HWND、入力先HWND、表示コールバックとコンテキスト、レンダラーとIMMの接続 |

既存の環境別`borrowed_target`型を基礎にできます。描画先と入力先を個別のsetterで交換すると、切り替え途中に表示と入力が異なる接続先へ向きます。この案では、新しい描画資源と入力アダプターを準備してから一括で切り替えます。回復可能な準備失敗では旧接続を維持する契約を検討します。

新旧の借用先は、APIが定めた切り替え完了までアプリが保持します。表示コールバックのコンテキストも同様です。古いコールバック、貼り付け、選択転送が新しい接続先へ届かない処理が必要になります。

現在のX11では、借用する描画先と入力先に同じscreen、Visual、depth、Colormapを要求しています。Win32では同じプロセスと現在のUIスレッドに属することが条件です。移設時に許す新旧の組み合わせは、これらの契約と描画方式に照らして定めます。

案1とは所有関係が異なるため、別の操作として提供します。WaylandやGTKに同形の借用先変更APIを追加することは、この案の前提に含めません。

## 案3 UI状態を取り出して新しいコンポーネントへ引き渡す

環境別の移送オブジェクトを用意し、`view`や表示設定の所有権を新しいコンポーネントへ引き渡します。Win32の仮案は`boxrig_win32_terminal_component_detach_content()`と`boxrig_win32_terminal_component_create_child_from_content()`です。X11とWaylandでは、それぞれの接続と親を受け取る生成APIを用意します。GTKでは、新しいウィジェットが移送オブジェクトを受け取る形になります。

移送オブジェクトは複製せず、一度だけ引き渡せる所有物にします。新しいコンポーネントの生成に失敗した場合は、移送オブジェクトを保持します。再試行や元の表示先への再接続が可能な契約を検討します。ネイティブ入力接続とホスト向けコールバックは、移動先に合わせて設定し直します。

子ウインドウを再利用できない場合や、描画方式も変更したい場合に向きます。ただし、描画方式やプラットフォームをまたぐ転送を自動的に対応範囲へ加える案ではありません。必要な組み合わせを選ぶ段階で、保持できる状態と再計算する状態を定めます。

現状ではコンポーネントが`view`を生成・破棄します。この案には所有関係の変更が必要です。コンポーネントの表示設定や背景、フォント資源まで移送する範囲を明確にし、移送中にも端末の内容を維持できるようにします。3案の中では構造の変更が最も大きくなります。

## 案の比較と現時点の推奨

| 案 | 向く構成 | 主な利点 | 主な検討点 |
| --- | --- | --- | --- |
| 案1 親の変更 | コンポーネント所有の子ウインドウ、GTKウィジェット | 既存viewと表示設定を維持しやすい | 各環境の親変更、入力再接続、GPU資源、非同期完了 |
| 案2 借用先の変更 | アプリ所有の描画領域 | 描画先と入力先を一体で交換できる | 借用先の互換性、新旧資源の寿命、失敗時の扱い |
| 案3 状態の引き渡し | 表示オブジェクトを作り直す構成 | ネイティブ資源の再生成と状態保持を分けられる | viewと表示設定の所有関係を変更する範囲 |

通常のドック・アンドックに対する現時点の推奨は案1です。借用描画先も必要なら案2を追加する構成を推奨しました。案3は、既存の表示オブジェクトを維持する方式では要件を満たせない場合の候補です。3案の採用はまだ決めていません。

## 移設時の状態と完了条件の方針

端末、モデル、通信セッションは維持します。移設操作だけで端末の行列数を変更せず、新しい配置が確定したときに既存のリサイズ手順へ接続する方針です。移設の途中でも、受信データや端末の応答を失わない構成を検討します。

選択範囲、検索、装飾、背景、フォントなどの表示設定は原則として保持します。DPIやフォント寸法が変わった場合は、選択の幾何情報やレイアウトの再計算が必要か確認します。viewの保持だけでは、すべてのキャッシュや座標が有効なままである保証にはなりません。

IMEの未確定入力、候補表示、押下中のキーとボタン、ポインター捕捉、処理中の貼り付け、クリップボード所有権には移設時の規則が必要です。確定、取消、継続のどれを採るかを環境別に決めます。内容の二重送信や、遅れて届いた旧入力の適用を防ぐことを検証対象にします。

新旧表示を一時的に共存させる方式では、layout authorityを重複させません。複数viewのセル寸法の制約と、失敗時の権限の戻し方も確認します。案1・案2で同じviewを維持する場合には、不要な権限の解放・再取得を避ける設計を検討します。

処理中の描画フレームやコールバックから移設を要求した場合の扱いを決めます。BUSYを返すか、アプリのイベントループで後から実行するかは未決定です。移設前の描画完了や入力通知は、移設後の世代へ適用しません。新しい描画先には必要な範囲を再描画します。

APIの成功が要求の受理を表すのか、移設完了を表すのかを明記します。Waylandでは、親commitの完了と旧親を解放できる時点も契約の一部です。回復可能な準備失敗では旧表示を維持するか、案3なら移送状態を保持します。接続やデバイスを失った場合の回復まで、同じ保証に含めません。

現在の`quiesce()`は終了へ進む操作です。[共通の終了ライフサイクル](../../../include/boxrig/ui/lifecycle.h)にも再開する遷移はありません。移設用の一時停止・再接続は、終了処理と区別して設計します。

## 実装を開始する場合の段階案

以下は方式を選んだ後の進め方です。採用しない案は実装範囲に加えません。各段階では、その環境で動かせるドライバーと挙動を検証するテストを作り、個別にビルド・実行できる単位で進めます。

### 段階0 対応範囲とAPI契約を決める

案1・案2・案3の採否、対象の環境と描画方式を決めます。保持する状態、終了する入力操作、対応する接続・スレッド・DPI、失敗時の状態を整理します。新規関数の型と成功・完了の意味、アプリが保持する親やコールバックの寿命を定義します。

完了条件は、実装する案と組み合わせが明記され、各APIの保持状態、失敗時の状態、旧資源を解放できる時点を説明できることです。

### 段階1 最初の環境で往復移設を動かす

選んだ一環境で、表示中の端末を二つのウインドウ間で往復させる実行可能なドライバーを用意します。端末内容と通信の継続、選択と表示設定、移動先からの入力、配置変更を対象にします。問題を再現するテストのREDを確認してから実装し、GREENを確認します。

### 段階0で定める対応範囲

対象はX11、Win32、Wayland、GTK3、GTK4です。現在提供している描画方式も対象にします。X11のソフトウェア描画とOpenGL、Win32のソフトウェア描画とOpenGLとD3D11、Waylandの共有メモリー描画とOpenGL、GTK3・GTK4のCairoとOpenGLを順に検証します。異なる環境や描画方式への交換は行いません。

X11とWin32では、コンポーネントが所有する子ウインドウを移します。借用先を指定して生成したコンポーネントは対象外です。引数はコンポーネントと新しい親にし、配置は既存のallocate APIで別に指定します。移設だけでは配置、端末の行列数、PTYの寸法を変更しません。

X11は同じDisplayとscreen上にある有効なInputOutputの親へ移します。自身や子孫は親にできません。子Window、レンダラー、view、モデルと端末を保持し、XIMの入力コンテキストを新しい親に作り直します。成功はサーバーへの親変更の反映を表し、画面への提示完了は保証しません。成功後は旧親を破棄できます。新親は次の移設かコンポーネントの破棄までアプリが保持します。

Win32も子HWNDとviewを保持します。同じプロセス・UIスレッドと互換性のあるDPI awarenessの親を受け付けます。DPIが変わるときは既存のフォント寸法と配置の更新へ接続します。成功は親の交換完了を表します。旧親は成功後に解放でき、新親は次の移設かコンポーネントの破棄まで保持します。

Waylandは同じcontextの親surfaceへ移します。要求の受理と親commitの完了を分け、host actionに対象の親と世代を対応付けます。古い世代の完了では新しい移設を確定しません。受理後に旧親とのsubsurface関係を解除した時点と、新親のcommit後に移設が完了した時点を区別します。公開コメントと試験で、親を解放できる時点を明記します。

GTKでは参照を保持した同じウィジェットを、各コンテナーの標準APIで別のウインドウへ移します。移設後の配置とフォーカスはアプリが設定します。CairoとOpenGLそれぞれで、取り外しによる入力接続の終了と再配置による接続再開を検証します。

### 保持状態と失敗時の扱い

端末、モデル、view、選択、検索、装飾、背景、フォント設定、layout authorityを保持します。セッションは移設APIの所有物にせず、移設中も同じ端末に接続します。新しい描画先では再描画を要求します。GPU資源は同じ子ウインドウとコンテキストを使える場合に保持し、GTKのunrealizeなどで失われる場合は既存の再生成経路を使います。

ネイティブAPIでは処理中の入力を無理に移しません。キーやボタンの押下、未確定入力、未完了の貼り付け、描画や入力コールバック中の呼び出しはBUSYとして、状態を変更せずアプリのイベントループから再試行します。既に端末へ送ったデータは保持します。GTKでは既存の取り外し処理による未確定入力の取消を検証します。X11のクリップボード所有権と送信中の選択データは同じ子Windowとアダプターに保持します。

引数の不正、対応しない親、要求受理前の回復可能な資源準備失敗では旧表示先と入力を維持します。Waylandでは、要求受理後に新しいsubsurface関係を準備します。この準備に失敗した場合は、移設要求を保持して再試行します。接続切断やデバイス消失は通常の障害処理に従い、移設APIによる復旧保証には含めません。アプリが保持した旧入力は入力世代で識別し、古い世代の通知を新しい接続へ適用しないことを検証します。

### 段階2のWayland実装と検証

Waylandに非同期の親変更APIを追加しました。要求を受理すると旧subsurface関係を解除し、同じ子surfaceを新しい親へ接続します。アプリはhost actionに含まれる親をcommitし、その世代を完了通知へ渡します。移設の完了条件は、その後のサーバー応答です。描画の提示完了とは区別しています。

子surfaceには同時に二つのsubsurface関係を設定できません。そのため、要求受理前の失敗では旧接続を残し、受理後の準備失敗では受理済み要求を保持する契約としました。frameを呼び直すと準備を再試行します。旧親は要求受理後に破棄でき、新親は次の移設を受理するまで保持します。根拠は[Waylandのsubsurface仕様](https://wayland.freedesktop.org/docs/html/apa.html#protocol-spec-wl_subsurface)と、SDKの生成済みAPIコメントです。

Weston上の共有メモリー描画とOpenGLで4回の移設を検証しました。子surface、view、layout authority、選択を保持し、提出する描画内容も一致しています。OpenGLではEGLSurfaceとレンダラーを再生成せず、コンテキストと描画先の世代も維持できました。古い親commitの完了を渡しても、新しい移設は完了しません。

操作例examples/wayland/transfer.cでは、F6キーを離すと端末を別の親へ移します。二つの親は異なる大きさを持ち、移設後に配置とPTY寸法を更新します。--verifyでは、子プロセスの準備通知、移設完了、入力に対する応答を順に確認します。同じPTYセッションで2回の移設と通信が成功しました。

操作例から、親commit待ちの配置と出力スケール変更が重なる問題を検出しました。スケール変更が、親へ反映する前の描画バッファーを交換していました。親commit完了まで元の配置を保持するテストでREDを確認し、その間のframe処理を保留する修正でGREENとなりました。待ち時間の追加やコンポジターの変更による回避は行っていません。

この問題の調査では、Weston 13の共有メモリーバッファー参照でSIGSEGVを確認しました。[同版のPixman実装](https://gitlab.freedesktop.org/wayland/weston/-/blob/13.0/libweston/pixman-renderer.c)と[現在の実装](https://gitlab.freedesktop.org/wayland/weston/-/blob/main/libweston/pixman-renderer.c)には、破棄済みSHMバッファーの扱いに差があります。boxrigでは上記の配置順序を修正し、既存のWeston 13で再検証しています。外部コードは変更していません。

C99の警告をエラーとするビルド、test-wayland-input、Westonの共有メモリー・OpenGL試験、両方式の操作例が成功しました。Wayland入力試験はASan・UBSan・リーク検査も通りました。OpenGL統合試験のリーク検査除外は既存のEGL向け設定です。Westonのdebug protocolに関する通知も既存ランナーの設定によるもので、コンパイル警告はありません。

証跡はartifacts/plan15/のwayland-red.log、wayland-scale-red.log、wayland-scale-green.log、wayland-frame-green.log、wayland-frame-gl-green.logに保存しています。入力途中、資源準備失敗、古い入力通知の詳細は段階3で補います。GTKの環境追加、公開利用文書と全体テストも未完了です。

amd64・i686の通常ビルドで全optional-interface構成が成功しました。REDはwin32-release-red.log、修正後はwin32-release-green.logに保存しています。


### 段階2・3のGTK3とGTK4

GTK3・GTK4は、同じウィジェットの参照を保持し、標準コンテナーAPIで別のウィンドウへ移す構成にしました。CairoとOpenGLを切り替えずに移設し、同じwidget、view、選択、フォント設定とPTYを保持します。OpenGLのネイティブ資源は、unrealize後の既存の再生成処理で接続し直します。

examples/gtk/transfer.cを両GTK向けにビルドできます。F6操作に加え、--verifyでは子プロセスの準備通知、1回目の移設への応答、復帰後の応答を順に確認します。移設後に旧ウィンドウを破棄し、その後の表示と通信も検証しました。X11・Wayland、GTK3・GTK4、Cairo・OpenGLの8構成で往復が成功しています。make test-gtk-transferで実行できます。

既存の入力ライフサイクル試験を別ウィンドウ間の移設へ拡張したところ、GTK4で旧IME確定のキューが再配置後に送られる問題を再現しました。取り外し時に入力世代を進め、未開始の貼り付けと古い確定入力を破棄する修正でGREENとなりました。取り外した後も未確定文字が残る問題も、REDを確認してから取消処理を追加しています。

開始済みの貼り付けは、残りの本文と終了通知を新しい配置先で継続します。入力世代を更新する際、この貼り付けだけを引き継ぎます。GTK3とGTK4の試験で、送信容量が埋まった状態から移設し、残りの本文を欠落なく送ることを確認しました。旧クリップボード応答の破棄、移設先の新しい入力とフォーカスも検証しています。

widget試験は、GTK3・GTK4それぞれのX11 Cairo、X11 OpenGL、Wayland Cairoの6構成で成功しました。GTK3のWayland試験ではseatがないため、X11の遅延クリップボードケースを省略しています。同ケースはX11で成功しました。描画方式と通信継続は、上記8構成のドライバーでも確認しています。警告をエラーとして扱うビルドに新しい警告はありません。

標準操作は[GTK3 Container.remove](https://docs.gtk.org/gtk3/method.Container.remove.html)、[GTK4 Window.set_child](https://docs.gtk.org/gtk4/method.Window.set_child.html)とSDKの宣言・コメントを確認しました。quiesceは終了操作のため移設には使いません。公開コメントと利用文書には、参照、入力、再配置、OpenGL資源の扱いを記載しました。全体テストと最終的な完了条件の照合は次の段階で行います。

最終のGTK4試験では、ブラケット付き貼り付けの開始通知を送った後に移設し、残り本文と終了通知までバイト列で確認しました。GTK3・GTK4のX11 Cairo試験はASan・UBSan付きで成功しています。GTK3のリーク検査には、既存ランナーと同じ[倍率変更時の限定除外](../../../tests/gtk3/gdk_scale_leaks.supp)を適用しました。[GTK 3.24.41の該当コード](https://github.com/GNOME/gtk/blob/3.24.41/gdk/x11/gdkscreen-x11.c#L1131-L1160)から割り当てたリスト240バイトだけが対象で、設定の追加・変更はありません。ログはgtk3-final-green.logとgtk4-final-green.logです。
