# plan31 プロセス間で端末の状態を引き継ぐ

2026年11月24日作成。調査基準は`268522c`。実装後の検証結果を末尾に記す。

## 目的と前提

アプリが動作中の端末を別プロセスの表示先へ移し、同じ通信相手と操作を続けられるようにする。最初の利用例はelder-termsの単独ウインドウとタブトレイ間のドッキング・分離だが、boxrigの公開機能はアプリのタブ構造や特定の通信方式に依存させない。パイロットの計画はelder-termsリポジトリの`docs/ja/plans/plan30-terminal-tab-docking.md`にある。

`boxrig_terminal`は画面、履歴、入力モードなどを持つ端末本体である。`boxrig_session`は通信路と端末をつなぎ、`boxrig_ui_model`と表示先は端末の状態を画面に反映する。現行のGTK3・GTK4には、同一プロセス内でウィジェットを別ウインドウへ移す手順と往復移設の例がある。プロセスをまたぐ場合はポインターやGTKウィジェットを引き継げないため、移動先で端末を復元して表示先を作る。[基本概念](../architecture.md)・[GTK移設](../platforms/gtk.md)・[既存の移設計画](./plan15-ui-component-transfer.md)

端末を移した後も通常の入出力を速く保つ。ローカルの疑似端末（PTY）では、移動先プロセスがPTYのマスター側ファイル記述子（FD）を直接読み書きできる構成を対象にする。通信内容を常時別プロセスへ中継する場合は、キー入力と応答の双方でプロセス境界を越えるため、別の性能案として比較する。SSHなどの通信路オブジェクトはアプリが所有し、そのプロセスをまたぐ移管方法もアプリが決める。[通信路API](../../../include/boxrig/session.h)・[POSIX PTY API](../../../include/boxrig/posix.h)

## 転送対象と公開契約

次の1バイトから同じ動作を再開するために必要な端末データを、チェックポイントと呼ぶ。端末の所有スレッドで書き出し、別プロセスで新しい`boxrig_terminal`へ読み込むAPIを追加する。形式はバージョン付きとし、整数の幅、バイト順、各領域の長さを定める。ポインターとコールバックは呼出元のアドレス空間だけで有効なので、移動先で参照を組み直す。公開名の候補は`boxrig_terminal_export_checkpoint()`と`boxrig_terminal_import_checkpoint()`とする。詳細な引数と戻り値は最初のドライバー試験で確定し、データの最大長、形式の版、未対応版、容量超過、不完全なデータの扱いを公開コメントへ記す。書き出し元は変更せず、読み込み先は検証と割り当てがすべて成功してから端末を公開する。

| 対象 | 引き継ぎ方針 |
| --- | --- |
| 画面と入力 | 主画面・代替画面、属性、履歴と折り返し、表示位置、カーソル、スクロール領域、タブ位置、パレット、リンク、入力モード、キー変換設定を復元する。 |
| 受信途中の状態 | UTF-8デコーダー、制御列パーサー、OSC・DCSの途中状態を保持し、次の受信バイトで元の端末と同じ結果になるようにする。 |
| 端末からの送信とホスト要求 | 未送信の応答、部分送信位置、順序制約、保留中の要求を検査する。外部へ渡した未完了要求は移動前に完了・取消するか、呼出元へ再試行可能な状態を返す。 |
| Kitty画像 | 画面上の画素だけでなく、後続の更新・削除命令に必要な画像ID、資源、配置、アニメーション状態を扱う。進行中のアップロードや外部データ要求は転送境界を定義する。 |
| 表示と通信 | `boxrig_ui_model`、view、GTKウィジェット、描画資源とキャッシュは移動先で生成する。PTY、SSH、アプリの送受信キューは端末データとは別に扱う。 |

デコード済み文字の一時キャッシュ、履歴展開キャッシュ、字形・GL資源、描画のdirty情報は再構築できる。履歴や画像の原本を省くと表示や後続命令の結果が変わるため、これらは容量制限を検査して保持する。既存のテキストスナップショットで取得できるのは、文書全体または指定した範囲の論理テキストである。[端末内部状態](../../../src/core/terminal_internal.h)・[Kitty画像](../../../src/core/graphics.h)・[既存のテキスト取得API](../../../include/boxrig/terminal.h)

選択を引き継ぐアプリには、確定済みの両端を論理テキスト上の位置として保存し、復元後の同じ行と文字へ対応づける手段が要る。旧viewのハンドルを新viewに渡さず、位置の識別子を保存するか、復元先への対応を返す。本文監視やリンク認識を使う場合も、通知済みの結果と未通知のイベントを区別する。呼出元がルールを再登録しても、既に処理したイベントが新着として二度届かない扱いを決める。

`boxrig_session`には端末へ渡し切っていない受信データと、通信相手からの入力終了（EOF）の処理状態が残る。第一段階では、呼出元が受信を止め、`boxrig_session_input_pending()`で保留を確認し、未処理分を消費してから端末を書き出す契約を試す。ホスト要求による停止などで排出できない場合は失敗理由を返し、書き出し元の端末を操作可能なまま残す。排出できない状態を正しく扱う必要が明らかになった場合は、セッションの未消費データを順序付きで取り出す独立APIを設計する。[セッション実装](../../../src/session/session.c)・[セッション公開API](../../../include/boxrig/session.h)

## 所有権の切替

次の手順はboxrigを使うアプリのプロトコルである。boxrigは端末データの書き出し・読み込みと、その可否を判断できる状態を提供する。通信の停止、プロセス間通信、移動先の起動、どちらのプロセスが入力できるかの判定は呼出元が実装する。

1. 移動先を準備し、旧所有者への新規入力・リサイズ要求を止める。通信路からの読み出しも安全な境界で止め、既に読み出したバイトを端末へ投入する。未送信データがある場合は、転送データと通信路へ送信済みの位置を合わせる。
2. 旧所有者が端末を書き出す。移動先は容量と形式を検証して復元し、旧端末と同じ行数・桁数で最初の描画を準備する。旧所有者は切替確定まで端末と通信路を保持する。
3. 呼出元が一意のセッションIDと所有世代を使って切替を確定する。確定後は新所有者のみが入力・送信・リサイズを行い、保留した受信を順番に再開する。表示領域によって行列数が変わる場合は、移動先の準備後に一度だけ通信相手へ通知する。
4. 確定前に失敗した場合は、保留した受信を旧所有者へ戻す。確定応答が失われた場合は現在の所有世代を照会し、旧・新両方から同じ入力を送らない。旧所有者は確定を確認してから表示先と端末を解放する。

ローカルPTYのmaster FDはUnixドメインソケットの`SCM_RIGHTS`で移動先へ渡せる。FDを受け取ったプロセスが直接読み書きしても、子プロセスを`waitpid`する権利は移らない。起動元は子の終了回収を一度だけ担当する。FD転送前後の読み出し所有者とキューの位置を確定し、双方が同時にPTYを読まない。WindowsのConPTYやSSHの移管は、それぞれのアプリとプラットフォームに応じて別途設計する。移動先では、受け取ったFDを読み書きする通信路を復元済み端末に接続する。既存の`boxrig_session_create()`に読み書き用コールバックを渡す構成から試す。[通信路の接続](../../../include/boxrig/session.h)・[POSIX PTYの所有契約](../../../include/boxrig/posix.h)・[FD転送の仕様](https://man7.org/linux/man-pages/man7/unix.7.html)・[子プロセスの終了待ち](https://man7.org/linux/man-pages/man2/waitpid.2.html)

## 代替方式と性能の検証

| 方式 | 通常入出力への影響 | 移設時の負担 |
| --- | --- | --- |
| 端末状態とPTYのFDを移す | 移設後も新所有者がPTYを直接読み書きする。 | 履歴・画像を含む端末データの書き出し、転送、復元、初回描画が必要。 |
| 通信路を元プロセスに置き、端末状態を移す | 移設後のキーと受信出力をプロセス間で中継する。 | PTYのFDを移す必要がない。SSHの接続オブジェクトを元プロセスに保てる。 |
| 端末本体と通信路を常駐させ、表示先だけ移す | 端末処理は常駐先で続き、表示差分と入力を転送する。 | 履歴全体の再転送を避けられるが、選択、スクロール、画像、支援技術に対応するリモート表示APIが要る。 |

同一プロセス内の移設には既存のGTK手順を使用できる。測定では直接接続の現行構成と新構成を同じマシンで交互に試し、boxrigの独立したドライバーではローカルPTYの直接接続と中継を比較する。SSHの直結と移動後の中継はelder-termsのplan30で測る。キー入力から通信相手への到達、受信から`boxrig_terminal_feed()`の完了、最初の描画、p50・p95・最大値、大量出力のMiB/s・CPU時間をそれぞれ記録する。移設では受付停止から再開までの時間、転送バイト数、履歴行数と画像量の関係を記録する。比較する前に測定条件と許容差を決め、既存の描画時間からIPC費用を推定しない。

## 段階と完了条件

各段階では失敗する試験を先に追加し、REDを確認してから最小の変更を実装する。GREEN、警告のないビルド、段階ごとの成果物を確認してコミットする。

### 31.1 コア状態の往復

プロセスを二つ使うCドライバーを用意し、固定出力を途中で書き出して新しい端末へ読み込む。UTF-8・OSC・DCSの途中、主画面と代替画面、入力モード、未送信応答、履歴、画像を含むケースを増やす。元の端末へ続きを送った結果と、復元した端末へ同じ続きを送った結果について、画面・履歴・出力バイト列が一致することを完了条件とする。保存した選択の両端が、折り返しや結合文字のある行でも同じテキストを指すことを確かめる。無効な版、破損、容量超過では旧端末を使い続けられることも試す。

### 31.2 セッションとの境界

未消費の受信データ、部分送信、EOF、保留中のホスト要求を持つケースをドライバーに加える。静止可能な状態では受信・送信の欠落と重複がなく、静止不能な状態では書き出しを明示的に拒否することを完了条件とする。必要と判明したセッションの追加APIはこの段階で公開する。

### 31.3 PTYを使う二プロセス実例

一つの子プロセスとPTYを維持して端末とmaster FDを移し、往復移設後も連番出力、キーの応答、行列数を確認する。起動元が子を一度だけ回収し、移動先の確定前停止で元の端末へ戻れることを完了条件とする。大きな履歴とKitty画像を含む移設時間も測る。この段階の成果は他アプリから実行できる独立した例とする。

### 31.4 性能判定と公開

直接FD移管と通信中継を同条件で測り、通常入力、大量出力、移設停止時間、転送量を記録する。測定結果に基づき、性能上の採用範囲と未対応の通信方式を公開APIと利用文書に明記する。全体試験の`make test`を実行し、計画の各完了条件を満たしたことを確認する。elder-termsのplan30へ使用可能な公開API、検証したboxrigリビジョン、測定条件と結果を渡す。

## 実装と検証結果

plan30で利用できるboxrigの実装と試験は`e09a00f`に含まれる。通常の読み書きは既存の経路を使う。移設時にアプリが呼ぶAPIと、ホスト側の準備・失敗時の戻し方は[セッション利用手順](../sessions.md#動作中の端末を別プロセスへ移す)にまとめた。

| 31.1 | UTF-8・CSI・OSC・DCSの途中で書き出し、元と復元後の端末へ同じ続きを渡して画面と応答を比較した。圧縮履歴内の結合文字・全角文字を同じ選択範囲で取得できた。Kitty画像のフレーム切替、相対配置、Unicodeプレースホルダーも確認した。未対応版、破損、容量超過を拒否した後も元の端末を使える。 |

### 定常入出力

Linux 7.0.0-43 x86_64、Core i9-12900KS、GCC 13.3.0、最適化`-O2`を使用した。直接接続、復元済み端末へのFD移譲、常時中継の順に5周測定した。各経路で1バイトの入力と応答を400回往復した後、8MiBのASCII出力を最大4KiBずつ読み取り、端末へ投入した。入力時刻はPTYに書く直前、到達時刻は相手が読んだ直後、往復の終了は応答を読み終えた時点とした。CPU時間には端末、通信相手、中継プロセスを含む。[測定プログラム](../../../tests/performance/checkpoint_pty.c)

| 経路 | 入力到達 p50 / p95 / 最大 (µs) | 往復 p50 / p95 / 最大 (µs) | 受信からfeed完了 p50 / p95 / 最大 (µs) | 大量出力 (MiB/s) | CPU (ms) |
| --- | --- | --- | --- | ---: | ---: |
| 直接 | 4.5 / 5.1 / 93.0 | 9.0 / 9.9 / 198.7 | 3398.8 / 3590.0 / 5550.2 | 1.193 | 6729 |
| FD移譲後 | 3.6 / 3.7 / 127.7 | 7.6 / 8.2 / 168.4 | 3414.1 / 3622.8 / 6819.0 | 1.186 | 6753 |
| 常時中継 | 8.4 / 9.2 / 283.9 | 16.7 / 18.8 / 727.4 | 3406.5 / 3584.5 / 5857.3 | 1.191 | 6743 |

p50、p95、速度、CPUは各周の測定値の中央値、最大は全5周の最大値である。測定前に、FD移譲後の往復p95増分を50µs以内、大量出力の速度低下を10%以内とした。実測差は−1.7µsと0.59%低下で、両方の条件を満たした。常時中継では往復p95が直接接続より8.9µs長かった。大量出力では1チャンクの端末処理に約3.4msかかり、3経路の速度は近かった。SSHの中継費用はこの比較からは求められない。

### 移設中の停止時間

24行80列、Pango 1.52.1、Cairo 1.18.0で測定した。移動先プロセスを先に起動して待機させ、送信元での書き出し開始から、初回描画後の応答が送信元に届くまでを停止時間とした。初回描画にはモデル、view、レンダラーの作成、オフスクリーンの画像面への描画とフラッシュを含む。画像は512×384ピクセルのRGBAで、描画時に画像が実際に合成されたことも検査した。各条件を順番を変えて5回測った。各列は独立した中央値である。[描画ベンチマーク](../../../tests/performance/checkpoint_draw.c)

| 0 | 0 | 8,852 | 0.036 / 0.030 / 0.646 / 22.466 | 22.705 / 26.732 |
| 0 | 768 | 795,694 | 0.525 / 0.261 / 1.072 / 21.913 | 24.018 / 26.983 |
| 10,000 | 0 | 1,478,852 | 5.749 / 0.479 / 16.397 / 19.551 | 44.316 / 45.702 |
| 10,000 | 768 | 2,265,694 | 6.222 / 0.805 / 17.161 / 20.293 | 44.669 / 46.308 |

この条件では、履歴を1万行加えた場合の費用は主に両端の書き出しと読み込みで生じた。elder-termsではこの結果を基準に、ウィンドウの作成、実画面への提示、SSH接続の中継を含む利用者側の待ち時間を別途測れる。
