# X11の描画予約と文字・画像の処理を変更した結果

[前回の計測](step23-notcurses-btop-measurements.md)で時間がかかっていた処理を変更し、同じ入力を変更前後で再生しました。基準版は`94042ff`、すべての変更を含む版は`f97851f`です。Ubuntu 24.04、Core i9-12900KS、GeForce RTX 3090、75 HzのX11画面を使い、端末は118列45行、1セルは7×14画素にそろえました。アプリが出力を終えるまでの経過時間と、boxrigプロセスが使ったCPU時間は別々に測りました。

## X11の連続出力とキー入力

ネイティブX11端末では、間を置いて届く出力をすぐに描きます。その直後に出力が続く場合は、最大8ミリ秒の間に受け取った変更をまとめます。待ち時間は最初に決め、後続の出力で延長しません。待っている間も疑似端末（PTY）の読み書きとX11イベントの処理を続けます。キー入力やリサイズがあれば先に処理し、出力が止まればタイマーで定期的に起きることもありません。EGLの交換間隔は1です。[イベントループ](../../../examples/boxrig_term/x11/event_loop.c)・[描画期限の試験](../../../tests/x11/test_x11_event_wait.c)

| X11 OpenGL ESで測った項目 | 変更前 | 描画予約の変更後 |
| --- | ---: | ---: |
| 実際のgridデモの実行時間 | 10.29秒 | 1.67秒 |
| その間の端末CPU時間 | 3.69秒 | 1.28秒 |
| キー送信から応答の1セルが画面に現れるまでのp95 | 22.71 ms | 21.56 ms |

実行ファイルを交互に動かした3組の中央値です。デモはboxrigのPTYで直接 `notcurses-demo -c -d 0.03 g` を実行しました。別の試行で、大きなPTY入力の最初から最後までにバッファを交換した回数は769回から138回に、交換関数内の経過時間の合計は6.54秒から0.25秒になりました。交換完了の間隔の中央値は両方とも13.33ミリ秒で、変更後の最長間隔は20.82ミリ秒でした。デモの途中でも画面を更新しています。

キーの試験では、対象のウィンドウに100ミリ秒間隔でキーを送り、子プロセスがそのキーを受けて1セルを書き換えるところまでを観測しました。最初の表示を除く各23回から95パーセンタイル（p95）を求めています。すべての画素反映時間にはX11ウィンドウの連続2回の読み取りを含みます。全変更を含む版でも同じキー経路を1組測り、変更前が20.10 ms、変更後が22.31 msでした。[入力と画素の観測](../../../tests/performance/frame_latency.c)

## xrayの画像入力

画像の制御シーケンスの中では、印字可能なASCIIがどこまで続くかを調べてからBase64を復号します。走査の上限を先に求め、8バイトでまとめて検査するようにしました。制御文字などを含む8バイトと末尾だけを1バイトずつ調べます。256通りのバイト値を位置をずらして入れ、1バイトずつ渡す場合とパーサーの出力を照合しました。[入力走査](../../../src/core/parser.c)・[境界と再試行の試験](../../../tests/test_parser.c)

保存済みのxray出力のうち864更新、1,772,072,485バイトを端末コアだけで再生しました。同じ物理コアの論理CPU 4に固定し、順番を入れ替えた3回の中央値です。

| 走査方法 | 再生CPU時間 | ユーザーモードの命令数 |
| --- | ---: | ---: |
| 変更前 | 1.598秒 | 404.91億 |
| 上限だけを先に決定 | 1.266秒 | 334.38億 |
| 上限を先に決定して8バイトずつ検査 | 0.965秒 | 235.39億 |

ウィンドウで23画像すべてのRGBAのSHA-256、配置、最後の消去を照合し、最初の1枚を除く22画像でCPU時間を測りました。1画像あたりの入力CPU時間は、X11 OpenGL ESで3.55から2.71 ms、GTK3 OpenGLで3.73から2.71 ms、GTK3 Cairoで3.31から2.78 msです。実際のxrayデモをGTK3 OpenGLで動かした3組では、端末CPU時間が7.24秒から6.20秒に減りました。デモの実行時間は15.42秒と15.44秒でした。[画像・配置と画素の照合](../../../tests/performance/check_xray_replay.mjs)

## btopの文字整形

OpenGLの文字描画では、Pangoが返す整形区間と端末の文字のまとまりを、テキスト上の位置に沿って一度突き合わせます。1文字が複数の書体にまたがる場合も各区間を含め、ここで求めた列範囲から画面上の字形の位置を決める方式です。隣り合う区間の書体が同じなら、書体を識別する文字列を共用します。[文字整形の変更](../../../src/opengl/text_provider.c)・[Pangoが返す区間の順序](https://docs.gtk.org/Pango/func.itemize.html)

| 100ミリ秒更新のbtop | X11 OpenGL ESの変更前 → 変更後 | GTK3 OpenGLの変更前 → 変更後 |
| --- | ---: | ---: |
| 実アプリで受信1更新あたりの端末CPU時間、3組の中央値 | 5.97 → 5.55 ms | 6.13 → 5.71 ms |
| 固定入力1更新あたりの端末CPU時間、7組の中央値 | 5.83 → 5.98 ms | 6.62 → 6.23 ms |
| 固定入力の画素反映p95、7組の中央値 | 25.57 → 26.61 ms | 16.04 → 18.66 ms |

X11の対照には描画予約だけを変更した版を使いました。実アプリからの受信は12秒間に118〜119更新です。固定入力では両構成とも全24画面で画素が一致しました。p95が延びたのはX11で7組中4組、GTK3で7組中5組です。高頻度更新時のCPU削減として採用し、表示遅延の改善は確認できませんでした。参考に2秒更新を各1組で測ると、1論理CPUを100%とする端末CPU使用率はX11で0.33%から0.67%、GTK3で1.33%から0.25%でした。いずれも6更新の観測です。

書体の処理だけを調べるため、仮想X11上のGTK3 OpenGLで同じ固定入力を3組再生しました。24更新で計測した整形行は各712行、書体を識別する文字列の生成は16,417回から5,912回でした。行整形関数内の1更新あたりのCPU時間の中央値は1.98 msから1.60 msです。今回は行内の重複処理を省きました。前のフレームの字形を部分的に再利用する方式は、等幅数字を対象とした過去の試作で検証しています。この試作では、実際のbtopのCPU時間が減らず、GTK3の画素反映も遅くなっています。[数字の部分整形を試した結果](plan21-notcurses-btop-rendering-performance.md#212-btopの行整形)

## Cairoで下地をコピーする費用

boxrigは、文字がセルの端をまたいでも同じ輪郭を描けるように、字形をいったん小さな画像に描いてから必要な範囲を画面に戻します。この一時画像に背景や背面画像の画素を写すため、従来は字形を描くたびにCairoの描画関数を呼んでいました。

一時画像を通さずに文字を直接描く試作では、gridの全24画面で変更前との画素差が生じ、半透明の下地を部分更新する試験にも失敗しました。採用した実装では一時画像と字形の描き方を保ち、同じ形式の画像で画素の位置が整数座標で一致するときだけ、下地を行ごとにコピーします。画像を直接読む前にCairoの描画を完了させ、書き込み後に変更を通知する手順です。座標がずれた画像ではCairoにコピーを任せます。[boxrigのCairo描画器](../../../src/pangocairo/renderer.c)・[画素と描画経路の試験](../../../tests/pangocairo/test_paint_updates.c)・[Cairoの画像データへのアクセス](https://www.cairographics.org/manual/cairo-Image-Surfaces.html#cairo-image-surface-get-data)

| GTK3 Cairoのgrid | 変更前 | 変更後 |
| --- | ---: | ---: |
| 同じ24更新の下地コピーに使ったCairoの描画呼び出し | 122,289回 | 0回 |
| 各更新を1回ずつ描いたときの描画CPU時間、6組の中央値 | 15.68 ms/更新 | 14.63 ms/更新 |
| ウィンドウへの固定入力1更新あたりの端末CPU時間、7組の中央値 | 22.76 ms | 21.17 ms |
| 同じウィンドウでの画素反映p95、7組の中央値 | 45.78 ms | 46.81 ms |
| 実際のgridデモの実行時間、3組の中央値 | 2.77秒 | 2.88秒 |

固定入力で一時画像を作った回数は12万2,289回です。変更前は各画像に1回の描画で下地を写し、変更後は全件を直接コピーできました。描画だけを測った6組のうち5組でCPU時間が減り、全24画面が変更前と一致しました。ウィンドウ内の各区間を計測した別試行では、変更後の描画予約から描画開始までの中央値が0.05 ms、描画CPU時間の平均が18.21 ms、表示用の画像を用意してからX11の画素を確認するまでの中央値が6.55 msでした。[固定入力のCairo描画計測](../../../tests/performance/cairo_grid_replay.c)・[ウィンドウへの反映までの区間計測](../../../tests/performance/image_phase_probe.c)

Cairoの内部も、実行時と同じビルドのデバッグシンボルで調べました。同じgridを4回再生する計測を各版で2回行い、ユーザーモードのCPUを毎秒499回サンプリングしています。下位の呼び出しを含む `_cairo_surface_paint` の割合は10.27〜10.63%から4.50〜5.77%に減りました。変更後にも字形を合成する `pixman_composite_glyphs` が9.47〜9.66%を占めています。割合の分母は、入力や画素ハッシュの計算も含む再生プロセス全体です。各関数の集計は `artifacts/perf-step24/cairo-samples/*-symbols.txt` にあります。

## 短い間隔で画面を読んだときの表示遅延

btopとgridで観測したp95の差が小さいため、別の時間帯に、観測器が画面の再読み取りまで待つ時間を5 msから1 msにして各5組を測りました。各組で同じ24更新を再生し、どちらの版を先に動かすかは組ごとに入れ替えています。表は各試行のp95の中央値です。

| 固定入力と描画構成 | 変更前 | 変更後 | 変更後が短かった組 |
| --- | ---: | ---: | ---: |
| btop、X11 OpenGL ES | 25.60 ms | 21.65 ms | 5組中4組 |
| btop、GTK3 OpenGL | 12.67 ms | 14.77 ms | 5組中3組 |
| grid、GTK3 Cairo | 41.95 ms | 34.25 ms | 5組中4組 |

GTK3 OpenGLのbtopは、5組それぞれの差を取ると中央値で0.31 ms短く、試行別の差は9.38 msの短縮から9.36 msの増加まで広がりました。X11のbtopとGTK3 Cairoのgridも、5 ms間隔の7組とは中央値の変化が逆向きです。どちらの間隔で測っても画素の反映を一貫して速める効果は確認できませんでした。すべての試行の数値は `artifacts/perf-step24/fine-summary.json`、1 msの観測器は同じディレクトリの `fine-tools/` にあります。

## 再生と確認

ローカルの `artifacts/perf-step24/summary.json` に試行別の数値、同じディレクトリの `comparison/` と `fine/` に動画・画素・時刻を保存しています。各試行の画素画像は `frames.tar.zst` にまとめ、圧縮前の画像と照合しました。固定入力は前回と同じ `artifacts/perf-live-20261120-jpbBTX/inputs/` の3組です。実機で画素を観測した62試行と追加の30試行では、毎回24更新すべてが順に現れました。連続読み取りの間に画面が変わった271組542枚のうち、前後の画面が混在したのは77枚です。各画像に境界が1本あり、前後どちらにも属さない画素はありませんでした。

保存済み入力の再生と単発キーの確認は、リポジトリのルートから次のように実行できます。画素計測には実際のX11セッションと新しい出力先を使います。

```bash

BOXRIG_VERIFY_STABLE_READBACK=1 BOXRIG_REPLAY_PERIOD_MS=100 \

  bash tests/performance/run_frame_latency.sh build/boxrig_term/x11/boxrig_term \
  opengl 45 118 "$out/keys" x11
```

## 回帰試験

入力パーサーは、制御文字列の分割、容量上限、出力先が一部だけを受け取ったときの再試行を含めて検証しました。X11では連続出力の描画期限と単発出力の即時描画、OpenGLでは混在する書体や双方向の文字、4K画面のキャッシュを試験しています。Cairoで半透明の下地にまたがる字形を部分更新した画素は、全面描画と一致しました。さらに、描画先を横に1画素ずらした場合と縦横に2倍に拡大した場合のgridを各24更新再生しました。どちらも下地のコピーは全122,289回が従来のCairo描画を通り、すべての画素ハッシュが同じ変換をかけた基準版と一致しています。各試行は `artifacts/perf-step24/cairo-transform/` にあります。

全体テストの `make -k -j1 test` は8時05分から9時12分まで実行し、次の2項目で失敗して終了コード2でした。入力の再生、画面の更新時刻、連続描画、Cairoの部分更新の試験は通っています。実行順と出力は `artifacts/perf-step24/full-test.log` にあります。

- `test-native-blink` は、Wineの64ビット版で拡大したヘブライ文字上にカーソルを重ねたとき、暗い文字画素を検出できませんでした。判定値 `fill=420, ink=0, darkest=765` は基準版での失敗と一致します。[画素の判定](../../../tests/blink_renderer_fixture.c#L623)・[基準版の試験結果](step23-notcurses-btop-measurements.md#テスト結果)
- `test-win32-core-artifacts` は、Win32用の画像テスト自体が使う `msvcrt.dll` の `strstr` が許可リストにないため失敗しました。基準版のパーサーと画像テストで32・64ビットの実行ファイルを再生成しても同じ結果です。端末とカスタムUIの監査は両アーキテクチャで通っています。[画像テストの該当箇所](../../../tests/test_graphics.c#L3300)・[監査スクリプト](../../../tests/win32/check_core_pe.sh)

この失敗でMakeが開始しなかった全体テスト本体の153コマンドと、点滅関連の残り9コマンドを順に実行しました。156コマンドは成功し、6コマンドは次の画素判定と監査で失敗しました。再実行の出力は `artifacts/perf-step24/main-test.log` にあります。

| 追加実行で失敗した項目 | 対象 | 基準版との照合 |
| --- | --- | --- |
| 公開APIの監査 | GTK3 | 描画を実行する公開関数 `boxrig_gtk3_terminal_widget_dispatch_frame` が監査表に未登録。基準版のヘッダーと監査プログラムで同じ関数を検出 |
| ブロック文字の描画モード切り替え後の色 | Wineの32・64ビット版 | 基準版の共通描画試験を再ビルドし、両方で同じRGB判定が失敗 |
| マウスボタンを押したまま拡大したウィンドウの右端と下端の描画 | Wineの32・64ビット版の終了検査用サンプル | 基準版でも、同じ寸法で拡大領域の画素を確認できず |
| 拡大したヘブライ文字上のカーソル | Wineの32ビット版 | 基準版で再ビルドしても64ビット版と同じ判定値で失敗 |

公開API監査、DLLインポートとカーソル、ブロック文字、リサイズの基準版での再現記録は、順に `baseline-contract/`、`baseline-pe/`、`baseline-fixture/`、`baseline-shutdown/` に保存しました。
