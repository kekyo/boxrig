# plan25 スクロール履歴の選択式圧縮

作成日 2026年11月20日。基準版は`52c39f121cf812d0e814a9ba31e73fe9004e1290`。

## 目的と対象

端末のビューポートは、ユーザーが今見ている範囲です。通常の出力画面（primary）の上端から押し出された行は、スクロール履歴に入ります。画面外の履歴を読むのは、主に過去の出力を表示したり検索したりするときです。そこで画面外の履歴を可逆圧縮し、同じ行数を少ないメモリで保持します。

ビューポートに入っている履歴行は非圧縮で保持します。新しい出力を書き込むprimaryのセル配列と、全画面アプリなどが使う代替画面（alternate）のセル配列も常に非圧縮です。画像本体は既存の画像管理に任せます。

## 端末ごとに選べる3方式

| 設定値（識別子は案） | 保存方式 |
| --- | --- |
| `BOXRIG_SCROLLBACK_COMPRESSION_NONE`（値0、既定） | 無圧縮。現行のセル配列を保持する。圧縮器と展開領域は確保しない。 |
| `BOXRIG_SCROLLBACK_COMPRESSION_PACKED` | 独自形式。行内で繰り返す属性をまとめ、本文と使用列を保存する。 |
| `BOXRIG_SCROLLBACK_COMPRESSION_DEFLATE_LEVEL_1` | 独自形式の複数行を1組（ブロック）にまとめ、同梱のzlibでDEFLATEレベル1を適用する。 |

既存の生成設定`boxrig_terminal_config`のサイズを保ち、生成直後から次のAPIで方式を選べるようにします。型名と関数名は案です。

```c
boxrig_status boxrig_terminal_set_scrollback_compression(
    boxrig_terminal *terminal, boxrig_scrollback_compression mode);

boxrig_scrollback_compression boxrig_terminal_scrollback_compression(
    const boxrig_terminal *terminal);
```

設定の変更は保持済みの履歴にも適用します。変換先を用意できた時点で切り替え、無圧縮に戻したときは展開用の作業領域も解放します。メモリ不足時の戻り値は`BOXRIG_STATUS_OUT_OF_MEMORY`です。旧設定と履歴はそのまま保持します。無効な値には`BOXRIG_STATUS_INVALID_ARGUMENT`を返し、同じ方式の再指定は何もせず成功とします。取得APIで分かるのは端末に設定した方式です。

履歴容量`scrollback_capacity`の単位は、折り返し後の物理行です。上限に達したときは古い物理行から破棄し、容量0では履歴を作りません。方式だけを変更したときは、表示位置、再描画の対象範囲、テキストの更新番号を維持します。[履歴容量の仕様](../scrollbars.md#履歴容量を変更する)・[端末の公開API](../../../include/boxrig/terminal.h)

## 現行の保持量と予備計測

現行のboxrigは、履歴に1行入るたびに全列分のセル配列を確保します。Linux x86-64では1セルが64バイトで、うち色や文字属性が36バイトです。既定の80列で1万行を保持すると、セル配列に48.8 MiBかかります。行の管理表には、容量1行あたり88バイト、既定容量で約0.84 MiBを別に確保します。[セルと履歴行の定義](../../../src/core/terminal_internal.h#L21)・[履歴行を追加する処理](../../../src/core/screen.c#L2134)

基準版の`src/core/screen.c`を80列24行の端末に入力し、改行はCRLFに揃えました。履歴に残った4,496物理行は、すべて既定属性のASCII本文と行末の未使用セルで表現できました。試作では1行を種別1バイト、本文長1バイト、本文の順に記録しています。出力された空白文字も本文に含みます。汎用圧縮の比較では最大32行ずつ141ブロックに分け、展開した全ブロックの内容が元と一致することを確認しました。

| 保存方式 | 履歴4,496行のデータ量 |
| --- | ---: |
| 現行のセル配列 | 21.95 MiB |
| 独自形式のASCII行 | 148.6 KiB |
| 同じ行データにDEFLATEレベル1を適用 | 60.9 KiB |

検討時の比較値はLZ4が81.5 KiB、Zstandardレベル1が63.2 KiBでした。この入力では独自形式だけで約21.8 MiB減り、DEFLATEでさらに87.7 KiB減りました。測ったのは行データの符号量です。実装後は行管理表や展開領域を含む常駐メモリと操作時間を測ります。[計測入力](../../../src/core/screen.c)・[zlibの公式マニュアル](https://www.zlib.net/manual.html#Basic)・[同梱版のAPIコメント](../../../deps/zlib/zlib.h)

## 行の保存と読み出し

独自形式には、同じ色・属性が続く区間を開始列と長さで表すランレングス圧縮（RLE）を使います。行末で省略できるのは、既定属性の未使用セルだけです。実際に出力された空白と、背景色や保護属性のある空セルは区別して保存します。UTF-8本文を区切る単位は、結合文字や絵文字をひとまとまりとして扱う書記素です。書記素の境界、全角文字の列幅と後続セル、ハイパーリンク（OSC 8）の識別子を記録します。画像の位置を示す文字（プレースホルダー）とその属性も復元できます。リンクの参照を解放するのは、その参照を持つ履歴行を破棄するときです。[セルの属性と空セルの判定](../../../src/core/screen.c#L310)・[リンクの参照管理](../../../src/core/screen.c#L112)

折り返しの有無、論理行の識別子、行内の列位置と更新番号は管理表に残します。行数や行の対応を調べるだけなら、セルの展開は不要です。検索や選択範囲のコピーでは対象の行を順に読みます。幅を変えるときは新しい列幅に折り返し、確定した画面外の行から圧縮します。高さだけの変更なら、既存の履歴を引き継げるため、確定済みの行の再圧縮は不要です。[論理行とセルの参照](../../../src/core/text.c#L455)・[リサイズ時の履歴再利用](../../../src/core/screen.c#L1544)

DEFLATEのブロックにまとめるのは画面外の履歴行だけです。各ブロックを独立して展開できるようにし、試作の32行を出発点に展開後のバイト数にも上限を設けます。1行で上限を超える場合は、独自形式か現行形式での保持が可能です。通常出力中に圧縮用メモリが不足した場合や圧縮すると大きくなる場合も、元の行を保持します。ブロックの途中に履歴容量の境界が来ても、行の破棄とリンクの参照管理は物理行単位です。[coreに組み込むzlib](../../../Makefile#L290)

### 表示中の行と借用ポインター

スクロールでは、これから表示する履歴行を先に連続したセル配列へ展開してから、表示位置を切り替えます。表示中はその配列を保持します。履歴を見ている間に新しい出力が届いた場合も、同じ行が表示に残る限り再展開は不要です。履歴上限で先頭行が消えた場合は、現在の規則に従って表示位置を補正します。画像のプレースホルダーを列順に読む処理にも、展開済みの行を渡します。[ビューポートの行の対応](../../../src/core/screen.c#L637)・[画像のプレースホルダーの走査](../../../src/core/graphics_protocol.c#L3473)

画面外のセルを取得する`boxrig_terminal_get_text_fragment_cell()`では、返した文字列を次の端末変更まで参照できます。独自形式での参照先は、履歴行が所有するUTF-8本文です。DEFLATEでも、別の行を展開した後まで参照できる領域を用意します。一案は、ASCIIに固定の文字表を使い、他の書記素をブロックごとに重複を除いて保持する方法です。セル取得時にはブロックから書記素を特定し、対応する文字列のアドレスを返します。この領域の費用も圧縮後のメモリ量に含めます。[セルの参照寿命と戻り値](../../../include/boxrig/terminal.h#L2183)

表示用のセル配列は圧縮の有効化時やリサイズ時に用意し、DEFLATEを選んだ場合はzlibの展開作業領域も予約します。セル取得と表示位置変更の呼び出しでは予約済みの領域を使うため、既存の戻り値の契約のまま履歴を読めます。

## 実装の段階と完了条件

### 25.1 無圧縮の動作と保持量を再現する

既存のCテストドライバーで、短いログ、色付きログ、日本語と絵文字、複数行に折り返す長い出力を再生します。観測するのは、履歴が満杯になった状態と、履歴を表示したまま出力を続けたときの動作です。現行の無圧縮でセル、表示位置、コピー・検索結果を再現し、保持量と処理時間の基準値を記録した時点でこの段階を完了します。[履歴移送のテスト](../../../tests/test_history_transfer.c)・[既存のテキスト負荷計測](../text-workload-measurements.md)

### 25.2 独自形式で履歴を保存し、表示に戻す

ドライバーから独自形式を選び、通常の受信、スクロール、検索、リサイズを通して検証します。最初の試験は、同じログを保存したときに履歴の保持量が無圧縮を下回ることです。現行実装での失敗を確認してから、履歴行を圧縮して読み出す処理を加えます。完了条件は、無圧縮とセル内容が一致し、別の履歴行を読んだ後も取得済みの文字列を参照できることです。表示範囲を動かさずに再描画を繰り返したときの展開回数は0とします。

### 25.3 DEFLATEレベル1でブロックを保存し、個別に展開する

同じドライバーにDEFLATEを加え、隣の行、離れたブロック、最古の履歴の順に移動します。ブロックをまたぐ選択、検索の中断と再開、長い書記素、圧縮用メモリの不足も試験の対象です。どのブロックから読んでも独自形式と同じ結果が得られ、先に取得したセルの文字列を引き続き参照できることを確かめます。1画面の移動で展開するのは、移動先の表示に必要なブロックだけです。描画・セル取得に伴う履歴用メモリの追加確保が0であることも完了条件とします。

### 25.4 公開APIで方式を切り替え、3方式を比較する

この段階で公開するのは、方式の設定・取得の2関数です。公開ヘッダー、共有ライブラリの公開シンボル、API検査に加えます。初期値は無圧縮とし、3方式の全組み合わせについて、履歴を保持したまま切り替えられるかを公開APIから検証します。再指定、無効な値、容量0、変換時のメモリ不足も試験の対象です。切り替え前後で表示位置、選択範囲、画像配置、行の更新番号を照合し、失敗時には以前の設定と借用ポインターも確かめます。[共有ライブラリの公開シンボル](../../../packaging/linux/boxrig.map)・[公開API検査](../../../tests/frontend_public_contracts.def)

計画全体の完了条件は、3方式で既存APIの結果が一致し、同じログで履歴を満杯にしたときに独自形式とDEFLATEの常駐メモリがそれぞれ無圧縮を下回ることです。方式ごとに連続出力の処理速度、スクロール時間の95パーセンタイル、列幅変更時のピークメモリを記録します。全体テスト`make test`を実行し、基準版との結果も照合します。

## 実装と計測結果

公開した型名、定数名、関数名は25.4までの案と同じです。独自形式では印字可能なASCIIを1セル1バイトで記録します。属性が変わった列にだけ新しい属性を書き、既定属性の未使用セルが行末に続く場合はその部分を省きます。DEFLATEでは最大32行をまとめ、圧縮前の行データと参照用の文字列を合わせて64 KiBまでとしました。同じブロックで複数の行が同じ非ASCII文字列を持つ場合は、その文字列を共有します。[履歴の符号化と展開](../../../src/core/history.c)

表示用のセル配列と画面外を読む作業行は、方式の設定時に確保します。DEFLATEで受信中の端数の行は、ブロックがそろうか入力が終了するまで独自形式です。方式を変更した時点で表示中だった非圧縮の行は、画面外に出た後の入力処理で圧縮します。表示位置だけを動かすときは追加のメモリ確保がありません。

Linux x86-64で80列24行の端末に短いログ、色付きログ、日本語と絵文字、折り返す長いログを順に入力しました。履歴が1万物理行に達した時点でプロセスの常駐メモリを読みました。1回のスクロール計測には、履歴内を移動して表示中の24行から先頭セルを1つずつ読む時間を含みます。移動先を変えながら201回測り、所要時間の95パーセンタイルを求めました。列幅を80から64に変更した直後までの最大常駐メモリも記録しました。[計測ドライバー](../../../tests/performance/scrollback_compression.c)

25.1で圧縮の実装前に1回測った基準値は、常駐メモリ53,692 KiB、入力速度147,827行/秒、スクロール時間0.99 µs、列幅変更時までの最大常駐メモリ95,596 KiBでした。次の表は、実装後に各方式を別プロセスで5回ずつ測った中央値です。

| 方式 | 履歴満杯時の常駐メモリ | 入力ログ行数/秒 | スクロール時間の95パーセンタイル | 列幅変更時までの最大常駐メモリ |
| --- | ---: | ---: | ---: | ---: |
| 無圧縮 | 53,720 KiB | 162,820 | 1.02 µs | 95,624 KiB |
| 独自形式 | 4,632 KiB | 158,795 | 21.13 µs | 8,180 KiB |
| DEFLATEレベル1 | 4,116 KiB | 144,425 | 26.98 µs | 7,528 KiB |

この入力での常駐メモリ削減率は、無圧縮を基準に独自形式が91.4%、DEFLATEが92.3%でした。201回の移動で読んだセルの検査値、リサイズ後の検索結果、該当範囲をコピーした文字列は3方式で一致しました。計測を再現するには次を実行します。

```sh

for mode in none packed deflate; do
    build/tests/measure_scrollback_compression "$mode"
```

## 動作の検証

履歴に結合文字、全角文字、色、保護属性、ハイパーリンクを混在させ、無圧縮の端末とセル単位で照合しました。試した組み合わせは、3方式の全9通りと、履歴表示中・代替画面表示中の2つの状態です。変換時のメモリ確保を先頭から1回ずつ失敗させても、旧設定、借用済みの文字列、画面の内容、行の更新番号を引き続き参照できました。セル取得と表示位置の移動に伴う追加確保は0回です。別のブロックを読んでから表示中の全セルを4回読み直しても、DEFLATEの追加展開は0回でした。[圧縮方式と参照寿命の試験](../../../tests/test_scrollback_compression.c)

検索を1セルまたは1バイト処理するごとに中断し、別の履歴行を読んだり方式を切り替えたりしてから再開しました。検索対象はブロックの境界をまたぎ、結合文字、字間の空白、改行を含む文字列です。一致箇所をコピーして得た文字列は期待どおりでした。履歴を含む矩形選択のコピーと、画像の位置を示す文字から求めた表示座標も3方式で一致しました。[選択とコピーの試験](../../../tests/test_selection_history.c)・[画像配置の試験](../../../tests/test_graphics.c)

Linuxの共有ライブラリにリンクしたCプログラムから両方の公開関数を呼び、方式を切り替えました。端末ヘッダーにある100宣言はすべて公開API検査に適合しています。履歴移送、リサイズ、テキスト同期、圧縮の各試験は、core本体にAddressSanitizerとUndefinedBehaviorSanitizerを有効にしたビルドでも成功しました。
