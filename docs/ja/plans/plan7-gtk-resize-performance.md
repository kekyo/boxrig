# plan7: GTKのOpenGL描画とウィンドウサイズ変更の改善

## 目的と開始点

boxrigを使う端末で、手動のサイズ変更、最大化、デスクトップへのスナップにかかる時間を減らす。現在のPCでOpenGLの待機が長くなる条件を調べ、boxrigから変更できる描画方法を比較する。効果と正しさを確認した方式を実装する。

対象は`~/Projects/boxrig/`で、開始時のHEADは`bba72066329e75f9e8e2adf180a041ad31911477`である。開始時の作業ツリーに変更はなかった。作業ブランチは`feature/gtk-resize-performance`とし、mainへのマージは行わない。依存コードとelder-termsのソースは変更しない。

前回の測定は、GNOMEのX11セッション、NVIDIA RTX 3090、ドライバー615.71.09で行った。各操作8回の中央値では、elder-termsの最大化で端末内プロセスへ最終サイズが届くまで356ms、左スナップでは371msだった。Cairo指定ではそれぞれ125ms、134msに短縮した。boxrigの公式GTK3サンプルでも通常のサイズ変更に約110msかかっている。

前回のデータは`~/Projects/elder-terms/artifacts/resize-investigation-20261022/`にある。この計画では、現在のビルドで基準値を取り直す。過去の測定値だけで改善を判定しない。

## 分けて測る処理

端末の行・桁数をグリッドと呼ぶ。ウィンドウの画素寸法が変わると、GTKは子ウィジェットへ新しい寸法を割り当てる。boxrigは、その寸法でプレビューを描画した後にグリッド変更をアプリへ渡す。アプリが端末と通信先を更新し、完了を返すと、新しいグリッドを描画する。

前回は、OpenGL画像をGTKへ渡す`gdk_cairo_draw_from_gl`に中央値23ms、`gdk_window_end_draw_frame`に21msかかった。各呼び出しのスレッドCPU時間は約1msだった。ただし、GPU、ドライバー、Xサーバー、画面合成のどこで待っているかは分かっていない。

現行のGTK3とGTK4は、画素寸法が変わるたびに保持用の描画先とOpenGLレンダラーを作り直す。このときの資源生成、文字の再描画、画像転送、コンテキスト切り替え、GTKへの合成、グリッド通知を分けて観測する。

GTKの契約は[GL画像の描画](https://docs.gtk.org/gdk3/func.cairo_draw_from_gl.html)、[描画終了](https://docs.gtk.org/gdk3/method.Window.end_draw_frame.html)、[GLArea](https://docs.gtk.org/gtk3/class.GLArea.html)の公式文書とAPIコメントで確認する。新たに使うOpenGL APIについても公式仕様と宣言・コメントを読む。

## ステップ1: 再現できる測定と原因の分離

現行boxrigのGTK3サンプルと、端末処理を持たない小さなGTK/OpenGLドライバーを動かす。必要に応じてGTKを介さないOpenGL処理も測り、どの処理から待機が長くなるかを調べる。測定用ドライバーは、それだけでビルド・実行できる単位にする。

同じ画素寸法、フォント、本文、履歴量で通常の拡大・縮小、最大化、スナップ、連続ドラッグを測る。起動と初回描画を測定区間から外す。単調時計による経過時間とスレッドCPU時間を記録し、必要なら公開APIの呼び出しやシステムコールを追加で観測する。測定中に全体テストや別のビルドを重ねない。

測定結果には実行コマンド、ビルド、描画方式、GPU情報、試行数、中央値、上位側の分位点を残す。端末へのサイズ通知、GTKへの描画提出、録画上の表示を区別し、描画提出を物理的な表示完了とは扱わない。既存のユーザー端末と設定は変更しない。

この段階の完了条件は、現在の遅延を再現し、boxrig固有の費用とGTK/OpenGL連携で生じる費用を区別できることである。観測できない範囲も記録する。

## ステップ2: 複数方式の比較

ステップ1の観測に基づき、次の候補から原因に対応する方式を個別に試す。環境側のOpenGL処理にも待機が見られる場合は、少なくとも異なる2方式を実測する。

| 候補 | 確認する内容 |
| --- | --- |
| 描画先だけの更新 | レンダラー、文字や画像のキャッシュ、シェーダーを保持し、寸法に依存するテクスチャとFBOを更新できるか |
| テクスチャの割り当て方 | 毎回の確保、容量の再利用、更新範囲の違いで、待機とメモリ使用がどう変わるか |
| 命令の発行時点と同期 | GTKへ渡す前の命令提出やコンテキスト間の受け渡しで、同期待ちを減らせるか |
| 転送と描画の集約 | テクスチャ更新や描画命令をまとめ、不要な全体転送や状態照会を減らせるか |
| サイズ変更中の描画 | 既存の安全なプレビューとグリッド通知の契約を保ち、不要な資源再生成や描画を避けられるか |

候補ごとに変更点を分け、同じ測定を行う。複数の変更を重ねた後に原因が分かった場合は、不要な変更を戻す。ドライバー全体の設定変更、待機を隠す固定タイマー、無条件のCairo切り替えを改善の代用にしない。共有コンテキストや半透明描画などの成立条件も調べる。

この段階の完了条件は、採用する方式と不採用の方式を測定結果で説明できることである。必要な設計変更が当初の候補から外れる場合は、先にこの計画を更新する。

## ステップ3: 採用方式をテスト付きで実装

修正前に問題を再現するテストを追加し、失敗を確認する。時間のしきい値だけに頼らず、描画結果、端末へ渡る最終寸法、再利用される資源の働き、失敗時に保持する画像などを実行から検証する。その後に修正し、対象テストの成功を確認してコミットする。

描画先の更新では、拡大と縮小、連続更新、同寸法、世代の古い要求、確保や描画の失敗、コンテキストの終了を確認する。透明度、色空間、選択、部分更新、文字・画像キャッシュの正しさを維持する。GTK3とGTK4で共有する処理を変えた場合は両方を検証する。

ネイティブ描画前にグリッドを通知するなど、公開契約を変える必要が生じた場合は、実装前に契約と計画の整合を確認する。外部依存コードは変更しない。使われなくなったコードは削除し、既存コメントは変更後の内容に合わせる。

この段階の完了条件は、修正前の失敗と修正後の成功を確認し、関連する描画・サイズ変更テストとドライバーが実行できることである。

## ステップ4: 実機での改善と全体の検証

変更前後のビルドを同じ条件で交互に動かし、通常のサイズ変更、最大化、スナップ、連続ドラッグを比較する。各操作を複数回測り、外れ値とばらつきも残す。少量の本文と1万行の履歴を分けて確認する。必要ならelder-termsへ作業中の共有ライブラリを指定し、アプリやサブモジュールを変更せずに効果を確認する。

録画でサイズ変更中と完了後の表示を検査する。テスト用の基準画像を追加・変更した場合は目視する。公開APIや利用上の条件が変わる場合は、日本語文書を原本として英語文書も更新する。

最後に全体テストを実行する。既存の全コマンドを収集する必要があれば`make -k -i -j1 test`を使うが、`-i`の終了コード0を成功の根拠にしない。各失敗とスキップをログから調べ、今回の変更に起因する問題を解消する。ビルド警告も原因を確認して対処する。

最終的な完了条件は、原因を説明できること、複数候補を比較した記録があること、採用方式で実機のサイズ変更が改善すること、描画とサイズ契約の回帰がないこと、全体テストを実施して結果を説明できること、変更を適切な単位でコミットしていることとする。
