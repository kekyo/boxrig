# step22 等倍画像の合成とnotcurses xrayの再計測

実施日 2026年11月19日〜20日

GTK3 Cairoでnotcursesの動画デモxrayを描くと、plan21では画像合成に1枚あたり12.62ミリ秒かかり、描画CPU時間の約85%を占めました。今回の基準はplan21の完了時点`e02f5ae`、変更版は`d5508f4`です。完了条件を、同じ入力で合成CPU時間を短縮し、途中の画面から最後の画像消去まで全画素が基準版と一致することとしました。[plan21の計測](plan21-notcurses-btop-rendering-performance.md#214-xrayの復号と描画)

## 等倍画像の合成

観測した23画像は、いずれも826×464画素で、表示寸法も同じでした。透明な画素が7,873,471、不透明な画素が941,601あり、その中間の透明度を持つ画素はありませんでした。従来は各出力画素に対して参照位置を計算し、隣接する4画素から色を補間していました。等倍なら、出力画素の中心は元画像の画素の中心に重なります。

切り抜き後の元画像と表示寸法が両軸で等しい場合、更新範囲に重なる元画素を直接読むようにしました。画像を前面に重ねると、不透明画素はそのまま書き込まれ、透明画素の下には描画先の色が残ります。半透明画素の合成式は従来どおりです。画像が背面にあるときは、描画先の画素を前面として扱います。拡大・縮小には従来の補間を使います。[ソフトウェア描画の画像合成](../../../src/ui/image.c)

試験では、元画像を切り抜き、負の位置に置いて、画面の一部だけを更新しました。前面と背面で合計8画素を処理したとき、透明度を使う一般の合成処理は基準版で8回、変更版で3回でした。透明な画素も処理画素数に含み、更新範囲外と行末の余白を含めて期待した画素が得られました。基準版との別の照合では、等倍・拡大縮小・片軸だけの拡縮・空の範囲など48,000件で、全出力画素、処理画素数、戻り値が一致しました。[合成の回帰試験](../../../tests/test_image_compositor.c)

## 同じ画像列を表示したときの差

plan21で記録した疑似端末（PTY）への入力875,786,498バイトを使いました。404画像を事前に送り、続く23画像と消去の計24更新を、118列45行の実ウィンドウで確認しました。機器はCore i9-12900KSとGeForce RTX 3090、描画構成はX11上のGTK3 Cairoです。両版を交互に3回ずつ実行しました。表は試行の中央値で、括弧内は最小値と最大値です。p95は、各試行で測った遅延の95パーセンタイルです。

| 指標 | 基準版 | 変更版 |
| --- | ---: | ---: |
| 合成CPU時間（ミリ秒／画像） | 12.50（11.93〜13.58） | 0.21（0.19〜0.22） |
| 描画全体のCPU時間（ミリ秒／画像） | 14.61（13.91〜15.98） | 2.44（2.11〜2.58） |
| 入力から画素反映までのp95（ミリ秒） | 38.25（32.93〜44.48） | 21.43（18.50〜22.78） |

合成と描画のCPU時間は、最初の観測と最後の消去を外し、22画像で平均しました。各試行の合成は916回、処理した画素は8,431,808個です。画素反映のp95には通常の実行ファイルを使い、入力開始からX11ウィンドウで画素を確認するまでの23件を用いました。表の3指標は3組すべてで短縮しています。区間計測を組み込んだ別試行では、表示予約から画素確認までのp95の中央値は26.34ミリ秒と15.96ミリ秒でした。3組中1組ではこの時間が延びました。[画面観測の手順](../../../tests/performance/run_frame_latency.sh)

各組で24画面の端末領域826×630画素がすべて一致しました。別の録画検証では427画像の復号結果と配置、23画像中の不透明な938,854画素を元データと照合しました。最後の画像を消すと両版とも35,461画素が変化し、残った画像と配置は0件です。[復号結果と画面の照合](../../../tests/performance/check_xray_replay.mjs)・[端末領域の全画素比較](../../../tests/performance/compare_capture_pixels.mjs)

## 実際のxray

`notcurses-demo -c -d 0.03 x`を同じ端末寸法で3組実行しました。notcursesは動画の進行に合わせて送信フレームを選ぶため、各版が送る内容も枚数も試行ごとに変わります。

| 指標 | 基準版 | 変更版 |
| --- | ---: | ---: |
| notcursesが送ったフレーム数 | 602（537〜682） | 849（812〜869） |
| 送信フレーム毎秒 | 38.8（34.6〜44.1） | 57.0（52.5〜59.4） |
| 端末プロセスのCPU時間（秒） | 13.44（13.43〜14.06） | 7.05（6.82〜7.27） |
| 送信1フレームあたりの端末CPU時間（ミリ秒） | 22.31（20.62〜25.03） | 8.37（8.30〜8.40） |

両版とも3試行すべてでデモと端末が正常終了しました。送信完了時間の中央値は15.50秒と15.24秒、ホスト全体のCPU使用率は30.9〜34.0%でした。実デモの表示フレーム数は未計測です。最初の起動ではデモ開始前にセル寸法の取得に失敗したため、この起動を除外し、寸法取得時のシステムコールを記録して両版を再計測しました。[実アプリの計測スクリプト](../../../tests/performance/run_notcurses_evaluation.sh)

6試行で記録した端末への入力は、`artifacts/step22-xray-compositing/live/`以下の各試行の`output.bin.zst`に保存しています。展開後のデータが元の入力と一致することをSHA-256で確認しました。同じ記録の一覧は`artifacts/step22-xray-compositing/live-captures.sha256`にあります。

## btopの対照試験

画像を使わないbtopを100ミリ秒間隔で動かすと、基準版・変更版の各3試行とも12秒間に119更新を受信しました。保存した同じ24更新の比較は6組です。下表のCPU時間には端末プロセスの全スレッドを含みます。

| 指標 | 基準版 | 変更版 |
| --- | ---: | ---: |
| 実際のbtopで受信1更新あたりの端末CPU時間（ミリ秒） | 8.15（8.07〜8.24） | 8.32（7.90〜8.57） |
| 保存入力の1更新あたりの端末CPU時間（ミリ秒） | 8.22（6.34〜10.06） | 9.50（7.51〜10.98） |
| 同じ保存入力の画素反映p95（ミリ秒） | 24.93（10.40〜34.84） | 24.36（22.52〜25.22） |

保存入力では端末CPU時間が6組中5組で増加しました。そこで、端末と子プロセスを同じ高性能コアの論理CPU 8に固定し、基準版、同じ基準版の再実行、変更版の実行順6通りを1回ずつ試しました。1更新あたりの端末CPU時間の中央値は順に9.07、9.23、9.49ミリ秒でした。変更版は最初の基準版との比較で6組とも増え、同一バイナリを再実行した基準版との比較では4組で増えました。いずれも24更新の端末領域は全画素が一致しています。

画像処理の呼び出しを記録すると、btopの24更新では両版とも画像合成が0回でした。この試行で最初の観測を除く23更新の描画は各23回、描画スレッドのCPU時間は1更新あたり7.89ミリ秒と7.29ミリ秒です。

実行ファイル内の関数配置も調べました。基準版の合成関数の直後に320バイトの余白を設けて再リンクすると、合成関数と余白を除く命令領域911,824バイトが、変更版と同じアドレスで一致します。この比較版を加え、同じ論理CPUで3種類を実行順の全6通りで計測しました。全試行で24画面の画素が一致しています。

| 保存したbtop入力での中央値 | 基準版 | 配置をそろえた基準版 | 変更版 |
| --- | ---: | ---: | ---: |
| 端末CPU時間（ミリ秒／更新） | 11.61 | 10.21 | 11.12 |
| 画素反映のp95（ミリ秒） | 31.14 | 30.51 | 30.93 |

この6組では、変更版のCPU時間は基準版より4組で短く、配置をそろえた基準版より4組で長くなりました。ホスト全体のCPU使用率の中央値も、先のコア固定試験では約19%、この試験では約5%です。btopの端末CPU時間は試験条件によって増減の向きが変わり、原因の特定には至りませんでした。

## 再現と検証

入力を用意する手順と元の記録のSHA-256はplan21に記載しました。次は通常の実行ファイルで画素反映の遅延を測り、区間計測を組み込んだ実行ファイルで復号と合成を確かめる例です。全画像のSHA-256を求める試行はCPU時間の比較から外します。[保存入力の準備](plan21-notcurses-btop-rendering-performance.md#保存入力から比較を再現する)

```sh
input=artifacts/plan21-implementation/xray/preserved-input
out=$(mktemp -d artifacts/step22-replay-XXXXXX)
make notcurses-evaluation-tools build/tests/performance/frame_latency \
  build/boxrig_term/gtk3/boxrig_term_image_work
bash tests/performance/run_frame_latency.sh \
  build/boxrig_term/gtk3/boxrig_term cairo 45 118 "$out/latency" "$input" gtk3
bash tests/performance/run_frame_latency.sh \
  build/boxrig_term/gtk3/boxrig_term_image_work cairo 45 118 "$out/phases" "$input" gtk3
node tests/performance/check_xray_replay.mjs "$input" "$out/phases"
```

全画像を照合するには別の出力先を用意し、再生に`BOXRIG_VERIFY_ALL_IMAGES=1`と`BOXRIG_VERIFY_STABLE_READBACK=1`、その後の照合に`BOXRIG_VERIFY_ALL_IMAGES=1`を指定してください。試行ごとの数値の保存先は`artifacts/step22-xray-compositing/summary.json`です。録画検証の`verify-before/`と`verify-after/`では、連続する2回の画面読み取りに差がありました。該当する基準版の10枚、変更版の4枚は、すべて更新前か更新後の画面全体と一致しています。
