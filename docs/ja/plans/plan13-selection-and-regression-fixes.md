# plan13 通常選択の行末・改行表示と残存不具合の修正

作成日：2026年10月28日

状態：実施中。第1段階を完了し、第2段階の右端改行マーカーと描画系の検証を進めています。第3～6段階は未着手です。

## 目的と対象

通常のマウスドラッグ選択で、本文の後ろの余白が端末の右端まで反転する問題を直します。同時に、改行が選ばれたことを目で確認できるようにします。短い行では本文直後の1セルを改行の表示に使い、余白がない行では右端の細いマーカーで示します。右端のマーカーは、追加の質問に対する利用者の回答で決まった方針です。

もう一つの対象は、[plan12](plan12-recognition-and-osc8-performance.md)の最終試験で残った21件の失敗です。21個の別々の不具合ではなく、GTK4のズーム、Windowsの表示倍率と座標系を合わせるDPI初期化、Windowsの点滅描画という3群に分けて調査・修正します。

基準版は、`feature/plan12`をdevelopへマージした`a2fefa321bdb3852f4e7d9c8faab067c8e18914b`です。計画作成時の`feature/plan13`も同じ版を指しています。作業先は`~/Projects/boxrig/`で、端末の状態を保持するcore、共通UI、各描画系、boxrig_term、試験を対象とします。elder-termsは呼び出し条件の確認と引き渡し先です。本計画で依存の更新やmainへのマージは行いません。

検証は、これまでの指定どおりこのPCを基本とします。LinuxのGUI試験、Windows向けコンパイラーのMinGWでの32・64ビットのビルド、Windowsプログラムの実行環境であるWineでの試験が対象です。Wine固有の制約と判明した場合は、製品へWine専用の回避処理を重ねず、実Windowsで残る確認を分離します。実Windowsの証拠が必要な項目は、それが揃うまで未完了です。

## 用語と選択の仕様

論理行は、自動折り返しで分割される前の本文の1行です。物理行は端末画面に表示される1段で、自動折り返しでは複数の物理行が同じ論理行に属します。本文終端は、実際の文字が占める最後のセルの直後です。文字として出力された空白は本文に含め、未使用・消去済みの余白セルとは区別します。

ここでいう改行は、coreのコピー用テキスト投影が隣接する論理行の間に出す改行コードLF（`\n`）です。投影とは、セルの状態をコピーなどに使うテキストへ変換する処理を指します。受信ストリームにあったLFの履歴を復元する意味ではありません。現在のcoreは初期状態の空行にも論理行の境界を持つため、それらをまたいだコピーにも改行が入ります。この既存の文書上の意味に合わせます。

文字の表示方向は、左から右をLTR、右から左をRTLと呼びます。双方向テキストは、これらの方向を含み、論理的な文字順と表示上の並びが異なることがあるテキストです。

改行セルは、このLFを選ぶための表示上の1セルです。端末の本文へ空白や改行文字を追加する処理ではありません。通常文字と同じく一つの選択単位として扱い、選択範囲にLFが含まれる場合に反転させます。単にマウスポインターが近くにあることだけを表示条件にはしません。

| 操作・条件 | 期待する表示とコピー |
| --- | --- |
| `Ran git diff --check`の最後の`k`まで選ぶ | 本文20セルを反転し、コピーにLFを付けない |
| 同じ行の本文直後にある改行セルまでドラッグする | 本文20セルと改行1セルを反転し、コピーは本文とLFになる |
| 改行セルだけを選ぶ | 1セルだけが反転し、コピーはLFの1バイトになる |
| その行から次の論理行まで選ぶ | 途中の行は本文と改行1セルを表示し、残りの余白を反転しない |
| 明示的な末尾空白が2文字ある | 本文22セルの後ろに改行セルを置き、空白2文字をコピーに残す |
| 末尾を消去制御列で消した | 消去済みセルを本文として扱わず、現在の本文終端へ改行セルを移す |
| 空の論理行の改行を選ぶ | 行頭の1セルを反転し、コピーにLFを1つ入れる |
| 自動折り返しの途中 | 折り返し位置に改行セルを置かず、コピーにもLFを増やさない |
| 文書の最後で次の論理行がない | 存在しないLFを選択・コピーさせず、改行マーカーも出さない |
| 文字が画面幅を使い切っている | LFが選ばれたとき、右端に細いマーカーを表示する。最終文字を改行セルに置き換えない |
| 逆方向へのドラッグ、行末を往復する操作 | 同じ論理範囲なら同じ表示・コピーになり、LFの選択と解除を正確に追従させる |
| 矩形選択 | 指定した矩形と空白の扱いを維持し、通常選択用の改行セル規則を適用しない |

本文より右に余白が続いていても、そこに複数の改行や追加の空白を作りません。通常選択のドラッグでは、余白を本文終端・改行の境界へ正規化します。文字単位の既存の選択方式を保ち、改行セルだけに新しい半セル選択方式を導入しません。

右端の細いマーカーは選択の表示色に従い、表示倍率に応じた幅で描きます。グリッドの列数や折り返し位置は変えません。右端でのヒット判定も改行の選択単位に対応させ、最後の文字だけを選ぶ位置と区別できるようにします。

通常の改行セルは、幅広文字や双方向テキストも含め、論理終端をレイアウト上の位置へ変換して配置します。1セルを置けない場合の代替マーカーは、利用者が選んだ右端の表示に統一します。RTLでもグリッド右端に固定し、その細いヒット領域を同じLFの選択へ対応させます。文字の論理列・表示列の対応自体は維持し、RTLの最後の文字を選ぶ領域と混同させません。

## 現在のコードと再現結果

### 通常選択の余白と改行

[view.c](../../../src/ui/view.c)の`range_logical_interval()`は、行の表示範囲を`fragment.logical_column_offset + view->column_count`までとしています。選択の始点・終点が別の論理行にあると、その物理行は画面幅まで選択表示に含まれます。`boxrig_ui_view_selection_visual_ranges()`の通常選択もこの処理を通ります。矩形選択には独立した経路があります。

塗りつぶしや文字色に使う`selected_logical_interval()`、`boxrig_ui_view_apply_color_state()`、ヒット結果の`BOXRIG_UI_OVERLAY_SELECTION`も確認が必要です。輪郭の矩形だけを短くすると、セルの選択色やヒット判定との不一致が残ります。共通の範囲関数は検索強調にも使われるため、無条件に変更しません。

現在の文字選択は`character_selection_unit()`で、ヒットしたセルの始点・終点をそのまま使います。本文直後の空セルを選んでも、同じ論理行の列範囲になるだけです。[text.c](../../../src/core/text.c)の`project_range()`がLFを出すのは論理行をまたぐ場合なので、その空セルを選んだだけではLFをコピーできません。

調査用の[ドライバー](../../../artifacts/plan13/investigation/selection-probe.c)を、この基準版と製品コードが同じビルド済みライブラリーへリンクしました。[使用した版](../../../artifacts/plan13/investigation/source.json)と[実行ログ](../../../artifacts/plan13/investigation/selection-probe.log)を保存しています。80列の端末で次の結果を確認しました。

| 現在の操作 | 現在の先頭行の反転幅 | 現在のコピー |
| --- | --- | --- |
| 短い行から次行の`next`まで | 80セル | `Ran git diff --check\nnext` |
| 末尾空白2文字を含む行から次行まで | 80セル | 末尾空白2文字を保持した本文、LF、`next` |
| 末尾消去後の行から次行まで | 80セル | 消去した文字を含まない本文、LF、`next` |
| 空行から次行まで | 80セル | `\nnext` |
| 最後の`k`まで | 20セル | 本文20バイト |
| 本文直後の空セルまで | 21セル | 本文20バイトで、LFはない |
| 本文直後の空セルだけ | 1セル | 0バイト |

この結果は公開APIを使った範囲・コピーの確認です。実マウスのドラッグや各描画系の動画による修正後の確認は、実装段階で追加します。

### 既存の本文終端情報を使う方針

coreの`boxrig_text_fragment_metadata`には、既に`projected_end_column`があります。`measure_logical_line()`が実際の文字と明示的な空白を数え、同期時に同じ論理行の各物理片へ保持しています。空行は0、幅広文字はその占有幅までを含みます。この情報をUIへ公開する契約を第一候補にします。

現在の[公開fragment情報](../../../include/boxrig/terminal.h)には終端位置がないため、意味が分かるフィールドまたは限定した照会を追加します。既存の情報を渡すだけで成立する方式を優先し、描画のたびにコピー用スナップショットを作ったり、行末の空白を文字列として削ったりしません。公開定義を変更した段階で、API文書、公開契約監査、配布成果物の検査も実行します。

改行の選択範囲は、「現在の論理行の本文終端から、次の論理行の列0まで」という既存の位置表現を優先します。`project_range()`のLFと対応できるためです。最終行など次の論理行がない場合には、この範囲を作りません。通常のセル情報を矩形選択やリンク判定にも使っているため、改行用のヒット情報がそれらへ混入しない形に分離します。

表示は、選択された本文と選択された改行を区別して導出します。セル内の1セル表示と、右端の細い表示に必要な情報が既存のセル範囲APIだけで表せない場合は、共通UIに改行マーカーの幾何情報を追加します。描画系ごとにLFの有無を独自に推定する設計にはしません。

双方向テキストでは、論理終端が見た目の右端とは限りません。既存の論理列・表示列の対応を使い、改行セルと本文の幅広文字・結合文字を重ねない配置を確認します。選択を縮めたときは、変更前後の表示領域を再描画し、古い余白の反転や右端マーカーを消します。

アクセシビリティには既に`newline_selected`があります。ただし、現在は物理行末を使った判定であり、[accessible.c](../../../src/ui/accessible.c)には行区切り文字を作る独自の処理もあります。コピーのLF、選択された改行の通知、表示上の位置を照合します。アクセシビリティ文書の行区切り表現を、そのまま選択可能な改行の根拠には使いません。

| 対象 | 失敗件数 | 確認済みの事実 | まだ確定していない点 |

件数の根拠は[plan12の最終集計](../../../artifacts/plan12/step7/full-test-audit-summary.json)です。本文投影の計測先、公開APIの監査登録、Windows成果物の実行時依存、隔離ビルドへの依存ファイルのコピーはplan12で修正済みです。これらは回帰確認へ含めますが、未修正の問題として数え直しません。

GTK4は[terminal_widget.c](../../../src/gtk4/terminal_widget.c)の`prepare_zoom_presentation_candidate()`で寸法の一致を確認し、不一致を`BOXRIG_UI_UNAVAILABLE`として返します。[診断結果](../../../artifacts/plan12/step7/gtk4diag2-result.txt)では、変更前の25回目と現行実装の33回目に、候補`40448×23040`と現在の格子`35328×21120`の不一致を記録しています。値は内部の固定小数点座標です。終了後の`BadWindow`は二次的なエラーです。

再現操作はスクロールバーを非表示にして拡大、倍率を戻す、常時表示へ戻す、再び拡大する順です。候補の失効漏れは有力ですが、原因箇所は状態遷移を記録してから決めます。候補とレイアウトの版を結び付け、古い候補を破棄して最新の候補を準備する方式を検討します。利用不能の戻り値だけを成功へ変える処理は、正しい表示を保証しません。

Windowsの起動18件は、[test_win32_sample.c](../../../tests/win32/test_win32_sample.c)の`SetThreadDpiAwarenessContext()`呼び出しで止まります。[plan12の診断6条件](../../../artifacts/plan12/step7/wine-startup-summary.json)は、32・64ビットと不透明度・フォールバック・最初のフレームで、すべて製品起動前の失敗でした。実装時には呼び出し前後のDPIコンテキスト、引数の妥当性、実行環境、マニフェストを記録します。`GetLastError()`は補助情報として扱い、対象APIが保証する範囲を確認します。

[Microsoftの公式文書](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setthreaddpiawarenesscontext)では、戻り値は変更前のコンテキストで、無効な指定の場合はNULLとなり、スレッド設定は更新されません。[現在のコンテキストを読むAPI](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getthreaddpiawarenesscontext)と、利用するSDKヘッダーの宣言・コメントも確認して診断します。計画作成時には、このPCのMinGWの`winuser.h`に宣言があることまで確認済みです。NULLだけから製品のDPI処理が壊れているとは判断しません。

Windows点滅描画は、[blink_renderer_fixture.c](../../../tests/blink_renderer_fixture.c)の塗りつぶしカーソル試験です。`LאבR`の条件で、旧UIを使った[64ビット](../../../artifacts/plan11/verification/wine-blink-old-ui/old-ui-diag.log)・[32ビット](../../../artifacts/plan11/verification/wine-blink-old-ui/i686/old-ui-diag.log)の両方が`fill=420, ink=0, darkest=765`でした。[Win32描画](../../../src/win32/renderer.c)の`draw_filled_cursor()`は背景を塗った後に対象字画を再描画します。下地にも字画がないのか、カーソル内の再描画だけ欠けるのかを先に分けます。

## 段階ごとの実装と完了条件

各段階で振る舞いを検証する試験を用意し、修正前の失敗をRED、修正後の成功をGREENとして確認します。修正の単位ごとに`fix:`、`refactor:`、`chore:`、`doc:`のコミットを作る方針です。診断を増やしただけの状態と、利用者向けの振る舞いを直した状態を区別し、各段階を単独でビルド・実行できるようにします。

### 第1段階 通常選択の本文終端と改行を一致させる

調査ドライバーの短い行、明示的な空白、末尾消去、空行を管理対象の機能試験へ移します。最後の文字まで、改行セルまで、改行だけ、次行までという操作を別々に試し、反転範囲とコピーのバイト列を同じ試験で確認します。改行だけ選んでもコピーが空になる現状をREDとして残します。

本文終端を取得するcoreの契約と、通常選択専用の本文・改行の範囲計算を実装します。ヒット判定、通常選択の始点・終点、セルの色、輪郭、アクセシビリティの選択情報へ同じ規則を適用します。検索と矩形選択の範囲計算を変更する必要がない形を優先します。

まず短い左から右への行を、boxrig_termのCairo表示で操作できるところまで仕上げます。画像比較だけでなく、選択した改行がコピーに入ることを確認します。新しい公開定義があれば、Doxygenの説明と公開契約監査への登録を同じ段階で揃えます。

完了条件：20文字の例が「文字だけなら20セル・LFなし」「改行までなら21セル・LFあり」「改行だけなら1セル・LFのみ」になること。空行の改行も選べ、空白2文字と消去済みセルを区別できること。最小のサンプル操作と対象の単体試験が成功すること。

### 第2段階 右端表示と各描画系の選択を確認する

画面幅を使い切る行に右端の細いマーカーとそのヒット領域を実装します。最後の文字から改行へ進み、戻って改行を解除する操作を動画で記録します。マーカーは文字を移動・再折り返しせず、矩形選択の幅にも影響させません。

同時に、Unicode、折り返し、履歴、逆方向の操作を広げます。既存の[選択試験](../../../tests/test_selection.c)、[履歴の試験](../../../tests/test_selection_history.c)、[描画fixture](../../../tests/selection_renderer_fixture.c)、[表示スタイル動画](../../../tests/run_native_selection_style_video.mjs)へ機能として組み込みます。各描画系が共通UIの結果に従うことを確かめます。

| 検証軸 | 条件 |
| --- | --- |
| 文字と位置 | ASCII、明示的空白、幅広文字、結合文字、絵文字、LTR・RTL・混在 |
| 行境界 | 短い行、空行、連続空行、自動折り返し、幅ぴったり、文書の最終行 |
| 更新 | 文字の追加・消去、リサイズ、再折り返し、フォント変更、主画面・代替画面 |
| 操作 | 順方向・逆方向、行末の往復、改行だけ、選択解除、スクロール・自動スクロール |
| 表示 | 塗り、輪郭、塗りと輪郭、透過度、フォーカス、複数の表示倍率 |
| 回帰 | コピー、矩形選択、単語・行選択、検索、リンク、選択されたセルの色とヒット、アクセシビリティ |

GTK3・GTK4のCairo/OpenGLを先に確認し、共通UIを使うX11・Wayland・Win32にも回帰試験を適用します。動画はドラッグ中、行末到達、次行への移動、逆戻り、解放後の各状態を検証します。固定時間の待機だけに頼らず、入力とフレームの処理完了を確認して判定します。画像マスターを追加する場合は目視確認します。

性能面では履歴0・1,000・10,000行、短い行と長い折り返し行で、選択更新・再描画の区間時間と追加の走査量を比較します。本文終端の取得に全履歴走査や毎フレームのスナップショット生成を追加しないことを確認します。既存の行ID検索にも履歴探索があるため、総時間が厳密に一定になるとは先に約束しません。

完了条件：表の境界条件で本文・改行の表示、コピー、ヒットが一致すること。幅ぴったりの行でも改行の選択が右端の細いマーカーで分かること。古い反転が残らず、矩形選択と検索に退行がないこと。動画と処理量の比較を保存すること。環境のため実行できない描画系は、成功に含めず未検証として記録します。

### 第3段階 GTK4の連続ズームで古い画像候補を使わないようにする

[GTK4 widget試験](../../../tests/gtk4/test_gtk4_widget.c)の単発ズーム試験を基に、候補準備後の倍率変更・スクロールバー切替・サイズ変更完了を順序制御できる再現を作ります。画像候補の寸法、レイアウトとサイズ要求の版、ズーム世代、スクロールバーの待機状態を記録し、不一致が生じる変更を確定させます。
